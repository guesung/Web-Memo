# 노션 DB 카탈로그

이 플러그인이 읽고 쓰는 노션 DB의 **식별자·속성·접근 규칙의 단일 진실 공급원(SSOT)**이다.
스킬 본문에는 ID를 두지 않는다. 노션을 건드리는 스킬은 **시작 전에 이 파일을 읽고** 필요한 값을 채운다.

ID가 바뀌거나 속성이 늘면 **여기만 고친다.**

모든 DB는 개인 워크스페이스(guesung)에 있고 **`notion-home` MCP**로만 접근한다 — `API-post-page`, `API-patch-page`, `API-query-data-source`, `API-patch-block-children`, `API-retrieve-page-markdown`, `API-retrieve-a-page`. `claude.ai Notion`으로 열면 404다. 접근 실패 시 가장 먼저 의심할 것은 권한이 아니라 **MCP를 바꿔 쓴 것**이다.

> 회사판(`/nudge:` 플러그인)과 **같은 개인 DB를 공유한다.** 회사 작업과 개인 작업이 같은 업무 로그·QA 항목·개발 위키 DB(문제 해결 기록)에 쌓이고, 프로젝트 select로 갈린다. DB를 옮기면 양쪽 플러그인의 이 파일을 모두 고쳐야 한다.

## 개인 업무 로그

작업 하나 = 페이지 하나.

| 식별자 | 값 |
|---|---|
| database | `5f408e05-0015-4532-bcd8-bd36439bec5a` |

### 속성

`이름` · `프로젝트` · `상태` · `작업 시작 날짜` · `메모 / 일정` · `TODO` · `대기 작업` · `PR` · `우선순위` · `평가` · `회고` · `블로그 소재` · `ID`

이 플러그인이 채우는 것:

| 속성 | 타입 | 채우는 규칙 |
|---|---|---|
| `이름` | title | 기획명. 짧은 명사구 (회사판과 달리 슬랙 URL 링크가 없다 — 개인 작업에는 스레드가 없다) |
| `프로젝트` | select | [레포 경로 ↔ 프로젝트](#레포-경로--프로젝트) 참조. 신규 프로젝트면 비운다 |
| `상태` | status | **스킬은 쓰지 않는다.** 사람과 notion-orca 러너가 관리한다. 읽기(idea ④의 중복 확인)만 한다. select가 아니라 status 타입이다 |
| `작업 시작 날짜` | date | 생성일 |
| `시작 단계` | select | `논의` / `기획` / `설계` / `구현` / `QA` / `이슈 해결`. **스킬은 쓰지 않는다** — 사람이 고르고 notion-orca 러너가 읽어 시작 스킬을 정한다: 논의→`/gs:discuss`, 기획→`/gs:idea`, 설계→`/gs:design`, 구현→`/gs:implement`, QA→`/gs:self-qa`, 이슈 해결→`/gs:issue-solve`. 비어 있거나 모르는 값이면 기획. `논의`는 사람과 같이 기획·설계를 정하는 입구이고(확정하면 곧장 구현으로 간다), `기획`부터 고르면 AI가 기획·설계를 정한 뒤 설계를 설명해 승인을 받는다. `이슈 해결`은 파이프라인 순서 밖의 별도 입구로, 카드에 이미 적힌 버그·에러 리포트에서 바로 진단·구현으로 들어간다. 프로젝트별로 지원 여부가 갈리므로(`apps/cli/notion-orca/runner.ts`의 `PROJECT_SKILLS`) 매핑 없는 프로젝트에서 고르면 실행이 `UNKNOWN_ERROR`로 실패한다 |
| `TODO` | rich_text | implement-loop가 `남은 n건: …`으로 갱신 |
| `PR` | relation | implement-loop 마무리가 채운다. **url이 아니라 GitHub PR DB로 가는 relation이다** — URL 문자열을 그대로 넣으면 실패한다 |
| `블로그 소재` | rich_text | `/gs:blog-material`이 `<제목 후보> — <왜 쓸 만한가>` 한 줄씩 2~3개. 기존 값은 덮지 않고 아래에 잇는다 |
| `ID` | unique_id | 노션이 매긴다. **값 자체가 `DB-123` 형태다 — `DB-`를 두 번 붙이지 않는다** |

> 설계·기획 확정을 담을 속성이 없다. 확정 도장은 본문 `## 기획서`·`## 설계서` 첫 줄에 quote 블록으로 둔다.

### 본문 골격

카드 본문은 **H1 두 개로 갈린다.** DB 기본 템플릿이 그 모양이고, 파이프라인은 그 경계를 지킨다.

```
목차
# 인간 작성
  ### 기획
  ### 설계
# AI 작성
  ## 기획서
  ## 디자인
  ## 설계서
  ## TDL
  ## QA 체크리스트
  ## 논의 필요
  ## 해결한 문제
  ## 루프 로그
```

`/gs:idea` ④가 이 골격을 만든다. **API로 만든 페이지에는 DB 기본 템플릿이 적용되지 않으므로** 두 H1까지 스킬이 직접 만들어야 한다. 여덟 제목은 **이 이름 그대로** 둔다 — design·implement-loop가 제목으로 섹션을 찾으므로 이름을 바꾸면 파이프라인이 끊긴다. 회사판(6개)과 달리 `## 기획서`·`## 디자인`이 앞에 붙는다 — 개인은 기획·디자인도 만들어야 하기 때문이다.

`## 논의`는 이 골격에 없다 — `/gs:discuss`가 합의를 처음 기록할 때 `# AI 작성` 맨 끝에 만든다.

`## QA 체크리스트`에는 데이터를 두지 않는다 — [QA 항목](#qa-항목) DB 링크와 요약 한 줄만 남긴다.

[AI 작성 경계](#ai-작성-경계)를 반드시 함께 읽는다.

### AI 작성 경계

**AI는 `# AI 작성` 아래만 고친다.** `# 인간 작성` 아래는 **읽기만 한다** — 사람이 자기 손으로 적어두는 자리이고, 여기에 스킬이 손대면 사람은 자기가 쓴 것이 남아 있는지 매번 확인해야 한다. 그 확인 비용이 자동화로 아낀 것보다 크다.

| 하는 것 | 하지 않는 것 |
|---|---|
| `# AI 작성` 아래 섹션을 만들고 채우고 지운다 | `# 인간 작성`·`### 기획`·`### 설계` 블록을 고치거나 옮기거나 지운다 |
| `# 인간 작성` 아래 내용을 **읽어** 기획·설계의 맥락으로 쓴다 | 거기에 내용을 덧붙인다 — 비어 있어도 채우지 않는다 |
| 사람이 적은 것과 어긋나면 `## 논의 필요`에 적는다 | 사람이 적은 것을 고쳐서 맞춘다 |

**섹션을 찾을 때는 `# AI 작성` 아래에서 찾는다.** `# 인간 작성` 쪽에도 `### 기획`·`### 설계`가 있어서, 제목 문자열만으로 찾으면 사람 자리를 집는다. 레벨(`##` vs `###`)과 부모 H1을 함께 본다.

**골격이 없는 옛 카드**(H1 없이 `##` 섹션만 최상위에 있는 것)를 만나면 **구조를 옮기지 않는다.** 있는 자리에 그대로 쓰고, 마지막 출력에 `본문 골격: 구버전 (H1 없음)` 한 줄만 남긴다. 옮기는 순간 사람이 그 카드에서 무엇을 잃었는지 알 수 없다.

## QA 항목

행 하나 = QA 항목 하나. **모든 작업의 항목이 이 DB 한 곳에 쌓이고** `작업` relation으로 구분된다. 작업별 페이지를 따로 만들지 않는다 — "수동 비율"·"FAIL 잦은 유형"을 세려면 한 곳에 있어야 한다.

| 식별자 | 값 |
|---|---|
| 페이지 "QA 항목" (인라인 DB가 놓인 페이지) | `3cb89de0-2fde-8048-bcd2-cc834d7e03f6` |
| 인라인 DB database | `67c9937c-44f1-4d43-b306-d6fd66031cac` |
| 인라인 DB data source | `bf2d9b85-98bb-4d4f-9ec4-d6a2018ff02f` |
| `작업` relation 대상 = 업무 로그 data source | `8412989c-11e3-4685-8af9-35299fc6c097` |

| 속성 | 타입 | 채우는 규칙 |
|---|---|---|
| `항목` | title | "X하면 Y가 보인다" — 관측 가능한 문장 하나 |
| `작업` | relation | 개인 업무 로그 페이지 |
| `ID` | text | `Q-01`, `Q-02` … 작업 안 순번 |
| `유형` | select | `자동` / `수동` |
| `상태` | select | `미실행` → `PASS` / `FAIL` / `수동 대기` → (사람이) `수동 확인` |
| `전제` | text | 경로 · 로그인/데이터 상태 · 뷰포트 |
| `판정 기준` | text | 무엇을 보고 PASS라 하는가. DOM·텍스트·네트워크·스크린샷 중 하나로 |
| `재현 방법` | text | 수동만. `진입 → 조작 → 기대 결과 → 확인 포인트` |
| `수동 사유` | text | 수동만. 왜 브라우저로 못 보는가 |
| `증거` | url | 스크린샷·PR 링크 |
| `회차` | number | 실행 회차 |
| `실행일` | date | |

- `수동 확인` 상태는 **스킬이 만들지 않는다.** 사람만 찍는다.
- 갱신할 때 기존 행을 지우지 않는다. ID가 같으면 갱신, 새 ID만 추가.

## 개발 위키 DB — 문제 해결 기록

막혔다가 뚫은 문제를 한 행으로. **사람 승인 없이 쓰지 않는다**(`/gs:problem-log` ②).

블로그 `/wiki`가 렌더하는 **공개 위키와 같은 DB**다(2026-09-14에 옛 "문제 해결 일지DB" 91건을 여기로 옮겼다). 옛 DB(`35189de0-…`)는 비어 있고 더 쓰지 않는다. `/wiki:draft`가 쓰는 규칙은 `~/.claude/skills/wiki/references/wiki-db.md`에 있다.

**속성표는 2026-09-20에 `API-retrieve-a-data-source`로 실제 DB와 대조해 맞췄다.** 이 DB는 노션에서 사람이 구조를 바꿀 수 있어 문서가 쉽게 낡는다. 그래서 `/gs:problem-log`는 쓰거나 조회하기 전에 실제 속성명을 한 번 대조한다.

| 식별자 | 값 |
|---|---|
| database | `447c1ee8-b8d0-4d79-b9cd-f898d7a72e7c` |
| data source | `6f5083bc-ca1b-4b58-a63e-fb323cc69cc8` |

| 속성 | 타입 | 채우는 규칙 |
|---|---|---|
| `Name` | title | **증상** 한 줄. 원인이 아니라 겉으로 드러난 현상 (예: `드롭다운이 열린 상태의 Escape가 메모 상세까지 닫음`) |
| `요약` | rich_text | `상황`(무엇이 어떻게 안 됐나) · `원인`(왜 그랬나 + 확인한 근거, 못 밝혔으면 `미확인 — 우회함`) · `트레이드 오프 / 해결 과정`(다른 선택지가 있었고 그중 골랐을 때만, 없으면 생략) · `해결 방법`(무엇을 바꿔서 뚫었나, 커밋 해시나 `파일:라인`, 아직이면 `(아직 해결은 X)`로 시작)을 순서대로 레이블(볼드, `상황: `처럼)만 붙여 이어붙인다. 값이 없는 항목은 레이블째로 건너뛴다. 코드 식별자는 인라인 코드로. **rich_text 한 조각은 2000자까지**라 조각으로 나눠 넣는다(레이블은 볼드 조각, 본문·식별자는 각각 별도 조각) |
| `메모` | rich_text | 업무 로그 페이지 mention · PR 링크 |
| `AI 작성` | checkbox | **항상 `true`.** 스킬이 쓰는 행은 전부 AI가 작성한 것이다 |
| `Tags` | multi_select | 본문 내용을 보고 **기존 옵션 중에서만** 골라 채운다. 새 옵션은 만들지 않는다. 전체 목록은 `API-retrieve-a-data-source`로 조회. 자주 쓰는 것: `SEO`·`SSR`·`SSG`·`Frontend`·`Mono Repo`·`pnpm`·`Github Actions`·`Build`·`자동화`·`기록`·`Infra`·`성능 최적화`·`클린 코드`·`AI` |
| `유형` | select | `트러블 슈팅` · `설계 판단` · `트레이드 오프 고민` · `고민` · `개발 기록` · `깊이 있는 학습` · `공식 문서 번역` · `환경 기록`. 막혔다가 원인을 찾아 뚫은 문제는 `트러블 슈팅`, 여러 선택지 중 하나를 고른 판단이면 `설계 판단`(장단을 저울질했으면 `트레이드 오프 고민`), 구현 과정 기록은 `개발 기록`, 환경 세팅은 `환경 기록` |
| `상태` | status | **항상 `작성 완료`**(`{"status": {"name": "작성 완료"}}`). 나머지 옵션은 `작성 전` · `작성 중` · `작성 중단`. 등급을 나누는 건 사람이 노션에서 한다 |
| `공개` | checkbox | **스킬은 체크하지 않는다.** 블로그 공개 여부를 정하는 칸으로 보이지만 정확한 의미는 확인하지 못했다(2026-09-20). 공개는 사람이 노션에서 켠다 |
| `프로젝트` | select | [레포 경로 ↔ 프로젝트](#레포-경로--프로젝트) 참조 |
| `작성일` | date | 오늘 |

- 실제 DB에는 위 표에 없는 `발표일`(date)·`배운 점`(rich_text)·`더 나아가서`(rich_text)도 있다(2026-09-25 확인). `/gs:problem-log`는 채우지 않는다 — 사람이 노션에서 쓰는 칸이다.
- 옛 문서에 있던 `카테고리`·`Project`·`Status`·`날짜`는 **실제 DB에 없다**(2026-09-20 확인). 옛 이름으로 쓰거나 필터하면 `validation_error: Could not find property`가 난다. 예전에 `카테고리`가 하던 분류는 지금 `유형`이 한다.
- **본문에도 같은 내용을 넣는다** — `### 상황` · `### 원인` · `### 해결 과정`(있을 때만) · `### 해결 방법` · `### 메모`(있을 때만). 블로그는 본문만 렌더하므로, 칸에만 두면 나중에 공개했을 때 빈 글이 된다. 옮긴 91건도 이 형식이다.
- 행 생성은 `API-post-page`(속성만), 본문은 `API-update-page-markdown`의 `replace_content`. `post-page`의 `children`은 문단·불릿만 받아 헤딩이 빠진다. `parent`는 `{"type": "database_id", "database_id": "<위 database>"}` 형태로 쓰면 된다(2026-09-20 확인).

## 레포 경로 ↔ 프로젝트

프로젝트 select는 개인 업무 로그와 개발 위키 DB가 함께 쓴다(두 DB 모두 속성 이름이 `프로젝트`다). **선택지가 서로 다르므로** 아래 표를 그 DB의 선택지로 한 번 더 거른다.

| 레포 경로 | `프로젝트` |
|---|---|

역방향(`프로젝트` → 레포 경로)은 `/gs:design` §0-4가 쓴다.

## 왜 한 곳에 모았나

- **ID는 스킬의 지식이 아니라 환경의 사실이다.** 스킬마다 적어두면 DB를 옮겼을 때 어느 스킬이 옛 ID로 남았는지 알 수 없다.
- **회사판과 DB를 공유하므로 더 그렇다.** 두 플러그인 네 스킬이 같은 data source를 가리킨다. 이 파일이 어긋나면 노션이 404를 뱉을 때까지 드러나지 않는다.
