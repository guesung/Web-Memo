# 프로젝트 문서 규격

이 플러그인의 에이전트들이 **대상 레포 안에서** 읽는 문서들의 규격이다. 스킬·에이전트 본문에는 골격을 두지 않고 여기를 참조한다 — 골격이 여러 군데 흩어지면 문서마다 항목이 어긋난다.

| 문서 | 경로 (대상 레포 기준) | 읽는 쪽 | 없으면 채우는 곳 |
| --- | --- | --- | --- |
| 프로젝트 정체 | `docs/project-identity.md` | `gs:planner` | `/gs:idea` §0-4 · `/gs:discuss` ① |
| 디자인 시스템 | `docs/design-system.md` | `gs:designer` | `/gs:design` §0-5 · `/gs:discuss` ② |
| 아키텍처 | `docs/architecture.md` | `gs:frontend-dev` · `gs:backend-dev` · `gs:qa-verifier`(`## QA 실행`만) | `/gs:implement` §0-8 |
| 이벤트 명세 | `docs/events.md` | `gs:event-analyst` | `/gs:implement` §이벤트 로깅 |

## 왜 레포 안인가

노션이나 OS 레포에 모아두면 대상 코드와 떨어져 드리프트가 난다. 스택을 바꾸는 커밋과 문서를 고치는 커밋이 같은 PR에 들어가야 문서가 거짓말을 하지 않는다. 에이전트는 이미 레포 경로를 인자로 받으므로 찾는 비용도 없다.

---

## docs/project-identity.md — 기획의 바닥

`gs:planner`가 기획서 초안을 쓰기 전에 읽는다. **"이 아이디어를 이 프로젝트가 해야 하는가"** 를 판단할 근거다. 이게 없으면 planner는 아이디어만 보고 기획하므로, 방향이 다른 기능이 그럴듯하게 들어온다.

### 골격 — 정체

여섯 항목. 제목을 그 이름 그대로 쓴다 — planner가 제목으로 섹션을 찾는다.

| 항목 | 내용 |
| --- | --- |
| 정체 | 이 프로젝트는 무엇인가. 한 문장. "~하는 서비스" 형태 |
| 페르소나 | 1순위 사용자 한 명. 나이·직업 나열이 아니라 **어떤 상황에서 무엇이 아쉬운 사람인지**. 만든 사람 본인이면 그렇게 적는다 |
| 톤·태도 | 제품이 사용자에게 말 거는 방식. UI 카피와 기능 결정의 기준이 된다 |
| 방향성 | 6~12개월 뒤 어디까지 가려는가. 지금 없는 것을 적어도 된다 |
| 하지 않을 것 | 방향성의 반대편. **비워두지 않는다** — 비어 있으면 기획이 아무 데로나 뻗는다 |
| 제약 | 혼자 만드는 사람의 시간·비용·기술 제약. 유료 API를 못 쓴다거나 주말에만 만든다거나 |

### 인터뷰 질문 — 정체

문서가 없을 때 `/gs:idea`는 묻지 않고 이 질문들의 답을 아이디어·레포에서 찾아 채운다(근거 없으면 `추정:`). `/gs:discuss`는 조사로 안 나오는 것만 사람에게 한 건씩 묻는다.

1. 이 프로젝트를 한 문장으로 하면? → `정체`
2. 이걸 제일 먼저 쓸 사람은 누구고, 그 사람은 지금 어떤 상황에서 아쉬운가? → `페르소나`
3. 사용자에게 어떤 태도로 말 걸고 싶은가? (담백하게 / 친근하게 / 전문가처럼 …) → `톤·태도`
4. 반년~1년 뒤 이 프로젝트가 어디까지 가 있으면 만족스러운가? → `방향성`
5. 반대로, 사람들이 원해도 안 할 것은? → `하지 않을 것`
6. 시간·비용·기술에서 못 넘는 선이 있나? → `제약`

답이 짧으면 그대로 적는다. 살을 붙이지 않는다 — 근거(아이디어 문장·레포·사람의 답)가 있는 것만 단정하고, 없는 것은 `추정:`으로 표시한다. 이 문서는 AI가 상상하는 자리가 아니다.

## docs/design-system.md — 화면의 바닥

`gs:designer`가 와이어프레임을 그리기 전에 읽는다. 이게 없으면 **작업할 때마다 시각 언어가 조금씩 달라진다.** 정체 문서의 `톤·태도`가 "담백하게"라고 적혀 있어도, 색·간격·모서리로 번역돼 있지 않으면 매번 다시 정하게 되기 때문이다. 이 문서는 그 번역본이다.

### 골격 — 디자인 시스템

```markdown
## 토큰
| 항목 | 내용 |
| 컬러 | 역할 이름으로 적는다 — 배경/표면/본문/보조 텍스트/강조/위험. 색상 코드만 나열하지 않는다 |
| 타이포 | 크기 단계(제목1/제목2/본문/캡션)와 각각의 굵기·행간 |
| 간격 | 쓰는 단계만 (4·8·16·24·32 등). 그 밖의 값은 쓰지 않는다는 뜻이다 |
| 모서리·그림자 | 굴림 정도와 높이 단계. "그림자 안 씀"도 답이다 |
| 정의 위치 | 이 토큰들이 코드 어디에 있는가 (`tailwind.config.ts`·`globals.css` 등) |

## 컴포넌트 인벤토리
| 컴포넌트 | 위치 | 변형(variant) | 쓰는 자리 |
| Button | `src/components/Button.tsx` | primary / ghost | … |

## 레이아웃
| 항목 | 내용 |
| 반응형 기준 | 브레이크포인트와 각 구간에서 달라지는 것 |
| 페이지 골격 | 헤더·사이드바·본문 폭 등 화면 공통 구조 |
| 상태 표현 | 빈 화면·로딩·에러를 이 프로젝트는 어떤 방식으로 보여주는가 (스켈레톤/스피너/문구) |
```

`상태 표현`을 골격에 박아둔 이유: designer가 와이어프레임에 빈/로딩/에러를 빠뜨리면 QA 항목이 나올 수 없고, 그 상태는 사용자가 실제로 제일 자주 만나는 화면이다.

### 인터뷰 질문 — 디자인 시스템

문서가 없을 때 `/gs:design`이 채운다. **아키텍처 문서와 같은 원칙 — 코드에서 읽을 수 있는 건 묻지 않는다.** `tailwind.config.*`·전역 CSS·`src/components/` 폴더를 훑어 토큰과 컴포넌트 인벤토리를 먼저 채운다. 읽어서 알 수 없는 것도 묻지 않고 채우고(근거 없으면 `추정:`), 설계 설명의 `자동 작성 문서`로 노출한다. `/gs:discuss`에서는 조사로 안 나오는 것만 사람에게 묻는다.

읽어서 알 수 없는 것 — AI 경로는 아래 순서로 찾아 채우고, `/gs:discuss`는 이것만 사람에게 묻는다:

1. 정체 문서의 `톤·태도`를 화면으로 옮기면 어떤 인상인가? (여백 넉넉한 / 정보 밀도 높은 / 둥글고 부드러운 …)
2. 빈 화면·로딩·에러를 어떤 방식으로 보여줄 것인가
3. 다크 모드를 지원할 것인가

세 번째는 **작게 물어보이지만 나중에 바꾸면 전 화면을 건드린다.** 처음에 정해두면 designer가 색을 역할 이름으로 쓰게 된다.

## docs/architecture.md — 구현의 바닥

`gs:frontend-dev`·`gs:backend-dev`가 첫 코드를 쓰기 전에 읽는다. 각 에이전트는 **`## 공통` + 자기 섹션만** 읽는다.

FE·BE를 한 파일에 두는 이유: 개인 프로젝트는 대개 풀스택 단일 레포라 경계가 얕고, 두 파일로 나누면 API 계약 같은 걸친 내용이 양쪽에 중복돼 어긋난다.

### 골격 — 아키텍처

세 섹션. 제목을 그 이름 그대로 쓴다.

```markdown
## 공통
| 항목 | 내용 |
| 런타임·언어 | Node 22 / TypeScript |
| 패키지 매니저 | pnpm |
| 폴더 구조 | 라우팅·비라우팅 폴더 규칙, 전역 공통 위치 |
| 실행 | 개발 서버·타입체크·빌드 명령 |
| 배포 | 어디에 어떻게 올라가는가 |
| 환경 변수 | 이름과 용도만. **값은 적지 않는다** |

## 프론트엔드
| 항목 | 내용 |
| 프레임워크 | Next.js App Router 등 |
| 상태 관리 | 서버 상태·클라이언트 상태 각각 무엇으로 |
| 스타일링 | Tailwind / CSS Modules / … + 디자인 토큰 위치 |
| 데이터 패칭 | API 호출 계층이 어디 있고 어떤 규약인가 |
| 컴포넌트 규칙 | 공통 컴포넌트 위치, 분리 기준 |

## 백엔드
| 항목 | 내용 |
| 서버 형태 | Next.js Route Handler / 별도 서버 / 서버리스 |
| DB·ORM | 무엇을 쓰고 스키마 파일이 어디 있는가 |
| API 규약 | 경로 네이밍, 응답 형태, 에러 응답 형태 |
| 인증 | 방식과 세션 저장 위치 |
| 외부 연동 | 쓰는 외부 API와 그 경계 |

## QA 실행
| 항목 | 내용 |
| 서버 기동 | 명령과 뜨는 포트. 준비될 때까지 걸리는 대략의 시간 |
| 진입 URL | 기본 진입 주소 |
| 테스트 계정 | **아이디·비밀번호를 적지 않는다.** 어느 파일 어느 키에 있는지만 (`.env.local`의 `QA_TEST_EMAIL` 등) |
| 로그인 절차 | 로그인 화면 경로와 밟는 순서. 소셜 로그인뿐이면 그 사실 |
| 시드 데이터 | 빈 DB에 초기 데이터 넣는 명령. 없으면 "없음" |
| 뷰포트 | 이 프로젝트의 기본값 — `web` / `webview`(모바일) |
```

**해당 없는 섹션은 지운다.** 백엔드가 없는 프로젝트에 빈 `## 백엔드`를 남기면, backend-dev가 "적혀 있지 않다"와 "없다"를 구분하지 못한다. 지웠으면 `## 공통`에 한 줄 남긴다: `백엔드 없음 — 클라이언트 전용`.

`## QA 실행`은 `gs:qa-verifier`만 읽는다. 이게 없으면 **로그인 뒤 화면이 전부 수동 항목으로 밀려난다** — 에이전트가 서버를 띄우고 로그인을 뚫지 못하면 관측 자체를 못 하기 때문이다. 자동 QA의 사정거리를 정하는 섹션이다.

**여기에 비밀번호·토큰 값을 적지 않는다.** 이 문서는 레포에 커밋된다. 어느 env 키에 들었는지까지가 한계고, 값은 `.env.local`이 갖는다.

### 인터뷰 질문 — 아키텍처

문서가 없을 때 `/gs:implement`가 **묻지 않고** 채운다. **레포에서 읽어낼 수 있는 것부터** 채운다. `package.json`·설정 파일·기존 폴더 구조로 채울 수 있는 항목(런타임·패키지 매니저·프레임워크·스타일링·ORM·실행 명령)은 먼저 읽어서 초안에 채운다.

읽어서 알 수 없는 것 — 설계서·기존 코드·보수적 기본값 순으로 정하고 `[AI 자동 결정]`으로 남긴다:

1. 상태 관리를 서버/클라이언트 각각 무엇으로 가져갈 것인가 (기존 코드에 없을 때)
2. API 응답·에러 응답의 형태를 어떻게 통일할 것인가
3. 인증이 필요한가, 필요하면 어떤 방식인가
4. 배포는 어디로 가는가

신규 프로젝트(스캐폴딩 전)면 읽을 코드가 없으므로 설계서의 스캐폴딩 계획이 곧 이 문서의 초안이다.

## docs/events.md — 측정의 바닥

`gs:event-analyst`가 이벤트 명세를 만들기 전에 읽는다. 이게 없으면 **회차마다 이벤트 이름 규칙이 달라진다** — `memoCreated`·`create_memo`·`memo_created`가 한 프로젝트에 섞이면 대시보드에서 같은 행동을 세 번 찾아야 한다.

### 골격 — 이벤트 명세

```markdown
## 도구
| 항목 | 내용 |
| 도구 | GA4 / PostHog / … |
| 호출 방식 | 이벤트를 찍는 래퍼 함수와 위치 (`packages/shared/src/utils/analytics.ts`의 `trackEvent`) |
| 이름 규칙 | `snake_case` · `목적어_동사(과거형)` 등 |
| 금지 속성 | 넣지 않는 값 — 이메일·이름·사용자 입력 원문 |

## 이벤트
| 이름 | 발생 시점 | 속성 | 답하려는 질문 | 추가된 작업 |
| memo_created | 메모 저장 요청 성공 뒤 | source | 어디서 메모를 가장 많이 만드는가 | DB-207 |
```

**`답하려는 질문` 칸을 비우지 않는다.** 그 칸이 비는 이벤트는 만들 이유가 없었던 이벤트다. 제거된 이벤트는 행을 지우고, 무엇을 지웠는지는 커밋이 기억한다.

### 채우는 방법

로깅 도구가 레포에 있는데 문서가 없으면 `/gs:implement`가 **묻지 않고** 만든다. `## 도구`는 기존 로깅 코드에서 읽고, `## 이벤트`는 레포에 이미 찍히는 이벤트를 grep해 채운다(`답하려는 질문`은 호출 맥락에서 추정해 `추정:`으로 둔다). **로깅 도구가 없는 레포에는 이 문서를 만들지 않는다** — 도구 없는 명세는 아무도 지키지 않는다.

## 갱신 규칙

- **네 문서(정체·디자인 시스템·아키텍처·이벤트 명세) 모두 승인 없이 쓰되 숨기지 않는다.** 쓴 스킬이 `자동 작성 문서 — 검토 권장`에 경로를 올리고 `추정:` 항목을 `[AI 자동 결정]`으로 남긴다. 사람은 설계 설명이나 마지막 보고에서 보고 고친다 — [autonomy.md](autonomy.md)의 자동 결정 원칙과 같다.
- 에이전트는 이 문서들을 **읽기만 한다.** 구현 중 스택이 문서와 달라졌으면 고치지 말고 보고에 한 줄 남긴다. 문서를 고치는 건 스킬(`/gs:idea`·`/gs:design`·`/gs:implement`·`/gs:discuss`) 몫이다.
- 문서와 코드가 어긋나면 **코드가 맞다.** 에이전트는 코드를 따르고 그 사실을 보고한다.
- 문서가 있어도 내용이 비었거나 `TBD`뿐이면 없는 것으로 친다.
