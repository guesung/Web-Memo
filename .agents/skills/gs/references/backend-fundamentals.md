# 백엔드 판단 기준 — Backend Fundamentals

`gs:backend-dev`가 커밋 전에 자기 코드를 훑는 기준이다. [frontend-fundamentals.md](./frontend-fundamentals.md)와 짝을 이루지만, 원문이 있는 FE와 달리 **이 문서는 특정 출처의 요약이 아니라** 개인 프로젝트 규모에 맞춰 추린 것이다. 엔터프라이즈 계층 패턴(헥사고날·CQRS 등)은 의도적으로 넣지 않았다 — 혼자 만드는 프로젝트에서 그 구조는 지키는 비용이 얻는 것보다 크다.

전제: FE의 "변경하기 쉬운 코드"에 하나가 더 붙는다. **서버는 틀려도 화면처럼 눈에 안 띈다.** 잘못된 응답과 반쯤 저장된 데이터는 조용히 남아서 나중에 발견된다. 아래 기준은 전부 "틀렸을 때 얼마나 빨리 티가 나는가"를 묻는다.

## 4가지 기준

| 기준 | 정의 | 자문할 것 |
| --- | --- | --- |
| **경계 명확성** | 이 코드가 무엇까지 책임지는지 | 이 함수가 HTTP를 아는가, 아니면 도메인만 아는가? |
| **실패 다루기** | 잘못됐을 때 어떻게 되는지 | 이게 실패하면 호출한 쪽이 무엇을 알게 되나? |
| **데이터 정합성** | 중간에 끊겼을 때 남는 상태 | 3단계 중 2단계에서 죽으면 DB에 무엇이 남나? |
| **변경 안전성** | 고쳤을 때 누가 깨지는지 | 이 응답 형태를 바꾸면 FE의 어디가 깨지나? |

## 기준이 부딪힐 때

- 경계를 지키려고 계층을 쪼개면 **파일 수가 늘고 읽기 어려워진다.**
- 정합성을 지키려고 트랜잭션을 넓게 잡으면 **락이 길어지고 외부 호출이 물린다.**

판단 규칙:

> **틀린 데이터가 남는 쪽**을 먼저 막는다. 성능·구조는 그다음이다.
> 계층은 **실제로 재사용되거나 테스트가 필요한 순간에** 쪼갠다. 미리 쪼개지 않는다.

한 줄로: **데이터가 깨지는 건 되돌리기 어렵고, 구조가 못생긴 건 나중에 고칠 수 있다.**

## 항목별 체크

### 경계 명확성

- **HTTP를 아는 코드는 라우트 핸들러까지다.** 도메인 로직 함수가 `req`/`res`, 상태 코드, 헤더를 알면 그 함수는 테스트도 재사용도 안 된다. 핸들러는 "파싱 → 도메인 함수 호출 → 응답 형태로 변환"만 한다.
- **DB 접근을 도메인 로직에 흩지 않는다.** 다만 개인 프로젝트에서 Repository 클래스를 세우라는 뜻은 아니다 — 쿼리를 한 파일(`src/server/db/*.ts`)에 모으는 정도로 충분하다.
- **입력 검증은 경계에서 한 번.** 핸들러 진입 직후 스키마로 검증하고, 그 안쪽은 검증된 타입만 받는다. 안쪽에서 또 `if (!x) return` 하고 있으면 경계가 새고 있다는 신호다.
- 외부 API 호출은 감싸는 함수를 하나 두고 도메인 로직이 그걸 부른다. 응답 형태가 바뀔 때 고칠 자리가 한 곳이어야 한다.

### 실패 다루기

- **에러를 삼키지 않는다.** `catch {}`나 `catch { return null }`은 호출한 쪽에서 "없음"과 "실패"를 구분할 수 없게 만든다. 최소한 로그를 남기고, 가능하면 실패를 그대로 위로 던진다.
- **응답의 실패 형태를 성공 형태와 같은 수준으로 정한다.** `{ error: "..." }`인지 `{ ok: false, message }`인지가 엔드포인트마다 다르면 FE가 매번 다르게 분기한다. 설계서·`architecture.md`의 `API 규약`을 따른다.
- **상태 코드를 뭉뚱그리지 않는다.** 잘못된 입력(400)·인증 없음(401)·권한 없음(403)·없는 리소스(404)·서버 잘못(500)을 구분한다. 전부 500이면 FE가 "다시 시도"밖에 못 보여준다.
- **에러 메시지에 내부 정보를 담지 않는다.** 스택·쿼리·env 값은 로그로, 응답에는 사람이 읽을 문장만.

### 데이터 정합성

- **여러 테이블을 함께 쓰면 트랜잭션으로 묶는다.** "주문 생성 + 재고 차감"처럼 하나만 성공하면 안 되는 쌍이 대상이다.
- **트랜잭션 안에서 외부 API를 호출하지 않는다.** 응답이 느리면 그동안 락이 잡혀 있다. 외부 호출은 트랜잭션 앞이나 뒤로 뺀다.
- **재실행해도 같은 결과가 나오게 만든다.** 결제·알림처럼 두 번 실행되면 안 되는 것에는 멱등 키나 중복 검사를 둔다. 클라이언트의 재시도·더블 클릭은 반드시 일어난다.
- **마이그레이션은 되돌릴 수 있는 형태로.** 컬럼 삭제·이름 변경은 "추가 → 양쪽 쓰기 → 제거" 순서로 나눈다. 개인 프로젝트라 데이터가 적더라도, 되돌릴 수 없는 작업은 되돌릴 수 없다.

### 변경 안전성

- **응답 형태 변경은 FE 재작업이다.** 필드 이름·타입을 바꾸면 그 사실을 보고에 명시한다. 조용히 바꾸면 FE는 런타임에야 안다.
- **DB 스키마 변경은 마이그레이션 파일과 같은 커밋에** 둔다. 나눠 커밋하면 중간 커밋에서 앱이 안 뜬다.
- **N+1을 만들지 않는다.** 목록을 돌면서 항목마다 쿼리를 날리고 있으면 join이나 `in` 조회로 바꾼다. 개인 프로젝트의 데이터가 적어도, 이건 나중에 느려지는 게 아니라 처음부터 잘못 짠 것이다.
- **인덱스는 실제 쓰는 조회 조건에만.** 설계서에 없는 인덱스를 미리 만들지 않는다.

## 시크릿

- **키·토큰·비밀번호를 코드에 쓰지 않는다.** env 변수 자리만 만들고 보고에 "채울 것"으로 남긴다.
- `.env.example`에는 **키 이름만** 넣는다. 값은 절대.
- 로그에 요청 본문을 통째로 찍지 않는다 — 비밀번호·토큰이 섞여 들어간다.

## 전역 컨벤션과 부딪힐 때

전역 `CLAUDE.md`의 프론트엔드 TypeScript 컨벤션이 정한 네이밍·JSDoc·화살표 함수·`async/await` 규칙은 서버 코드에도 그대로 적용한다. 이 문서와 부딪히는 항목은 없지만, 부딪히면 **전역 컨벤션이 우선**이다. 이 문서는 컨벤션이 다루지 않는 "무엇이 위험한가"를 다룬다.

## 이 문서가 다루지 않는 것

인증 방식·ORM 선택·서버 형태 같은 **결정**은 여기 없다. 그건 프로젝트마다 다르고 `<레포>/docs/architecture.md`가 갖는다. 이 문서는 어떤 스택을 쓰든 같은 판단 기준만 담는다.
