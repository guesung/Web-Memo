# 클린 코드 기준 — Frontend Fundamentals

토스 팀의 [Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/)("변경하기 쉬운 프론트엔드 코드를 위한 지침서")를 이 플러그인용으로 압축한 문서다. `gs:frontend-dev`가 커밋 전에 자기 코드를 훑는 기준으로 쓴다.

전제: **좋은 코드 = 변경하기 쉬운 코드.** 아래 기준은 전부 "나중에 이 코드를 고칠 때 얼마나 덜 아픈가"를 묻는다.

## 4가지 기준

| 기준            | 원문 정의                                                        | 자문할 것                                        |
| --------------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| **가독성**      | 코드가 읽기 쉬운 정도                                            | 이 코드를 이해하려고 몇 군데를 오가야 하나?      |
| **예측 가능성** | 동료가 함수·컴포넌트의 동작을 얼마나 예측할 수 있는지            | 이름과 타입만 보고 동작을 다 알 수 있나?         |
| **응집도**      | 수정되어야 할 코드가 항상 같이 수정되는지                        | 한쪽만 고치고 다른 쪽을 빼먹을 수 있나?          |
| **결합도**      | 코드를 수정했을 때의 영향 범위                                   | 이걸 고치면 몇 개 파일이 따라 바뀌나?            |

## 기준이 부딪힐 때

네 기준은 동시에 만족되지 않는다. 원문이 명시하는 트레이드오프:

- 응집도를 높이려고 공통화·추상화하면 **가독성이 떨어진다.**
- 중복을 허용하면 결합도는 낮아지지만 **응집도가 떨어진다.**

판단 규칙(원문):

> 함께 수정되지 않으면 오류가 발생할 수 있는 경우에는, 응집도를 우선해서 코드를 공통화·추상화한다.
> 위험성이 높지 않은 경우에는, 가독성을 우선하여 코드 중복을 허용한다.

한 줄로: **빼먹으면 버그 나는 것만 묶고, 나머지는 중복을 놔둔다.**

## 항목별 체크

### 가독성

**맥락 줄이기**

- 동시에 실행되지 않는 분기가 한 함수·컴포넌트에 섞여 있으면 별도로 쪼갠다. 상호배타적 코드가 교차하면 개선 대상.
- 한 번에 이해해야 할 맥락은 6~7개까지. 넘으면 Wrapper·커스텀 컴포넌트로 구현 상세를 감싸고 부모에는 단순한 인터페이스만 남긴다.
- Hook은 로직 종류(쿼리 파라미터·상태·API)로 뭉치지 말고 책임 단위로 쪼갠다. 쿼리 파라미터 하나당 Hook 하나(`useCardIdQueryParam()`).

**이름 붙이기**

- 복잡한 조건식에는 변수명을 붙여 의도를 드러낸다. 단, 여러 줄이거나 반복되거나 테스트가 필요할 때. `arr.map(x => x * 2)` 같은 1회성 단순 로직은 그냥 둔다.
- 매직 넘버에 이름을 붙인다. `delay(300)` → `ANIMATION_DELAY_MS`. 숫자만 보고 뜻을 모르면 매직 넘버다.

**위에서 아래로 읽히게 하기**

- 시점 이동을 줄인다. 조건을 이해하려고 파일·함수를 오가게 만들지 말고, switch문이나 정책 매핑 객체로 한곳에 편다. 성급한 추상화가 시점 이동을 만든다.
- 중첩 삼항 연산자는 `if-else`로 푼다.
- 범위 비교는 부등식 순서대로. `80 <= score && score <= 100` (하한 → 변수 → 상한).

### 예측 가능성

- 같은 이름은 같은 동작을 해야 한다. 원본 라이브러리를 감싼 모듈에 같은 이름(`http`)을 붙이면 토큰 처리 같은 숨은 동작이 생긴다 → `httpService`, `getWithAuth`처럼 동작을 드러내는 이름으로.
- 같은 종류의 함수·Hook은 반환 타입을 통일한다. API 호출 Hook은 Query 객체, 검증 함수는 `{ ok, reason }` 같은 Discriminated Union으로 일관되게.
- 숨은 로직을 드러낸다. 이름·파라미터·반환값에 안 드러나는 부작용(로깅·동기화)은 함수 밖 호출 지점으로 뺀다. **이름과 타입 선언만으로 동작을 전부 알 수 있어야 한다.**

### 응집도

- 파일은 종류(components/hooks/utils)가 아니라 도메인·기능 단위로 묶는다. `../../../Domain2/`처럼 깊은 상대경로 import나 죽은 코드가 남아 있으면 구조가 잘못됐다는 신호.
- 매직 넘버를 상수로 만들어 관련 코드와 함께 수정되게 한다. 같이 바뀌어야 할 것 중 한쪽만 바뀔 수 있으면 응집도 부족.
- 폼은 변경 단위를 보고 설계한다. 필드가 독립 검증·재사용된다면 **필드 단위**, 하나의 비즈니스 기능이거나 필드 간 의존·단계별 입력이면 **폼 전체 단위**.

### 결합도

- 책임이 넓은 Hook은 영향 범위가 폭발한다. 하나의 Hook은 하나의 관심사만.
- 성급한 공통화를 하지 않는다. 반복돼 보여도 페이지마다 로깅 값·닫기 동작·UI가 다르면 공통 컴포넌트만 복잡해진다. **지금도 앞으로도 동일할 것이 확실할 때만 공통화하고, 아니면 중복을 허용한다.**
- Props Drilling을 지운다. 데이터를 쓰지 않고 전달만 하는 컴포넌트를 거치면 Composition(`children`)으로 중간 단계를 없애거나 Context로 직접 공유한다. 단, prop이 그 컴포넌트의 역할·의도를 담고 있으면 Drilling이 아니다.

## 전역 컨벤션과 부딪힐 때

전역 `CLAUDE.md`의 프론트엔드 TypeScript 컨벤션이 항상 우선한다. 실제로 겹치는 지점:

- **매직 넘버 vs "과도한 상수·파일 분리 금지"(전역 10번).** 이름은 붙이되 **쓰는 파일 안의 지역 상수**로 둔다. 별도 `constants` 파일로 빼는 건 여러 도메인에서 광범위하게 재사용될 때만. 툴팁 문구·기본값처럼 한두 곳에서만 쓰는 값은 인라인.
- **추상화 vs 선제적 분리 금지.** 맥락이 실제로 6~7개를 넘어 읽기 힘들 때 쪼갠다. "나중에 쓸 것 같아서" 미리 쪼개지 않는다.
- **성능 최적화.** 리렌더링이 걱정돼도 `useCallback`/`useMemo`는 쓰지 않는다(전역 9번). Hook 분리로 푸는 게 이 문서의 처방이기도 하다.
