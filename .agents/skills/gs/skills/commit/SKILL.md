# /gs:commit — 작업 단위 커밋

## 동작

1. `git status`, `git diff`(staged+unstaged), `git log -n 5`를 병렬로 확인하여 변경 범위와 레포의 커밋 메시지 스타일을 파악한다.
2. 변경사항을 **논리적인 작업 단위로 분리**한다.
   - 파일·디렉터리별이 아니라 **의도/기능/버그 단위**로 묶는다.
   - 예: UI 변경 + API 호출 수정이 섞여 있으면 두 개의 커밋으로 나눈다.
   - 변경이 단일 주제이면 하나의 커밋으로 처리한다.
3. 각 커밋마다:
   - 해당 단위에 속하는 파일만 **명시적으로 `git add <files>`**로 스테이징한다 (`git add -A`, `git add .` 금지).
   - 레포의 기존 커밋 메시지 스타일(컨벤션·언어)을 따른다.
   - 1–2 문장으로 "왜"를 담은 간결한 메시지를 **HEREDOC**으로 전달한다.
4. 커밋 후 `git status`로 결과를 확인하고 한 줄 요약으로 보고한다.

## 커밋 메시지 템플릿

```
<타입>: <무엇을 왜 바꿨는지 한 줄>

(선택) 보충 설명 1–2 문장
```

## 하지 않는 것

- **co-author / Co-Authored-By trailer 추가 금지.** `Generated with Claude Code`, `🤖` 같은 생성 표식도 금지.
- `--no-verify` 등 훅·서명 우회 금지 (사용자가 명시적으로 요청한 경우 제외).
- `--amend`는 사용자가 명시적으로 요청한 경우에만. 기본은 항상 새 커밋.
- `.env`, 자격증명, 대용량 바이너리 등 민감·부적절 파일은 커밋하지 않는다.

## 인자

`$ARGUMENTS` — 커밋 분할 방식이나 메시지 톤에 대한 추가 지시 (선택). 예: "하나로 묶어줘", "이 파일들만 먼저 커밋해줘".
