# /gs:design — 디자인·설계 초안 → 사람 확정

설계 권한은 사람에게 있고, AI는 **사람이 검토할 재료**를 만든다. 회사판과 다른 점 하나 — 회사는 피그마 시안이 있지만 개인은 없으므로, UI가 있는 작업이면 **designer 에이전트가 디자인 명세를 먼저** 만든다.

**⑥이 AI 경로(idea → design)에서 사람이 개입하는 유일한 자리다.** 여기서 승인하면 구현·셀프 QA·테섭 배포·PR까지 묻지 않고 끝까지 간다. 그래서 ⑥은 결정 목록이 아니라 **설계를 사람에게 설명한다** — 기획(`/gs:idea`가 자동 확정했든 `/gs:discuss`에서 합의했든)부터 AI가 정한 것까지 전부 그 설명 안에 녹인다. 규약은 [autonomy.md](../../autonomy.md)가 SSOT다.

사람과 같이 정하는 경로는 [`/gs:discuss`](../discuss/SKILL.md)다. 거기서 확정한 카드는 이 스킬을 거치지 않고 `/gs:implement-loop`로 간다.

```
/gs:discuss ─→ (다른 입구) 사람과 같이 기획·설계 → 확정 → implement-loop
        │       └ 도중에 넘기면 합의(`## 논의`)를 입력으로 idea·design이 이어받는다
        ▼
/gs:idea ─→ 기획 확정 · 씨앗 (한 줄 목표 · 범위 밖)
        │
        ▼
§0 페이지 읽기
 ①-D 디자인      Agent: gs:designer — UI 있는 작업만
 ①   레포 탐색   Explore → 변경 지점 file:line (신규 프로젝트면 스캐폴딩 계획)
 ②   설계서 6항목 목표 · AS-IS · TO-BE · 변경 지점[FE/BE] · 동작 명세 · 범위 밖
 ③   다이어그램   트리거 해당 시에만. 미해당이면 "해당 없음 + 이유"
 ④   막힐 지점 → ## 논의 필요
 ⑤   논의 필요 해소   /gs:interview --auto — 묻지 않고 추천안으로 확정
 ⑥   설계 설명 → 승인 도장   ★ 사람이 승인해야만 찍는다 — AI 경로의 유일한 게이트
        │
        ▼
/gs:implement-loop   구현 → QA → 테섭 배포 → PR (묻지 않는다)
```

**⑤가 ⑥ 앞에 있다.** 미결 항목을 AI 추천안으로 채워 두어야, 사람이 ⑥에서 "이대로 끝까지 가도 되는가"를 한 번에 판단할 수 있다.

## 노션 접근

**시작 전에 [notion-databases.md](../../notion-databases.md#개인-업무-로그)를 읽는다.** 개인 업무 로그는 **`notion-home` MCP**로만 읽고 쓴다.

**본문은 `# AI 작성` 아래만 고친다.** `# 인간 작성` 아래는 읽기만 하고, 섹션도 그 H1 아래에서 찾는다 — [AI 작성 경계](../../notion-databases.md#ai-작성-경계).

## §0. 시작 전 확인

1. **인자 파싱.** 첫 토큰이 `notion.com/…` 이어야 한다. 없으면 멈추고 요구한다.

   URL을 확보했으면 **[orca-worktree.md](../../orca-worktree.md)의 절차대로 현재 워크스페이스 메모에 이 URL을 기록한다.** 실패해도 멈추지 않는다.
2. **페이지 읽기.** `API-retrieve-page-markdown`으로 `## 기획서`·`## 디자인`·`## 설계서`·`## 논의 필요`·`## 논의`를 확보한다. `## 기획서`에 확정 도장이 없으면 `/gs:idea`를 먼저 돌리라고 안내하고 멈춘다 — 기획이 흔들리는 상태에서 설계하면 전부 재작업이다.

   **`## 논의`가 있으면 확정된 입력이다.** [`/gs:discuss`](../discuss/SKILL.md)에서 사람과 합의한 결정이므로 ①-D·① 에이전트 프롬프트에 항목 **원문**을 넣고, ⑤의 `--items`에서 이미 합의된 지점을 뺀다 — 사람이 정한 것을 AI 추천안으로 다시 정하지 않는다. 설계서 초안이 합의와 어긋나면 합의가 이긴다.

   같은 호출로 `# 인간 작성` 아래 `### 기획`·`### 설계`도 읽는다. 사람이 미리 적어둔 것이 있으면 **맥락으로 쓴다** — 거기에 쓰지도, 고치지도 않는다. 설계서 초안이 그것과 어긋나면 `## 논의 필요`에 적는다.
3. **이미 확정된 페이지인지 확인.** `## 설계서` 안에 확정 도장(§⑥)이 있으면 **묻지 않고 `/gs:implement-loop <페이지 URL>`을 그대로 이어서 실행한다.** 이미 사람이 승인한 설계다. `/gs:discuss`가 찍은 `사람 합의` 도장도 같다.

   예외는 하나 — **인자에 재설계를 지시하는 말이 함께 왔을 때**(`다시 설계`·`설계 다시`·`--redesign`)다. 그러면 도장을 지우고 ①부터 돌리되, 기존 설계서는 **지우지 않고** 아래에 이어 쓴다.
4. **레포 경로 판정.** `--repo`가 있으면 그것. 없으면 페이지 속성 `프로젝트`로 [레포 경로 ↔ 프로젝트](../../notion-databases.md#레포-경로--프로젝트)를 역인용한다.
   - **`레포지토리/cashwalk/` 아래면 멈춘다** — 회사 작업은 `/nudge:design` 몫이다. 이 플러그인은 개인 프로젝트 전용이다.
   - **신규 프로젝트(레포 없음)면** ①에서 탐색 대신 스캐폴딩 계획을 세운다. 어디에 만들지(`~/Desktop/레포지토리/guesung/<이름>`)와 스택 후보를 ④ 논의 필요로 낸다.
   - 후보가 둘 이상이면 **묻지 않고 정한다** — 기획서와 겹치는 도메인이 큰 쪽, 같으면 최근 커밋이 새로운 쪽. 고른 이유를 `[AI 자동 결정]`으로 ④에 남기고 ⑥ 설계 설명의 `어디를 고치나`에도 밝힌다.
5. **디자인 시스템 문서 확인 — 화면 변화가 있는 작업일 때만.** `<레포>/docs/design-system.md`를 읽는다. 있고 내용이 차 있으면 ①-D로 간다. 화면 변화가 없으면 이 단계를 건너뛴다.

   **없거나 `TBD`뿐이면 여기서 채운다** — 이게 없으면 designer가 작업마다 조금씩 다른 시각 언어로 화면을 그리고, 그 어긋남은 화면이 쌓인 뒤에야 눈에 띈다.

   1. **먼저 레포에서 읽는다.** `tailwind.config.*`·전역 CSS·`src/components/`를 훑어 [디자인 시스템 골격](../../project-docs.md#골격--디자인-시스템)의 토큰과 컴포넌트 인벤토리를 채운다.
   2. 읽어서 알 수 없는 것은 **묻지 않고 채운다.** [인터뷰 질문](../../project-docs.md#인터뷰-질문--디자인-시스템)의 답을 `project-identity.md`의 `톤·태도` → 기존 화면의 실제 스타일 → 프레임워크 기본값 순서로 찾는다. 그래도 안 나오면 `추정: <내용>`으로 표시한다.
   3. 승인 없이 `<레포>/docs/design-system.md`에 쓴다. `추정:` 항목은 `[AI 자동 결정]`으로 ④에 남기고, 파일 경로를 마지막 출력의 `자동 작성 문서 — 검토 권장`에 올린다.

   **신규 프로젝트(레포 없음)면 여기서 만들지 않는다.** 읽을 코드가 없고, 스캐폴딩 전이라 `정의 위치`를 적을 수도 없다. 대신 톤·다크 모드 여부를 정체 문서에서 끌어와 ④ `## 논의 필요`에 `[AI 자동 결정]`으로 남기고, 문서는 `/gs:implement` 스캐폴딩 이후 다음 `/gs:design` 회차에 만든다.

## ①-D 디자인 — designer 에이전트 (조건부)

이번 작업에 **사용자가 보는 화면 변화가 있으면** `Agent` 도구로 `gs:designer`를 띄운다. 프롬프트에는 **확정된 기획서와 레포 경로만** 넣는다. 디자인 시스템 문서는 옮겨 담지 않는다 — designer가 레포에서 직접 읽는다.

- 결과의 `디자인 명세 초안`을 페이지 `## 디자인`에 쓰고, `결정 필요`는 ④의 `## 논의 필요`로 합친다.
- 화면 변화가 없는 작업(스크립트·API만·리팩토링)은 건너뛰고 `## 디자인`에 `해당 없음 (화면 변화 없음)` 한 줄을 남긴다 — 안 한 것이 판단인지 누락인지 구별되어야 한다.

## ① 레포 탐색

`Explore` 에이전트를 띄운다. 프롬프트에 **기획서·씨앗·레포 경로만** 넣는다. 찾을 것은 셋이다.

- 기획이 말하는 화면·기능의 **진입점** (라우트 파일 · 페이지 컴포넌트 · API 라우트)
- 거기서 갈라지는 **현재 흐름** — 어떤 상태·API·컴포넌트를 거치는가
- 이번에 **고칠 자리** — `path/File.tsx:120` 수준

**신규 프로젝트면 탐색할 레포가 없다.** 대신 스캐폴딩 계획을 세운다 — 만들 폴더 구조·초기 파일 목록·스택. 이것이 ②의 `변경 지점`을 대신한다(전부 `(신규)`).

**못 찾은 것은 지어내지 않는다.** 추측한 `file:line`은 없는 것보다 나쁘다. 못 찾았으면 ④로 넘긴다.

## ② 설계서 6항목

`## 설계서`에 아래 순서로 쓴다. **초안이다. 확정은 사람이 한다.**

| 항목 | 내용 | 출처 |
|---|---|---|
| 한 줄 목표 | 이 작업이 무엇을 되게 하는가 | 씨앗 |
| AS-IS | 지금 이 화면·흐름이 어떻게 도는가. 신규 프로젝트면 `신규 — 해당 없음` | ① 탐색 |
| TO-BE | 무엇이 어떻게 달라지는가 | 기획서 + ①-D + ① |
| 변경 지점 | `[FE]`/`[BE]`/`[공통]` 태그 + `path/File.tsx:120` 목록. 새 파일은 `(신규)` | ① 탐색 |
| 동작 명세 | 입력·상태·분기 표. BE가 있으면 **API 계약**(METHOD·path·요청/응답)도 여기 | 기획서 + ①-D |
| 범위 밖 | 이번에 안 하는 것 | 기획서 |

- **변경 지점의 FE/BE 태그는 `/gs:implement`의 에이전트 라우팅 키다.** 태그 없는 항목은 구현이 라우팅을 못 하므로 반드시 붙인다.
- 기획서·디자인에 없고 레포에서도 확인되지 않는 동작은 **쓰지 않는다.** ④로 넘긴다.
- `범위 밖`을 비워두지 않는다. 비어 있으면 구현 중 범위가 새는 경로다.

## ③ 다이어그램 — 조건부

아래 표에 **해당할 때만** 그린다. 판단 여지를 남기지 않기 위해 임계값을 숫자로 둔다.

| 트리거 | 그리는 것 | 안 그리는 경우 |
|---|---|---|
| 조건 분기 **2개 이상** (상태 · 권한 · 플랫폼) | `flowchart TD` | 분기 1개 이하 |
| 프론트↔서버 왕복 **2회 이상** | `sequenceDiagram` | 단일 조회 |
| 화면·컴포넌트 상태 **3개 이상** | `stateDiagram-v2` | 상태 2개 이하 |
| 새 파일 **3개 이상** 또는 모듈 경계 변경 | `flowchart LR` | 단일 파일 수정 |

노션에는 **code block(language `mermaid`)** 으로 넣는다. 언어가 거부되면 `plain text` 코드 블록으로 넣고 `## 논의 필요`에 한 줄 남긴다.

전부 미해당이면 다이어그램은 **0개**다. 다만 그때도 `## 설계서` 끝에 한 줄을 남긴다.

```
다이어그램: 해당 없음 (분기 1개 · 단일 파일)
```

다이어그램은 **설계서에 이미 쓴 것만** 그린다. 그림에만 있고 글에는 없는 분기를 만들지 않는다.

## ④ 막힐 지점 → `## 논의 필요`

각 항목은 **`무엇이 불명확한가 → 어느 선택지가 있는가 → 내가 추천하는 쪽과 이유`** 로 쓴다. ①-D designer가 낸 `결정 필요`도 여기 합친다.

여기 들어가는 것:

- 기획서·디자인에도 없고 레포에서도 확인 안 되는 동작
- ①에서 변경 지점을 특정하지 못한 부분
- 레포의 현재 구조와 기획의 요구가 충돌하는 지점
- 신규 프로젝트의 스택·폴더 구조 후보
- 설계서대로 만들면 기존 동작이 깨질 것 같은 자리

## ⑤ 논의 필요 해소 — `/gs:interview --auto` 호출

**묻기 전에 여기까지의 결과를 노션에 저장한다.**

그다음 `## 논의 필요` 항목을 **`--items`로 넘기고 `--auto`를 붙여 [`/gs:interview`](../interview/SKILL.md)를 호출한다.** 맥락으로 확정된 기획서·②의 설계서 초안·레포 경로를 함께 넣는다. 조사 우선·추천 채택·보수적 선택 규칙은 그 스킬이 갖고 있다 — 여기서 다시 정하지 않는다.

`--page`는 넘기지 않는다. 그 스킬은 `## 논의 필요`만 건드릴 수 있고, 여기서는 `## 설계서`·`## 디자인` 본문까지 고쳐야 하므로 **반영은 이 스킬이 한다.**

반환받은 네 표를 이렇게 쓴다.

| 반환 섹션 | 여기서 하는 일 |
|---|---|
| `AI가 정한 것 (높음/중간)` | `## 설계서`(또는 `## 디자인`)에 반영하고, 표 전체를 `## 논의 필요`에 `[AI 자동 결정]`으로 남긴다. **⑥ 설계 설명에서 각 결정을 해당 대목에 녹여 설명한다** |
| `조사로 답한 것` | 근거의 `file:line`이 ①의 탐색 결과와 맞는지 확인하고 반영한다 |
| `내가 정한 것 (낮음)` | 반영한다. 마지막 출력에 건수만 알린다 |
| `미해소` | `--auto`에서는 비어 있어야 정상이다. 차 있으면 그 항목을 `## 논의 필요`에 남기고 ⑥ 설계 설명 끝의 `아직 못 정한 것`에 올린다 |

- 반영으로 다이어그램 트리거가 새로 충족되면 ③을 다시 돌린다.
- **미해소가 남아도 ⑥으로 간다.** 예전에는 0건이어야 도장을 찍었지만, 지금은 사람의 검토 자리가 ⑥ 하나뿐이라 여기서 멈추면 사람이 볼 기회 자체가 사라진다. 미해소는 설계 설명에 그대로 드러내 함께 판단하게 한다.
- 되돌리는 비용 `높음` 항목은 `## 논의 필요`에서 **맨 위에** 둔다.

## ⑥ 설계 설명 → 승인 도장

**여기가 AI 경로의 유일한 게이트다.** 승인하면 구현·셀프 QA·테섭 배포·PR까지 묻지 않고 간다. 그래서 여기서는 "AI가 무엇을 정했는가"를 나열하지 않고 **설계를 사람에게 설명한다.** 사람이 판단해야 하는 건 결정 하나하나가 아니라 그것들이 모여 된 설계이고, 결정은 설계 안의 자리에서 읽어야 왜 그렇게 정했는지가 보인다.

**묻기 직전에, 질문 바로 위 본문에 설계 설명을 낸다.** `AskUserQuestion` 카드 안이 아니라 **본문에 둔다** — 카드의 설명 칸은 짧게 잘리고 링크로 열리지도 않는다.

```
작업카드: <페이지 URL>       ← 기획서·설계서 전문은 여기서

## 무엇을 만드나
<기획서의 문제·타깃·MVP 범위를 두세 문장으로. 범위 밖도 한 문장.>

## 어떻게 동작하나
<사용자 입장에서 흐름을 처음부터 끝까지. 화면 변화가 있으면 디자인도 여기서.
 분기·상태·API 왕복이 있으면 그 순서대로.>

## 어디를 고치나
<레포와 그 레포를 고른 이유. 변경 지점을 FE/BE로 묶어 "무엇을 위해 어디를" 수준으로.
 file:line 전체 목록은 카드에 있으니 여기서는 굵직한 것만.>

## 왜 이렇게 설계했나
<설계를 떠받치는 판단들. 각 판단은 "X로 했다. Y도 가능했지만 Z 때문에 뺐다" 형식.
 되돌리는 비용이 높은 판단은 **굵게** 쓰고 빠짐없이 넣는다.>

## 아직 못 정한 것            ← 없으면 섹션째 뺀다
<항목 — 왜 못 정했나 · 이대로 승인하면 구현 중 어떻게 처리되나>

자동 작성 문서 — 검토 권장: docs/project-identity.md · docs/design-system.md   ← 없으면 줄째 뺀다

승인하면 구현 → 셀프 QA → 테섭 배포(develop) → PR 까지 묻지 않고 진행합니다.
```

쓰는 규칙:

- **AI가 정한 것은 설계 설명 안에서 드러낸다.** `/gs:idea`부터 여기까지 `[AI 자동 결정]`으로 남긴 항목 중 되돌리는 비용 `높음`·`중간`은 전부 설명 어딘가에 들어가야 한다. 들어갈 자리가 없는 결정은 설계에 영향이 없다는 뜻이니 빼도 된다. 다만 `높음`은 빼지 않는다.
- **기획을 누가 확정했는지 `무엇을 만드나` 첫 문장에 밝힌다.** `## 기획서` 도장이 `기획 자동 확정 · … · AI`면 "기획은 `/gs:idea`가 사람 검토 없이 확정했다"고 쓴다 — 기획도 여기서 처음 검토된다. `사람 합의 (/gs:discuss)`면 "기획은 논의에서 합의했다"고 쓰고 기획 설명은 한두 문장으로 줄인다.
- `## 논의`에서 합의한 결정은 `왜 이렇게 설계했나`에서 AI가 정한 것과 구별해 쓴다.
- **목록을 산문으로 옮겨 적지 않는다.** "첫째 … 둘째 …"로 결정을 늘어놓으면 모양만 바뀐 목록이다. 설계의 흐름을 따라 쓰고, 결정은 그 흐름에서 나오는 자리에 둔다.
- 설계서에 없는 내용을 설명에 새로 만들지 않는다. 설명은 설계서를 읽는 방법이지 설계서의 확장이 아니다.

**작업카드 URL을 맨 위에 두는 이유** — 설명만 보고 승인하지 말라는 뜻이다. 이 승인은 설계서 한 장이 아니라 그 뒤 전부를 위임하는 계약이다.

- `승인` → `## 설계서` **첫 줄**에 quote 블록으로 도장을 찍는다. 기획서 도장이 `AI` 자동 확정이었으면 `(기획 포함)`을 붙이고 `## 기획서` 도장 아래에도 확인 줄을 더한다. 기획서가 이미 `사람 합의`면 둘 다 하지 않는다. 그리고 `/gs:implement-loop <페이지 URL>`을 이어서 실행한다.

  ```
  ## 설계서 첫 줄
  > 설계 확정 · 2026-09-13 14:20 · 사람 승인 (기획 포함)     ← 기획이 AI 자동 확정이었을 때
  > 설계 확정 · 2026-09-13 14:20 · 사람 승인                 ← 기획이 사람 합의였을 때

  ## 기획서 도장 아래 (기획이 AI 자동 확정이었을 때만)
  > 기획 확인 · 2026-09-13 14:20 · 사람 승인 (/gs:design ⑥)
  ```

- `보류` → 페이지만 저장하고 끝낸다. 무엇이 남았는지 한 줄로 보고한다.

**AI는 기술적으로 자기 도장을 찍을 수 있다.** 규칙으로 막는다 — `AskUserQuestion` 승인 응답 없이는 찍지 않는다. 이 스킬의 다른 모든 질문을 없앤 대가로, **이 하나만은 절대 자동화하지 않는다.**

## 마지막 출력

네 줄. 그 이상 쓰지 않는다.

```
설계서: <페이지 URL>  ·  디자인 있음/해당 없음  ·  다이어그램 n개
인터뷰: AI가 정한 n건(높음 n·중간 n) · 조사로 답한 n건 · 낮음 n건
논의 필요: n건        ← 남아 있어도 설계 설명에 드러내 함께 판단한다
확정: 2026-09-13 14:20 · 사람 승인  (또는 "보류 — <남은 것>")
```

## 하지 않는 것

- **`AskUserQuestion` 승인 응답 없이는 도장을 찍지 않는다.** "알아서 해"라고 해도 찍지 않는다. AI 경로에서 사람이 개입하는 자리가 여기 하나뿐이라, 이걸 자동화하면 검토 자리가 0개가 된다.
- **⑥ 말고 다른 곳에서 `AskUserQuestion`을 부르지 않는다.** 레포 선택·디자인 시스템 문서·논의 필요는 전부 자동 결정 + 기록으로 처리하고, ⑥ 설계 설명에 녹여 한 번에 검토받는다. 사람과 같이 정하고 싶으면 그건 `/gs:discuss`의 일이다.
- ⑥에서 `AI가 정한 것` 목록을 따로 내지 않는다. 대신 되돌리는 비용 `높음`·`중간` 결정이 설계 설명 안에 빠짐없이 들어갔는지 확인한다 — 그 설명이 곧 위임의 범위다.
- 기획서·디자인·레포에 없는 동작을 설계서에 지어내지 않는다. 빈 곳은 `## 논의 필요`로.
- 확인하지 못한 `file:line`을 쓰지 않는다.
- 트리거에 해당하지 않는 다이어그램을 그리지 않는다.
- 코드를 고치지 않는다. 이 스킬은 설계까지다.
- `## TDL`·`## QA 체크리스트`·`## 루프 로그`를 채우지 않는다. `## TDL`은 `/gs:implement`, 나머지는 implement-loop 몫이다.

## 왜 이렇게 나눴나

- **디자인을 설계 안의 한 단계로 접은 이유** — 회사는 디자인(피그마)이 기획과 함께 도착하지만, 개인은 디자인도 만들어야 한다. 별도 스킬로 빼면 확정 도장이 세 개가 되고 사람이 지친다. 기획(idea)과 구현 사이의 "재료 만들기"는 design 하나로 묶고, 도장은 기획·설계 둘만 받는다.
- **designer를 별도 에이전트로 두는 이유** — 설계 컨텍스트가 디자인까지 하면 "구현하기 쉬운 화면"으로 휜다. planner와 같은 논리다.
- **변경 지점에 FE/BE 태그를 붙이는 이유** — 개인 프로젝트는 한 작업이 프론트와 백엔드에 걸친다. 구현 단계에서 누가(frontend-dev/backend-dev) 맡을지를 설계서가 정해두지 않으면, `/gs:implement`가 임의로 가르게 되고 그 갈림이 곧 설계 판단이다.
- **다이어그램을 조건부로 둔 이유** — 다이어그램이 있다는 사실 자체가 "이건 복잡한 작업"이라는 신호여야 값이 있다.
- **⑤를 ⑥ 앞에 둔 이유** — 미결 항목을 추천안으로 다 채운 뒤에 물어야, 사람이 "무엇을 승인하는지"가 확정된 상태가 된다. 예전에는 미해소 0건을 도장의 조건으로 뒀지만, 지금은 검토 자리가 여기 하나뿐이라 멈추면 사람이 볼 기회가 사라진다. 대신 미해소를 설계 설명에 **드러내** 그것까지 포함해 승인하게 했다.
- **⑥을 결정 목록이 아니라 설계 설명으로 둔 이유** — `채택: <값>`이 줄지어 있으면 사람은 결정 하나하나의 옳고 그름만 보게 되고, 그것들이 모여 어떤 설계가 됐는지는 머릿속에서 다시 조립해야 한다. 승인하는 대상은 설계이므로 설계를 설명하고, 결정은 설계 안의 자리에서 이유와 함께 읽히게 했다.
- **다른 질문을 다 없애고 ⑥만 남긴 이유** — 질문이 여러 층에 흩어져 있으면 각각은 가벼워도 합치면 사람이 같은 작업에 대여섯 번 불려 나온다. 개인 프로젝트에서 그 왕복이 완성까지의 속도를 가장 크게 깎았다. 판단의 총량을 줄인 게 아니라 **한 곳에 모은 것**이고, 그래서 이 카드는 무겁다. 무거운 게 맞다 — 그 뒤로 PR까지 아무도 안 묻는다.
