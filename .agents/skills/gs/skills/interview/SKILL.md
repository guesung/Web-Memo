# /gs:interview — 물을 것과 묻지 않을 것을 가른다

이 스킬은 **질문을 만드는 스킬이 아니라 질문을 걸러내는 스킬**이다.

"모호하면 물어본다"를 그대로 구현하면 AI는 게을러진다. 레포를 5분만 읽으면 나오는 답을 사람에게 떠넘기고,
나중에 바꿔도 한 줄인 네이밍을 카드 UI로 물어 사람을 지치게 한다. 질문이 많을수록 좋은 인터뷰가 아니다.
**사람만 답할 수 있고, 틀리면 비싼 것만** 남기는 것이 이 스킬의 일이다.

```
§0 입력 판정
 ①  근거 수집      확인 가능한 것은 여기서 내가 답한다 (질문 아님)
 ②  후보 추출      두 관문 통과분만 · 되돌리는 비용 순 정렬
 ③  배치 확인   ★ "n건 나왔습니다. 어디까지 물을까요?"     — --auto 면 건너뛴다
 ④  한 번에 해소 ★ 고른 만큼만. AskUserQuestion 한 호출에 최대 4건 — --auto 면 건너뛴다
 ⑤  반환         확정 결정 목록 + 미해소 목록
```

**③이 ④ 앞에 있다.** 예산을 사람이 먼저 정해야, 답하다 지쳐 아무거나 고르는 일이 없다.

**`--auto`면 ③·④가 통째로 빠진다.** 후보를 뽑는 데까지(①·②)는 똑같이 하고, 묻는 대신 ②에서 만든 추천을 그대로 채택해 ⑤로 낸다 — [autonomy.md](../../autonomy.md#자동-결정--묻지-않는-대신-남긴다)의 자동 결정 규약이다. 파이프라인(`/gs:idea` ②·`/gs:design` ⑤)은 항상 이 모드로 부른다.

## 호출 규약

두 가지 방식으로 불린다. 어느 쪽이든 **이 스킬은 결정을 반환할 뿐 아무것도 고치지 않는다.**

| 호출 | 입력 | 묻는가 | 출력 |
|---|---|---|---|
| 파이프라인이 호출 | 맥락 + `--items <후보 목록>` + `--auto` | **아니오** | 추천안으로 전부 확정해 **반환만** 한다. 기록은 호출자 몫 |
| 다른 스킬이 호출 | 맥락 + `--items <후보 목록>` | 예 | 확정 결정 목록을 **반환만** 한다. 기록은 호출자 몫 |
| 사람이 단독 호출 | 맥락(문장·URL·파일 경로) | 예 | 대화로 출력. `--page`가 있으면 그 페이지에도 기록 |

**사람이 직접 부른 인터뷰를 `--auto`로 만들지 않는다.** 묻는 것이 이 스킬의 존재 이유이고, 자율 모드에서 유일하게 남은 "직접 물어보게 하는 탈출구"다.

`--items`가 주어지면 ②의 후보 추출을 건너뛰고 **받은 목록에 두 관문만 적용**한다. 호출자가 이미 찾아낸 것을 다시 찾지 않는다.

## §0. 입력 판정

1. **맥락 확보.** 인자를 순서대로 해석한다.
   - `notion.com/…` → `API-retrieve-page-markdown`으로 페이지를 읽는다(`notion-home` MCP). 이것이 맥락이다.
   - 파일 경로 → 읽는다.
   - 그 외 텍스트 → 그 자체가 맥락이다.
   - **인자가 없으면 지금까지의 대화를 맥락으로 삼는다.** 대화도 비어 있으면 멈추고 무엇에 대해 인터뷰할지 요구한다.
2. **레포 판정.** `--repo`가 있으면 그것. 없고 맥락에서 레포가 특정되면 그것. 없으면 없는 채로 진행한다(①의 조사 범위만 줄어든다).

## ① 근거 수집 — 묻기 전에 내가 먼저 답한다

②로 가기 전에 **답이 이미 존재하는지** 찾는다. 이 단계를 건너뛴 인터뷰는 사람에게 일을 떠넘기는 것이다.

찾는 순서:

1. **맥락 자체** — 기획서·설계서·대화에 이미 답이 적혀 있는가
2. **레포** — 기존 코드·설정·의존성이 이미 그 결정을 내려두었는가 (`Explore` 에이전트를 띄운다)
3. **프로젝트 문서** — `<레포>/docs/project-identity.md`, `docs/architecture.md`, `CLAUDE.md`
4. **공식 문서** — 라이브러리·SDK의 권장 방식이 사실상 정답인가

여기서 답이 나온 항목은 **질문이 아니다.** ⑤의 `조사로 답한 것`에 근거와 함께 적어 사람이 검증할 수 있게 남긴다.

레포에 이미 답이 있는데도 물으면, 사람은 자기 코드가 이미 정한 것을 다시 정하게 된다.

## ② 후보 추출 — 두 관문

남은 것에 관문 둘을 차례로 건다. **둘 다 통과해야 질문이 된다.**

### 관문 1 — 사람만 답할 수 있는가

①에서 답이 나오지 않았고, 더 조사해도 나오지 않는다. 즉 **취향·우선순위·외부 사정**에 달린 것이다.

| 통과 | 탈락 |
|---|---|
| "로그인을 넣을 것인가" (사람의 범위 판단) | "이 프로젝트가 쓰는 상태 관리 라이브러리" (레포에 있다) |
| "무료/유료 경계를 어디에 둘 것인가" | "Next.js App Router에서 서버 컴포넌트 기본값" (문서에 있다) |
| "이 화면을 MVP에 넣을 것인가" | "기존 버튼 컴포넌트 경로" (찾으면 된다) |

### 관문 2 — 되돌리는 비용이 있는가

| 등급 | 뜻 | 처리 |
|---|---|---|
| **높음** | 나중에 바꾸면 이미 쓴 코드를 버린다 — 스택 · 데이터 모델 · 인증 방식 · 모듈 경계 · 외부 서비스 | 묻는다 |
| **중간** | 여러 파일을 고쳐야 한다 — 라우팅 구조 · API 계약 · 상태를 두는 위치 · 화면 분할 | 묻는다 |
| **낮음** | 한 곳만 고치면 끝난다 — 네이밍 · 문구 · 여백 · 기본값 · 정렬 순서 | **묻지 않는다.** 정하고 ⑤에 알린다 |

**낮음은 질문 목록에 올리지 않는다.** 사람의 주의는 유한하고, 낮음 항목이 목록에 섞이는 순간 높음 항목의 무게가 같이 내려간다.

### 항목 형식

통과한 것은 셋을 갖춰야 한다. **하나라도 못 채우면 ①로 돌아가 더 조사한다.**

```
무엇이 불명확한가 → 어떤 선택지가 있는가 → 내가 추천하는 쪽과 그 이유
```

**추천이 없는 질문은 내지 않는다.** "어떻게 할까요?"는 인터뷰가 아니라 반품이다.
추천을 못 만들겠으면 근거가 부족한 것이고, 그건 ①이 덜 된 것이다.

## ③ 배치 확인 — 예산을 사람이 정한다 (`--auto`면 건너뛴다)

`--auto`면 이 단계와 ④를 건너뛰고 바로 §`--auto` 확정으로 간다.

후보를 **되돌리는 비용 순**으로 정렬해 한 번에 보여주고, 어디까지 물을지 `AskUserQuestion`으로 확인받는다.

```
결정이 필요한 지점 5건 (되돌리는 비용 순)

  1. [높음] 데이터 저장소 — 로컬 파일 vs SQLite vs 외부 DB
  2. [높음] 인증 범위 — 없음 vs 소셜 로그인만 vs 이메일+소셜
  3. [중간] 라우팅 구조 — 단일 페이지 vs 3개 라우트
  4. [중간] 목록 갱신 방식 — 폴링 vs 수동 새로고침
  5. [중간] 에러 표시 위치 — 토스트 vs 인라인

조사로 이미 답한 것 3건 (⑤에 근거 있음)
```

선택지는 **비용 경계에서 끊는다** — 임의의 숫자가 아니라 등급이 갈리는 지점이다.

| 선택지 | 뜻 |
|---|---|
| `높음만 (n건)` | 되돌리기 비싼 것만. 중간은 내가 추천안으로 진행하고 ⑤에 적는다 |
| `전부 (n건)` | 목록 전체 |
| `지금은 말고` | 묻지 않고 목록만 ⑤로 반환한다 |

`높음`이 0건이면 그 선택지는 내지 않는다. 없는 선택지를 내면 사람이 목록을 다시 읽어야 한다.

## ④ 한 번에 해소 (`--auto`면 건너뛴다)

고른 범위를 **`AskUserQuestion` 한 호출에 묶어** 묻는다. 한 호출에 최대 4건이 들어가므로, 5건 이상이면 되돌리는 비용이 높은 것부터 4건씩 나눠 연속 호출한다.

- ②에서 만든 **추천을 첫 옵션**으로 내고 이유를 `description`에 적는다.
- **전제가 서로 물리는 항목은 같은 배치에 넣지 않는다.** "외부 DB를 쓸 것인가"의 답이 "마이그레이션 도구를 무엇으로 할 것인가"라는 질문 자체를 없앨 수 있다. 상위 결정을 앞 배치에 두고, 답을 받은 뒤 남은 목록을 다시 정렬한다 — 이미 사라진 질문에 사람이 답하게 하지 않는다.
- 한 배치의 답을 받으면 확정 목록으로 옮기고 그 항목들을 지운다.
- 사용자가 "나중에"를 고르거나 비워 둔 항목은 거기서 멈춘다. 남은 것은 미해소로 ⑤에 넘긴다.
- **답하지 않은 항목을 가정으로 채우지 않는다.** 이 스킬이 존재하는 이유가 그 가정을 막는 것이다.

`--items`로 받은 항목을 물을 때는 **호출자가 준 문장을 다듬지 않고 그대로** 낸다. 중간에서 고쳐 쓰면 어디까지가 호출자의 판단인지 사람이 알 수 없다.

## `--auto` 확정 — 묻지 않고 정한다

`--auto`면 ②를 통과한 후보 전부를 **②에서 만든 추천대로 채택한다.** 등급별로 다르게 굴지 않는다 — `높음`이라고 멈추면 자율 모드가 성립하지 않는다. 대신 **등급이 그대로 보고에 실려 사람이 사후에 되돌릴 순서를 정한다.**

- 추천을 만들지 못한 항목은 채택하지 않는다. 그건 ①이 덜 된 것이므로 **①로 돌아가 더 조사한다.** 그래도 안 나오면 가장 보수적인 선택지(되돌리는 비용이 작은 쪽 · 기존 동작을 덜 바꾸는 쪽 · 범위를 덜 넓히는 쪽)를 고르고 근거에 `조사 실패 — 보수적 선택`이라 적는다.
- 전제가 서로 물리는 항목은 **상위 결정을 먼저 채택하고** 남은 목록을 다시 정렬한다. 상위 결정으로 사라진 질문은 확정 목록에 넣지 않는다.
- `미해소`는 비운다. 묻지 않았으므로 답을 못 받은 항목이라는 개념이 없다.

## ⑤ 반환

아래 형식 그대로 낸다. 호출자는 이 블록을 파싱해 자기 문서에 반영한다.

```
## 확정된 결정
| 항목 | 결정 | 근거 | 등급 |
|---|---|---|---|
| 데이터 저장소 | SQLite | 사람 응답 2026-09-02 14:20 | 높음 |

## 조사로 답한 것
| 항목 | 답 | 출처 |
|---|---|---|
| 상태 관리 | zustand | package.json:24 · 기존 store/ 6개 파일 |

## AI가 정한 것 (높음/중간)          ← `--auto`일 때만. 아니면 "해당 없음"
| 항목 | 채택 | 다른 선택지 | 근거 | 되돌리는 비용 |
|---|---|---|---|---|
| 데이터 저장소 | SQLite | 로컬 파일 / 외부 DB | 단일 사용자 · 마이그레이션 비용 최소 | 높음 |

## 내가 정한 것 (낮음)
| 항목 | 정한 값 | 바꾸는 비용 |
|---|---|---|
| 목록 빈 상태 문구 | "아직 항목이 없습니다" | 한 줄 |

## 미해소
| 항목 | 선택지 | 추천 | 왜 안 물었나 |
|---|---|---|---|
| 에러 표시 위치 | 토스트 / 인라인 | 인라인 | 사람이 "높음만" 선택 |
```

**빈 섹션은 제목만 남기고 `없음`을 적는다.** 섹션이 통째로 사라지면 안 한 것인지 없는 것인지 구별되지 않는다.

`--auto`에서는 `확정된 결정`(사람 응답)이 항상 비고, 대신 `AI가 정한 것 (높음/중간)`이 찬다. 호출자는 이 표를 `## 논의 필요`에 기록하고, `/gs:design` ⑥ **설계 설명 안에 녹여** 사람이 설계와 함께 검토하게 한다.

### 기록 — 조건부

- **다른 스킬이 호출** → 반환만 한다. 노션에 쓰지 않는다. 기록은 호출자 몫이다.
- **단독 호출 + `--page` 없음** → 대화 출력으로 끝낸다.
- **단독 호출 + `--page` 있음** → 페이지의 `## 논의 필요`에 위 네 표를 쓴다(섹션이 없으면 만든다).
  `## 기획서`·`## 설계서` 같은 **본문 섹션은 고치지 않는다.** 반영은 해당 스킬과 사람의 권한이다.

## 하지 않는 것

- **코드·문서를 고치지 않는다.** 결정을 반환할 뿐이다. 반영은 호출자 몫이다.
- 조사하면 알 수 있는 것을 묻지 않는다. ①을 건너뛴 질문은 일을 떠넘기는 것이다.
- 되돌리는 비용이 낮은 것을 묻지 않는다. 정하고 ⑤에 알린다.
- 추천 없는 질문을 내지 않는다.
- 해소를 한 건씩 쪼개 묻지 않는다. ③에서 이미 목록 전체를 보여줬으므로, 같은 내용을 n번의 왕복으로 다시 펴는 셈이다.
- ③의 배치 확인 없이 곧바로 캐묻기 시작하지 않는다.
- 답을 못 받은 항목을 가정으로 채우지 않는다. 미해소로 남긴다.
- 확정 도장을 찍지 않는다. 승인은 `/gs:design` ⑥과 `/gs:discuss` 확정의 권한이다.
- `--auto`에서 추천 없이 아무거나 채택하지 않는다. 추천이 없으면 ①로 돌아간다.
- `--auto`에서 채택한 것을 기록 없이 넘기지 않는다. `AI가 정한 것` 표가 빠지면 그건 자율이 아니라 은폐다.

## 왜 이렇게 나눴나

- **별도 스킬로 뺀 이유** — `idea` ②와 `design` ⑤가 같은 일(묻기)을 각자 구현하고 있었다. 규칙이 세 곳에 흩어지면 "추천을 첫 옵션으로" 같은 규칙 하나를 고칠 때 세 곳을 고쳐야 하고, 한 곳은 반드시 빠진다. 질문 규칙은 한 군데에만 있어야 한다.
- **두 관문을 둔 이유** — "물어보는 AI"의 실패 모드는 두 방향이다. 조사하면 나올 것을 물어 게을러지거나, 사소한 것까지 물어 사람을 지치게 한다. 관문 1이 앞을, 관문 2가 뒤를 막는다.
- **④를 한 번에 묻게 한 이유** — ③에서 사람은 이미 목록 전체를 보고 예산을 정했다. 그 뒤에 한 건씩 끊어 물으면 같은 내용을 여러 번의 왕복으로 다시 펴는 셈이고, 답하는 쪽은 전체 그림을 잃은 채 카드 하나만 본다. 한 화면에 모아 두면 서로 맞물린 결정을 함께 놓고 고를 수 있다. 전제가 물리는 항목에서만 배치를 끊는다.
- **③ 배치 확인을 넣은 이유** — 질문 예산은 작업 크기에 따라 다르다. 고정 상한은 짧은 작업에 과하고 긴 작업에 모자란다. 사람이 목록 전체를 **먼저 보고** 정하면, 몇 건을 포기하는지 알고 포기하게 된다.
- **아무것도 고치지 않게 한 이유** — 반영까지 하면 호출자(`design`)와 권한이 겹치고, 같은 문서를 둘이 쓰게 된다. 순수해야 `idea`·`design`·단독 어디서든 같은 규칙으로 돌아간다.
- **`--auto`를 등급 무시로 만든 이유** — "높음만 사람에게 묻는다"를 남기면 파이프라인이 결국 매번 멈춘다. 되돌리는 비용이 큰 결정은 사라지지 않기 때문이다. 대신 등급을 **보고에 실어** 사람이 설계 설명과 최종 보고에서 한 번에 훑게 했다. 판단 시점을 건건이가 아니라 한 곳으로 옮긴 것이지, 판단을 없앤 것이 아니다.
- **`조사로 답한 것`을 출력에 남기는 이유** — 안 물어본 것이 판단인지 누락인지 사람이 구별할 수 있어야 한다. 근거가 틀렸으면 여기서 잡힌다.
