# /gs:problem-log — 해결한 문제를 일지에 남긴다

**기록하기 전에 반드시 사람의 승인을 받는다.** 초안을 보여주고 답을 들은 뒤에만 노션에 쓴다.

**호출은 사용자가 시키지 않아도 한다.** ①의 판단 기준에 걸리는 일이 대화 중에 있었으면, 요청을 기다리지 않고 초안을 만들어 ②로 간다. 단, **[작업 스킬](#작업-스킬-끝의-점검)이 도는 중이면 스스로 부르지 않는다** — 그 스킬이 마지막 출력 뒤에 점검하고, 그때 모아서 묻는다. 기록할 게 없다고 판단했으면 아무 말도 하지 않는다 — "기록할 게 없습니다"를 매번 말하면 그게 소음이 된다(작업 스킬 끝의 점검만 예외다).

**호출과 승인은 다른 문제다.** 호출은 사람이 잊어도 되게 자동으로, 기록은 사람이 확인한 것만. 자동으로 하는 것은 *물어보러 오는 일*이지 *쓰는 일*이 아니다.

## 작업 스킬 끝의 점검

아래 스킬은 마지막 출력을 낸 **뒤에** 이 스킬의 ① 판단 기준으로 **반드시** 점검한다. 작업을 막 끝낸 사람은 다음 작업으로 넘어가지 일지를 떠올리지 않는다 — 스킬이 끝에서 대신 떠올린다. 이 표가 SSOT이고, 각 스킬은 자기 파일에서 여기를 가리키기만 한다.

| 스킬 | 점검하는 때 | 건너뛰는 때 |
| --- | --- | --- |
| `/gs:implement-loop` | ④ (마지막 출력 뒤) | — |
| `/gs:implement` | 단독 호출의 마지막 출력 뒤 | `--from-loop` — loop ④가 한다 |
| `/gs:issue-solve` | ③에서 이어 도는 `/gs:implement`가 한다 | `--diagnose-only` — 아직 뚫은 게 아니다 |
| `/gs:self-qa` | 모드 인자 없이 사람이 직접 부른 때 | `--checklist-only`·`--run` — loop가 부른다 |

- 점검 범위는 **그 스킬이 도는 동안 일어난 일 전부**다. 하위 에이전트(`gs:backend-dev`·`gs:frontend-dev`·`gs:qa-verifier`)가 반환한 막힌 지점·재시도·빌드 실패도 포함한다.
- 후보가 있으면 `--work-card <페이지 URL>`(작업카드가 있을 때)을 붙여 ②로 간다. 승인 규칙은 그대로다 — 한 건씩, 전문으로.
- 후보가 없으면 `문제 해결 기록: 없음` 한 줄을 출력한다. 대화 중 스스로 호출할 때와 달리 여기서는 점검했다는 흔적을 남긴다 — 점검을 빠뜨렸는지 사람이 볼 수 있어야 한다.
- cashwalk 레포 작업(`/common:local-setup` 등)은 `/nudge:problem-log`의 같은 규칙을 따른다.

## 저장소 — 노션 "개발 위키 DB" (guesung, `notion-home` MCP)

**시작 전에 [notion-databases.md](../../notion-databases.md#개발-위키-db--문제-해결-기록)를 읽는다.** data source ID · 속성별 채우는 규칙 · `유형` 선택지 8개 · `프로젝트` 판정 · 본문 형식이 거기 있다.

이 DB는 블로그 `/wiki`가 렌더하는 공개 위키와 같다. **`상태`는 항상 `작성 완료`로 쓰고, `공개` 체크박스는 켜지 않는다.** 블로그에 노출되는 조건은 노션 쪽 설정이라 스킬이 정하지 않는다 — 그래도 ②의 승인은 "이 내용이 공개돼도 된다"는 승인으로 받는다.

**쓰거나 조회하기 전에 `API-retrieve-a-data-source`로 속성 이름과 `유형`·`프로젝트`·`상태` 옵션을 실제 DB와 한 번 대조한다.** 이 DB는 사람이 노션에서 구조를 바꾸므로 카탈로그가 낡을 수 있다(2026-09-20에 `카테고리`·`Project`·`Status`가 이미 없어져 조회가 `validation_error`로 실패했다). 카탈로그와 다르면 **실제 DB를 따르고**, ②의 초안 아래에 어긋난 점을 한 줄로 알린 뒤 기록이 끝나면 `notion-databases.md`를 고친다.

이 스킬이 그 위에 얹는 규칙은 둘이다.

- `--work-card`를 받았으면 `프로젝트`는 그 업무 로그 페이지의 `프로젝트` 값을 **그대로 따른다.** 레포 경로로 다시 판정하지 않는다 — 같은 작업의 두 기록이 다른 프로젝트로 갈리면 안 된다.
- `유형`은 **제안**만 하고 ②의 승인 때 함께 확인받는다. 혼자 확정하지 않는다.

`--work-card`를 받았으면 **[orca-worktree.md](../../orca-worktree.md)의 절차대로 현재 워크스페이스 메모에 그 URL을 기록한다.** 실패해도 멈추지 않는다.

## ① 초안

---

무엇을 남길지 고른다. 판단 기준은 **"다음에 같은 걸 만나면 이 기록을 찾아볼 것인가"**.

| 남긴다                        | 남기지 않는다                   |
| ----------------------------- | ------------------------------- |
| 원인을 찾는 데 시간이 걸린 것 | 오타·문법 오류처럼 즉시 보인 것 |
| 처음에 세운 가설이 틀렸던 것  | 설계대로 순조롭게 짠 것         |
| 우회만 하고 원인을 못 밝힌 것 | 이미 일지에 같은 항목이 있는 것 |

세 칸을 채운다. **원인 칸에는 확인한 것만 쓴다** — 근거 없이 그럴듯한 설명을 넣으면 그 기록이 나중에 사람을 잘못된 방향으로 보낸다. 확인하지 못했으면 `미확인 — 우회함`이 정답이다.

`Tags`도 여기서 제안한다. 본문·상황·원인을 보고 [notion-databases.md](../../notion-databases.md#개발-위키-db--문제-해결-기록)의 기존 옵션 중에서만 고른다 — 새 옵션은 만들지 않는다.

중복 확인: `API-query-data-source`로 `유형`이 `트러블 슈팅`·`설계 판단`인 행을 `작성일` 내림차순 20개 받아 `Name`을 훑어 같은 증상이 있는지 본다. 있으면 새 행 대신 그 행을 갱신할지 ②에서 함께 묻는다.

## ② 승인 — 여기서 멈춘다

초안 **전문**을 사용자에게 보여준다. 요약하지 않는다. 사람이 읽고 고칠 수 있어야 승인이 의미가 있다.

```
제목     : <이름>
유형     : <제안> (트러블 슈팅 / 설계 판단 / 트레이드 오프 고민 / 고민 / 개발 기록 / 깊이 있는 학습 / 공식 문서 번역 / 환경 기록)
프로젝트 : <옵션 | (비움)>
Tags     : <제안 — 기존 옵션 중에서>
상태     : 작성 완료
공개     : 체크 안 함 (스킬은 공개를 켜지 않는다)
작성일   : <오늘>
메모     : <작업카드 mention · PR 링크>

상황 : <…>
원인 : <…>
해결 방법 : <…>
```

그리고 `AskUserQuestion`으로 묻는다.

| 답          | 하는 것                                      |
| ----------- | -------------------------------------------- |
| 그대로 기록 | ③으로                                        |
| 고쳐서 기록 | 무엇을 고칠지 듣고 초안을 고친 뒤 **다시 ②** |
| 기록 안 함  | 아무것도 쓰지 않고 끝낸다                    |

여러 건이면 **한 건씩** 묻는다. 한꺼번에 던지면 사람이 대충 넘기고, 그러면 승인 단계가 형식이 된다.

## ③ 기록

1. `API-post-page`로 개발 위키 DB의 data source에 행을 만든다. 속성은 카탈로그 표대로 — `상태: 작성 완료`, `AI 작성: true` 포함, `공개`는 건드리지 않는다. `요약`에는 ②에서 승인받은 `상황`·`원인`·`트레이드 오프 / 해결 과정`(있을 때만)·`해결 방법`을 레이블만 붙여 그대로 이어붙인다(원문을 다시 쓰거나 요약하지 않는다). rich_text 한 조각이 2000자를 넘으면 실패하므로 레이블(볼드)·본문·식별자(인라인 코드)를 조각으로 나눠 넣는다. `Tags`는 ②에서 승인받은 값 그대로 넣는다.
2. `API-update-page-markdown`의 `replace_content`로 같은 내용을 본문 섹션(`### 상황` · `### 원인` · `### 해결 과정` · `### 해결 방법` · `### 메모`)으로 넣는다. 빈 섹션은 만들지 않는다.

`--work-card`를 받았으면 `메모`에 그 페이지 mention을 넣는다.

마지막 출력은 한 줄: `일지: <제목> — <행 URL>`.

## 정지 조건

|     | 조건                                     | 남기는 것                                                |
| --- | ---------------------------------------- | -------------------------------------------------------- |
| A   | 사용자가 답하지 않음                     | 초안을 그대로 출력하고 끝낸다. **승인 없이 쓰지 않는다** |
| B   | 노션 접근 실패 (개인 DB는 `notion-home`) | 초안 전문과 에러. 사람이 손으로 옮길 수 있게             |

## 하지 않는 것

- 승인 없이 행을 만들지 않는다. 이 스킬의 존재 이유가 그 승인이다.
- `상태`를 `작성 완료` 말고 다른 값으로 쓰지 않는다. 등급을 나누는 건 사람이 노션에서 한다.
- `공개` 체크박스를 켜지 않는다. 공개는 사람이 노션에서 정한다.
- `프로젝트`·`유형`·`Tags` select에 없는 옵션을 새로 만들지 않는다. 판정이 안 서면 비운 채 두고 승인 화면에 `(비움)`으로 보여준다.
- 카탈로그에 있다고 해서 그 속성이 실제 DB에 있다고 믿지 않는다. 대조 없이 옛 이름(`카테고리`·`Project`·`Status`)으로 쓰거나 필터하지 않는다.
- 이미 있는 행과 같은 증상이면 새 행 대신 갱신을 제안한다.

## 왜 이렇게 나눴나

- **승인을 강제하는 이유** — 일지는 사람이 나중에 자기 언어로 검색할 것이다. AI가 정리한 문장은 그럴듯하지만 사람의 기억과 어긋난 단어를 쓰기 쉽다. ②에서 한 번 손대게 하면 그 어긋남이 사라진다.
- **작업 스킬 끝에 점검을 박은 이유** — "요청하지 않아도 스스로 호출한다"는 규칙만으로는 부족했다. 스킬 절차에 없는 단계는 흐름 중에 빠진다 — 실제로 implement-loop 밖의 작업에서는 한 번도 불리지 않았다. 절차의 마지막 단계로 적어야 매번 돈다.
- **호출은 자동, 기록은 승인으로 나눈 이유** — 이 둘을 묶어 생각하기 쉽지만 비용이 다르다. **호출을 사람에게 맡기면 그냥 잊힌다** — 문제를 막 뚫은 사람은 다음 작업으로 넘어가지 일지를 떠올리지 않는다. 반면 **기록을 자동으로 하면 틀린 원인이 조용히 쌓인다.** 그래서 AI가 물어보러 오는 것은 자동으로, 노션에 쓰는 것은 사람의 확인으로 나눴다.
- **`원인`에 `미확인 — 우회함`을 허용하는 이유** — 빈칸으로 두면 "안 적었나 보다"가 되고, 추측을 적으면 거짓이 된다. 못 밝혔다는 사실 자체가 정보다. 나중에 같은 증상이 재발하면 그 칸이 바로 단서가 된다.
- **쓰기 전에 스키마를 대조하는 이유** — 이 DB는 사람이 노션에서 속성을 바꾼다. 카탈로그를 믿고 옛 이름으로 요청하면 조회가 400으로 죽고, 더 나쁘게는 이름이 우연히 남아 있는 칸에 엉뚱한 값이 쓰인다. 한 번의 조회로 확인할 수 있는 사실을 문서 기억에 맡기지 않는다.
- **DB 한 곳에 모으는 이유** — "자주 막히는 유형"을 세려면 한 곳에 있어야 한다. 작업 페이지마다 흩어지면 셀 수 없다.
