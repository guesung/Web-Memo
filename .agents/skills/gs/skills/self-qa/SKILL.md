# /gs:self-qa — QA 명세 작성 → 자동 판정 → 수동 안내

"전부 자동화"가 목표가 아니다. **자동으로 판정할 수 있는 것과 없는 것의 경계를 명시적으로 남기는 것**이 목표다.
"자동화 못 하니 검증 안 함"이 되는 항목이 하나도 없어야 한다.

명세는 `qa-checklist`, 판정은 `qa-verifier` 에이전트가 별도 컨텍스트에서 한다. 이 스킬은 **입력을 넘기고, 반환을 DB에 기록하는 오케스트레이터**다.

## 저장소 — 노션 "QA 항목" DB (guesung, `notion-home` MCP)

**시작 전에 [notion-databases.md](../../notion-databases.md#qa-항목)를 읽는다.** 식별자와 12개 속성의 채우는 규칙이 거기 있다. **에이전트는 노션에 접근하지 않는다** — DB 읽기·쓰기는 전부 이 스킬이 한다.

**본문은 `# AI 작성` 아래만 고친다.** `# 인간 작성` 아래는 읽기만 하고, 섹션도 그 H1 아래에서 찾는다 — [AI 작성 경계](../../notion-databases.md#ai-작성-경계).

행 하나 = QA 항목 하나. 모든 작업의 항목이 이 DB 한 곳에 쌓이고 `작업` relation으로 구분된다. 작업별 페이지를 따로 만들지 않는다 — "수동 비율"·"FAIL 잦은 유형"을 세려면 한 곳에 있어야 한다.

로컬 설계서 파일로 호출됐을 때(개발·검증용)는 DB 대신 설계서 파일 하단 `## QA 체크리스트`에 같은 컬럼의 표로 쓴다.

## 모드

| 인자 | 하는 것 | 호출처 |
|---|---|---|
| `--checklist-only` | ① 명세 위임 → ④ DB에 행 생성 (`상태`=미실행) | implement-loop §0-5 |
| `--run` | DB에서 이 작업의 행을 읽어 ② 판정 위임 → ④ 갱신 | implement-loop ② |
| 없음 | 전부 | 사람이 직접 |

인자로 개인 업무 로그 페이지 URL을 받았으면, 모드와 무관하게 **시작 전에 [orca-worktree.md](../../orca-worktree.md)의 절차대로 현재 워크스페이스 메모에 그 URL을 기록한다.** 실패해도 멈추지 않는다. 로컬 설계서 파일로 호출됐을 때는 건너뛴다.

## ① 명세 작성 — Agent: `gs:qa-checklist`

`Agent` 도구로 `gs:qa-checklist`를 띄운다. 프롬프트에는 **개인 페이지의 `## 설계서`(동작 명세·변경 범위·범위 밖)와, 있으면 `## 디자인`만** 넣는다. 대화 이력·코드는 넣지 않는다 — 명세가 구현에 맞춰 왜곡되는 것을 막는 경계다.

항목 규칙(명세 줄당 ≥1 · 경계 4종 필수 · 관측 가능 문장 · TBD 금지 · 자동/수동 판정 기준)은 [에이전트 문서](../../agents/qa-checklist.md)에 있다.

- 반환된 `QA 체크리스트 초안`을 **다듬지 않고** ④로 보낸다 — 메인이 손대면 어디까지가 에이전트 판단인지 알 수 없다.
- `논의 필요 후보`가 있으면 항목으로 만들지 않고 implement-loop가 `## 논의 필요`로 보내게 한다.

## ② 판정 — Agent: `gs:qa-verifier`

`Agent` 도구로 `gs:qa-verifier`를 띄운다. 프롬프트에는 **이 작업의 QA 항목 전부(ID·항목·전제·판정 기준·유형)와 앱 실행 방법(진입 URL 또는 dev 서버 명령·라우트), viewport(web/webview)**를 넣는다.

**실행 방법은 `<레포>/docs/architecture.md`의 `## QA 실행` 섹션에서 가져온다.** 이번 작업에만 해당하는 진입 경로가 따로 있으면 그것만 덧붙인다. 섹션이 없으면 프롬프트에 실행 방법을 비워 보내지 말고, **레포에서 직접 찾아 채운다** — `package.json`의 `dev` 스크립트, 프레임워크 기본 포트, 라우트 파일에서 진입 경로. 사람에게 묻지 않는다([autonomy.md](../../autonomy.md)). 로그인이 필요한 화면이면 `aside-browser` 스킬로 사용자의 로그인 세션을 그대로 쓴다. 그래도 못 찾으면 해당 항목만 `관측 불가 — 실행 방법 미확인`으로 두고 나머지를 판정한다. **테스트 계정 값을 프롬프트에 넣지 않는다.** env 키 이름까지만 넘기고 값은 에이전트가 로컬에서 읽는다.

- 자동 항목은 브라우저 관측으로 PASS/FAIL + 증거, 수동 항목은 재현 방법 4줄 — 형식은 [에이전트 문서](../../agents/qa-verifier.md)에 있다.
- `관측 불가`로 돌아온 항목은 **`유형`을 수동으로 바꾸고** 수동 대기로 보낸다. 자동 판정에 실패한 항목을 PASS로 두지 않는다.
- `실행 환경 실패`로 돌아오면 멈춘다. 그건 QA 실패가 아니라 환경 문제라 implement-loop 정지 조건 D에 준한다.
- `부수 관측`(항목 밖 콘솔 에러·실패 요청)이 있으면 사람 보고에 그대로 올린다.

수동 항목의 `상태`=`수동 대기`. 사람이 확인하면 `수동 확인`으로 바꾼다 — 스킬은 이 상태를 만들지 않는다.

## ④ DB 갱신

- `--checklist-only`: 이 작업(`작업` relation)의 기존 행이 있으면 **지우지 않고** ID가 같은 행을 갱신, 새 ID만 추가한다. 이전 회차 결과를 잃지 않기 위해서다.
- `--run`: `상태`·`증거`·`회차`·`실행일`을 갱신. FAIL은 `증거`에 실패 증거를 넣는다.
- 개인 페이지 `## QA 체크리스트` 섹션에는 **DB 링크 + 요약 한 줄**만 남긴다: `PASS n · FAIL n · 수동 대기 n → <QA 항목 DB URL>`. 데이터는 DB 한 곳에만 둔다.

## 출력

사람용 표 + 기계용 JSON. implement-loop가 JSON을 읽는다.

```
| ID | 유형 | 상태 | 항목 |
|---|---|---|---|
| Q-01 | 자동 | PASS | … |
| Q-04 | 수동 | 수동 대기 | … |
```

```json
{ "pass": 5, "fail": 1, "manual": 2, "fail_items": [ { "id": "Q-03", "item": "…", "evidence": "…" } ] }
```

마지막 한 줄: `자동 n건 중 PASS n · FAIL n, 수동 n건 재현 방법 기록.` 총평 없음.

모드 인자 없이 사람이 직접 불렀으면, 출력 **뒤에** [`/gs:problem-log`의 작업 스킬 끝 점검](../problem-log/SKILL.md#작업-스킬-끝의-점검)을 **반드시** 한다(예: 브라우저 구동·셀렉터가 원인 모르게 실패하다 뚫은 것). `--checklist-only`·`--run`이면 implement-loop가 부른 것이므로 하지 않는다.

## 하지 않는 것

- FAIL 항목을 고치지 않는다. 판정까지가 책임이다. 수정은 implement-loop ②가 한다.
- 설계서에 없는 동작을 항목으로 지어내지 않는다.
- 수동 항목을 `수동 확인`으로 바꾸지 않는다. 그건 사람이 실제로 본 뒤에만.
- 에이전트 반환을 고쳐 쓰지 않는다. 반영할 수 없는 반환(형식 위반 등)이면 해당 에이전트를 다시 띄운다.

## 왜 이렇게 나눴나

- **명세와 실행을 분리** — 명세는 설계서가 확정되는 순간 나올 수 있고, 실행은 코드가 있어야 한다. 합치면 "구현 다 되고 나서 QA 항목을 생각"하게 되고, 그때는 구현에 맞춰 항목이 왜곡된다.
- **명세·판정을 각각 별도 에이전트로** — 구현 대화를 본 컨텍스트가 판정까지 하면 "이 정도면 되지"가 스며든다. 깨끗한 컨텍스트가 체크리스트 문장만 보고 브라우저와 대조해야 판정이 문장대로 나온다. 명세 쪽도 같은 이유로 코드를 안 보는 에이전트에 맡긴다.
- **애매하면 수동** — 자동 판정의 거짓 PASS가 수동의 비용보다 비싸다.
- **DB 한 곳** — 항목별 이력이 쌓여야 "이 유형은 매번 FAIL"이 보인다.
