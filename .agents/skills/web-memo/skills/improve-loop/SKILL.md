# /web-memo:improve-loop — 증거 기반 서비스 개선

Codex에서는 `$web-memo-improve-loop`로 실행한다. 선택 입력은 관심 범위(예: 메모 저장·확장 시작·웹 로딩·빌드)와 기존 업무 로그 카드 URL이다. 입력이 없으면 레포 전체에서 고른다. 스케줄러가 아닌 **현재 에이전트 세션에서 한 번 실행하는 스킬**이다.

**완료 계약:** 문제 하나 → 변경 전 증거 → 최대 3회 실험 → 독립 검증 → 일반 PR. 효과를 입증하지 못하면 **PR 없이** 중단 결과를 전달한다. 머지·운영 반영은 사람이 한다.

## 1. 시작과 격리

1. 대상 git 루트의 `AGENTS.md`, `docs/project-identity.md`, `docs/architecture.md`, 코드 컨벤션을 읽는다. 회사 레포에서는 실행하지 않는다.
2. GitHub 작업 전 `gh auth status --active --hostname github.com`을 확인한다. 활성 계정이 다르면 `gh auth switch --hostname github.com --user guesung` 후 재확인한다. 인증·원격 접근이 안 되면 실패를 보고한다. 비밀 값을 로그에 남기지 않는다.
3. `origin/master`를 fetch하고 그 SHA를 고정한다. 기존 작업 디렉터리·브랜치·미커밋 파일·stash를 건드리지 않고, 고유 run ID로 **별도 worktree와 `improve/<run-id>` 브랜치**를 고정 SHA에서 만든다. 변경 전 측정이 필요하면 같은 SHA의 detached baseline worktree도 별도로 만든다. 같은 주제의 열린 PR이 있는지 확인하고 중복이면 다른 후보를 고른다.
4. 로컬 기록은 `.omc/improve-loop/<run-id>/`에 둔다. 이는 실험 기록일 뿐 OMX 세션 상태나 권한 증명이 아니다. `report.md`에 base SHA, worktree 경로, 후보/판단, 계약, 시도 번호, 명령/종료 코드/로그 경로, 각 측정 SHA, 최종 상태를 누적한다. 다른 run을 자동 재개하지 않는다. 사용자가 특정 run의 재개를 요청하면 경로·branch·SHA·diff를 확인하고 **기존 횟수를 이어 센다**.
5. 첫 보고는 목표·범위·최대 3회·완료 조건 한 번만 알린다. 이후 일반 판단은 기록하고 진행하며, 사용자 입력을 기다리지 않는다. 단, 새로운 권한이 필요한 작업이나 파괴적 작업은 실행하지 않고 해당 후보를 제외하거나 `blocked`로 끝낸다.

## 2. 후보를 고르고 계약을 잠근다

최대 5개 후보를 코드·기존 테스트·읽기 전용 관측으로 살핀다. 기존 refactor 감사 결과가 있으면 입력으로 쓸 수 있지만 측정 없이 그대로 채택하지 않는다. **사용자 영향 × 근거의 확실성 × 검증 가능성 / 변경 위험·비용**으로 비교해 하나를 선택한다. 모든 후보와 채택/제외 근거(file:line)를 기록한다.

- 대상: 기존 기능의 지연·불필요한 작업·메모리/네트워크 낭비, 재현 가능한 오류·경쟁 상태·누수. 빌드/개발 속도도 후보지만 실제 사용자 영향과 구별해 보고한다.
- 제외: 화면 배치·문구·색·상태 표현 변경, 새 기능, 취향성 리팩토링, 의존성 추가, DB 마이그레이션, 운영 데이터 쓰기·부하 테스트, 유료 인프라/새 자격증명이 필요한 작업. 화면 변경이 필요하다는 사실이 나중에 드러나도 구현하지 않는다.
- 후보의 baseline 관측은 수정 실험 횟수에 포함하지 않는다. 선택 후 세 시도는 **같은 문제**에 쓴다. 세 번 실패했다고 새 문제로 갈아타지 않는다. 재현 가능한 후보가 없으면 `no-candidate`로 끝낸다.

**코드를 수정하기 전에** `report.md`에 실험 계약을 적고 고정한다:

| 필드 | 필수 내용 |
| --- | --- |
| 문제/불변 조건 | 관측된 불편·오류와 유지할 공개 동작/API·UI·데이터 정합성 |
| 가설/범위 | 원인 근거, 바꿀 파일과 최소 변경안 |
| 주 지표 | 단위·낮을수록/높을수록 좋음·실행 명령·데이터/환경·성공 임계값 |
| 전후 조건 | Node/pnpm 버전, lockfile, 빌드 모드, 기기, 입력 fixture, warmup/cache 정책 |
| 회귀 예산 | 영향 경로 테스트, lint/typecheck/build, 필요한 E2E, 보조 지표의 허용 회귀 |
| 중단 | 최대 3회; baseline 실패/환경 불일치/권한 부족/안전 위반 시 성공 처리 불가 |

성능은 원시 반복 측정과 변동폭을 남긴다. 임계값은 결과를 보기 **전에** 정한다. 안정성은 기존 코드에서 타깃 원인으로 실패하는 테스트/시나리오가 있어야 한다. import·설정 오류로 실패한 테스트는 재현 증거가 아니다. 단순 테스트 통과나 코드량 감소는 개선 효과가 아니다.

PR 카드도 구현 전에 준비한다. [pr 스킬](../pr/SKILL.md)의 `master 대상 PR — 작업 카드` 규칙대로 기존 카드/ID를 확인한다. 없으면 기존 [개인 업무 로그 접근 규칙](~/.agents/docs/notion-databases.md#개인-업무-로그)을 읽고 `notion-home`으로 선택 문제의 카드를 만든다(`상태` 속성은 쓰지 않는다). 기존의 검증된 카드 ID가 있으면 새 카드 생성은 필요 없다. 카드가 없고 해당 MCP도 없으면 ID를 지어내거나 다른 Notion 연결로 대체하지 말고 `blocked`로 보고한다. 카드 누락 시 PR 스킬의 질문 경로로 들어가지 않고 여기서 종료한다. 카드 원문/시크릿을 공개 증거에 복사하지 않는다.

## 3. 최대 3회 실험

각 시도는 **가설 하나의 수정 → 해당 후보 측정 → 회귀 판정**까지다. 코드 수정에 들어가면 시도 번호를 먼저 올린다. 검증 실패 후 수정도 다음 시도에 포함한다. 동일 코드에서 계약대로 반복 측정하는 것은 추가 시도가 아니지만, 유리한 샘플만 남기는 재실행은 하지 않는다.

1. 부족한 회귀 테스트부터 추가한다. 안정성 재현은 새 테스트를 baseline에도 적용해 기존 코드의 타깃 실패를 확인한다. 성능은 baseline 명령이 정상 완료되는지 확인한다.
2. 최소 변경을 구현한다. 필요하면 native `executor`에게 구현 파일 소유권과 계약만 전달한다. 다른 에이전트의 변경을 되돌리지 않도록 알린다. 실행 중 새 후보·새 기능으로 범위를 넓히지 않는다.
3. 전후 동일 harness·fixture·모드로 측정한다. 빌드 최적화라면 각 버전의 필요한 준비 빌드를 따로 수행하고 cold/warm 및 Turbo/Next cache hit 여부를 맞춘다. 캐시 삭제는 이 run의 격리 worktree 안에서만 한다. 실제 운영 데이터를 쓰지 않는다.
4. 타깃 테스트와 계약에 정한 회귀 검사를 실행한다. 실패한 검사도 명령·로그·종료 코드를 보존한다. 기준을 낮추거나 실패를 숨겨 통과시키지 않는다.
5. 효과가 없으면 원인과 다음 가설을 기록한다. run이 만든 변경만 명시적 파일/커밋 경계로 되돌린다. 기존 사용자 작업에 `reset --hard`, `clean`, 자동 stash/pop을 사용하지 않는다. 후보를 누적 개선할 경우 각 시도 diff와 SHA를 남기고 **최종 비교는 항상 최초 baseline**과 한다.

반복 시간 측정에는 [측정 도구와 증거 기준](evidence.md)을 읽고 `scripts/benchmark.mjs`를 사용할 수 있다. 도구의 `improved`는 시간 지표의 보수적인 선별 결과일 뿐, 제품 효과나 전체 QA 판정이 아니다.

## 4. 독립 검증과 PR

구현이 좋아 보여도 바로 PR을 만들지 않는다. native `verifier`에게 계약, baseline/최종 diff, 원시 로그와 실행 경로를 넘겨 **직접 검사를 재실행**하게 한다. 구현자의 결론을 정답으로 주지 않는다. 확인 대상:

- 타깃 오류가 baseline에서 실제로 실패하고 후보에서 통과하는가 / 측정 조건과 임계값을 지켰는가?
- 불변 동작·UI·데이터 경계를 보존했고, 누락된 실패·유의미한 보조 지표 회귀가 없는가?
- 최종 diff에 대해 타깃 테스트, `pnpm lint`, `pnpm type-check`, 영향 대상 build 및 필요한 E2E가 통과하는가?
- 전후 증거를 제3자가 같은 명령으로 재현할 수 있고, 공개 가능한가?

검증 에이전트가 없으면 같은 기준의 분리된 검증 패스를 수행하고 **독립 검증 아님**을 공개한다. 필요한 검사를 실행할 수 없거나 반증이 나오면 PR 성공 처리 없이 `blocked` 또는 남은 시도로 돌아간다. 검증에서 수정하면 시도를 소비하고 측정·검사를 새로 수행한다.

효과와 회귀 검증을 통과하면 공개 가능한 자료를 `docs/improvements/<run-id>/`에 복사한다. 짧은 `report.md`, 재현 harness/fixture(기존 경로 참조 가능), 원시 측정 JSON, 필수 검사 결과를 넣는다. 민감한 사용자 메모·토큰·절대 홈 경로·전체 개인 로그는 제외한다. 큰 로그는 요약/안전한 CI artifact 링크로 대신하고 원시 측정은 남긴다.

[commit](../commit/SKILL.md)과 [pr](../pr/SKILL.md)를 읽고 그 절차를 사용한다. 이번 승인에 커밋·push·PR 생성이 포함되어 있으므로 매번 진행 여부를 되묻지 않는다. 단, 레포 `AGENTS.md`가 우선이며 **base는 master**, develop은 작업 브랜치에 역머지하지 않는다. 기존 스킬의 `main` 기본값은 이 레포에서 쓰지 않는다. 필요한 develop/staging 검증은 기존 PR 절차를 따른다. **PR 자동 머지·운영 릴리스는 하지 않는다.** master 갱신/충돌 해결로 코드가 달라졌으면 baseline도 갱신하고 전후 측정과 회귀 검사를 다시 수행한다. 코드 수정은 남은 시도 안에서만 허용한다.

PR 본문은 한글로 문제·채택 이유, baseline/최종 SHA, 측정 표(단위·반복 수·변동폭·개선율), 재현 명령, 테스트 결과, 위험/한계와 증거 경로를 포함한다. 단위 테스트 성공을 사용자 지표 개선으로 표현하지 않는다. 원격 PR을 재조회해 base·head·본문·URL을 확인한 뒤 `pr-created`로 기록한다.

## 5. 종료와 결과물

| 상태 | 결과 |
| --- | --- |
| `pr-created` | 실제 PR URL, 전후 수치 또는 재현 실패→통과, 검증 요약, 위험 한 줄 |
| `no-improvement` | 최대 3회 내 효과 미입증. PR 없음, 시도별 결과와 중단 이유 |
| `no-candidate` | 검증 가능한 후보 없음. 조사한 범위와 제외 근거 |
| `blocked` | 권한·환경·필수 검증·안전 경계 문제. 확인한 오류와 남은 조건 |

실패 시 run이 만든 서비스 변경은 원래 baseline으로 되돌리되, 이 run의 증거 기록은 보존한다. 작업 경로·브랜치와 남긴 자료를 보고한다. 작업 디렉터리를 지우거나 다른 run을 중단하지 않는다. 후속 블로그/위키 기록·새 인터뷰·추가 루프를 자동으로 시작하지 않는다. 사용자가 요청한 한 번의 실행 결과만 전달한다.
