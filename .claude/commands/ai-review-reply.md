# /ai-review-reply — 두 페르소나가 내 답변에 답한다

`/ai-review`가 던진 질문에 내가 답한 스레드를 찾아, 각 봇이 **한 번만** 재답변한다.
질문 단계가 "설명하게 만드는" 단계였다면, 이 단계는 **그 설명을 남기는** 단계다.

- 이도현(인턴) 스레드 → 내 설명이 **코드 주석**으로 남는다
- 박성우(시니어) 스레드 → 내가 인정한 것이 **후속 작업 체크리스트**로 남는다

설계 근거는 [설계 문서](../../docs/superpowers/specs/2026-08-17-ai-review-personas-design.md) §6 참고.

## 인자

없다. `$ARGUMENTS`가 있어도 무시한다.

## 절차

### 1. PR 확인

```bash
gh pr view --json number,url,headRefOid --jq '{number, url, headSha: .headRefOid}'
git rev-parse HEAD
```

- PR이 없으면 중단하고 "먼저 `/pr`로 PR을 생성하세요"라고 안내한다.
- **`headRefOid`와 로컬 `HEAD`가 다르면 기억해 둔다.** 중단하지는 않는다 — 답글 자체는
  라인과 무관해서 정상 게시된다. 다만 이 경우 **suggestion 블록을 하나도 만들지 않는다**
  (5단계의 검증이 통과할 수 없다). 사용자에게 "`git push` 후 다시 실행하면 주석 제안까지
  받을 수 있다"고 알린다.

### 2. 미답변 스레드 조회

```bash
node scripts/ai-reviewer/cli.ts pending --pr <번호>
```

출력은 stdout에 JSON으로 나온다.

```json
{
	"prAuthor": "guesung",
	"threads": [
		{
			"rootId": 123456,
			"persona": "intern",
			"path": "pages/content-ui/src/ui/highlight/restoreHighlights.ts",
			"line": 65,
			"question": "**이도현** · 인턴 개발자\n\n...\n\n<!-- ai-review:intern:q1 -->",
			"authorReply": "..."
		}
	]
}
```

**`threads`가 비어 있으면 "재답변할 스레드가 없습니다"라고 안내하고 종료한다.**
`cli.ts post`를 실행하지 않는다. 비어 있는 이유는 셋 중 하나다.

- 아직 GitHub에서 답변하지 않았다
- 이미 봇이 답했다 (1턴 제한 — 아래 "주의" 참고)
- `/ai-review`를 아직 실행하지 않았다

`question` 본문 끝에는 마커가 붙어 있다. **읽을 때는 무시하고, 답글 본문에 옮겨 쓰지 않는다.**

`line`은 **`null`일 수 있다.** GitHub이 그 코멘트를 outdated로 판정했다는 뜻이며,
해당 스레드는 5단계에서 **suggestion 없이** 답글만 단다.

### 3. 코드 컨텍스트 읽기

각 스레드의 `path` 파일을 **전체** 읽는다. `line` 주변만 보지 않는다.
질문이 달린 뒤 커밋이 추가돼 코드가 이미 바뀌었을 수 있고, 그 경우
"바뀐 걸 모르고 옛 코드에 답하는" 답글이 나온다. 그게 이 단계에서 가장 눈에 띄는 실패다.

같은 파일에 여러 스레드가 걸려 있으면 파일은 **한 번만** 읽는다.

작성자 답변이 다른 파일을 가리키면(예: "그건 `resolveAnchors`에서 이미 막습니다")
그 파일도 확인한다. **확인하지 않은 것을 확인한 것처럼 답하지 않는다.**

**파일이 더 이상 없으면**(질문 이후 삭제·이동됨) 그 스레드는 코드를 읽지 못한 채 답하게
된다. 이 경우 **suggestion을 만들지 않고**, 답글에서 "해당 파일이 지금은 없어 현재 코드를
확인하지 못했다"고 밝힌 뒤 작성자 답변 내용에만 근거해 답한다. 없는 파일의 코드를
기억이나 `question` 본문에서 복원해 답하지 않는다.

### 4. 페르소나 프롬프트 로딩

Read로 읽고 그 규칙을 그대로 따른다. 요약해서 기억하지 말고 원문을 읽는다.

- `scripts/ai-reviewer/personas/intern.md` — 정체성·톤·금지 사항. **이 파일에는 재답변
  단계 규칙이 따로 없다.** 이도현의 재답변 규칙은 아래 5-1이 전부다.
- `scripts/ai-reviewer/personas/senior.md` — `## 재답변 단계 규칙` 절이 있다.
  그 절과 아래 5-2를 함께 따른다.

### 5. 재답변 생성 — 전체를 한 번에

**모든 스레드를 한 번에 읽고 한 번의 사고 흐름에서 답한다.**
스레드 하나씩 처리하면 같은 파일의 두 답글이 서로 모순되는 말을 하게 된다
(한쪽은 "의도 이해했습니다", 다른 쪽은 같은 코드를 문제로 취급하는 식).

한 스레드에는 **한 봇만** 답한다. 스레드의 `persona`가 곧 답할 봇이다.
인턴 스레드에 시니어가 끼어들지 않는다.

#### 5-1. 이도현(인턴) 스레드 → 주석 제안

이해한 내용을 요약하고, 작성자 설명을 **코드 주석**으로 정리해 suggestion으로 제안한다.

````
**이도현** · 인턴 개발자

아 pushState로 다른 글로 넘어가면 이 문서로 돌아올 일이 없는 거군요. 이해했습니다.
나중에 저 같은 사람이 또 헷갈릴 것 같아서 설명해주신 걸 주석으로 정리해봤는데 맞을까요?

```suggestion
		// 다른 글로 이동하면 이 문서로 돌아오지 않는다. 남의 페이지에 옵저버를 남기지 않도록 timeoutMs를 기다리지 않고 즉시 해제한다.
		if (location.href !== startUrl) {
```
````

**주석을 남기는 근거는 `AGENTS.md`의 주석 가이드다.**

```
AGENTS.md > AI 협업 가이드 > 주석 가이드
- 복잡한 코드에만 간결한 주석
- "무엇"보다 "왜"에 초점
```

- **"복잡한 코드에만"** — 트리거가 스스로를 증명한다. 사람이 읽고 물어봤다는 사실이
  그 코드가 자명하지 않다는 증거다. 질문이 없었던 곳에는 주석을 만들지 않는다.
- **"'무엇'보다 '왜'"** — 주석에는 **답변의 "왜"만** 담는다.
  코드를 한국어로 옮긴 문장("URL이 다르면 중단한다")은 "무엇"이라 넣지 않는다.

**`AGENTS.md`에 "모든 export에 JSDoc" 같은 규칙은 없다.** 그런 규칙을 근거로 들지 않는다.
`API 문서: 목적, 파라미터, 반환값, ...` 문장도 **문서를 쓸 때 무엇을 담는지**를 말하는 것이지
문서를 쓰라는 의무가 아니다. 이 문장을 근거로 주석을 밀어붙이지 않는다.

**주석을 제안하지 않는 경우** — 아래에 해당하면 suggestion 없이 답글만 단다.
없는 것보다 나쁜 주석은, 코드를 다시 읽으면 알 수 있는 내용을 반복하는 주석이다.

- 작성자 답변이 한 줄로 끝나고 그 내용이 코드·변수명에서 이미 보인다
- 답변이 "타입 때문입니다" 류라 주석으로 옮기면 코드 재진술이 된다
- 이미 같은 내용의 JSDoc·주석이 그 자리에 있다 (3단계에서 파일 전체를 읽었으니 안다)

이때 답글은 이해한 내용만 짧게 남긴다. "주석은 필요 없어 보여 제안하지 않았습니다"까지 쓸
필요는 없다 — 인턴이 주석 여부를 판단하는 위치가 아니다.

기존 JSDoc에 한 줄을 **덧붙이는** 경우에는 아래 5-3의 앵커 라인 제약 때문에
**앵커 라인이 그 JSDoc 안에 있어야** 한다. 앵커가 함수 본문 줄인데 위쪽 JSDoc을 고치려
하면 suggestion을 만들 수 없다. 그 경우 폴백한다.

#### 5-2. 박성우(시니어) 스레드 → 구체적 답 + (필요하면) 개선안

**여기서는 답을 준다.** 질문 단계에서 답을 미룬 이유가 이것이다 — 작성자가 먼저 생각한
뒤에 답을 얹는 구조다. 그러니 두루뭉술하게 넘어가면 순서를 지킨 의미가 없어진다.

- 작성자 답변을 **먼저 인정하거나 반박한다.** "그럴 수도 있겠네요"로 흐리지 않는다.
- 수정이 필요하다고 판단하면 suggestion으로 **구체적인 코드**를 제시한다.
- **작성자 답변이 타당하면 수긍하고 끝낸다.** 후속 작업을 만들지 않는다.
  쓸모 있어 보이려고 억지 지적을 덧붙이면, 다음 PR에서 이 봇의 지적을 아무도 안 읽는다.
- 작성자가 답변에서 이미 말한 내용을 다시 정리해 돌려주지 않는다.
  **작성자가 말하지 않은 것**(그래서 어떻게 되는지, 어디까지가 안전한지)을 더한다.

##### 제안한 코드가 실제로 무엇을 하는지 확인한다

5-3은 suggestion이 **어디에 붙는지**만 검증한다. **무엇을 하는지는 아무도 검증하지 않는다.**
사용자는 이 제안을 버튼 한 번으로 커밋하므로, 틀린 제안의 비용은 틀린 답글보다 훨씬 크다.

suggestion을 내기 전에 **제안한 코드를 파일 전체 맥락에서 다시 읽고**, 답글이 주장하는
동작만 하는지 확인한다. 특히 아래를 짚는다.

- 이 API가 **주장한 범위보다 넓게 작용하지 않는가.** 큐·캐시·구독을 비우거나 끊는
  API는 대개 "내가 만든 것"만 골라 처리해주지 않는다.
- 제안이 닿지 않는 경로가 있는가 (다른 호출부, 조기 반환, 정리 함수 이후).
- 제안이 새로 만드는 실패 모드는 무엇인가.

그 결과에 따라 셋 중 하나를 고른다.

| 확인 결과 | 답글 |
| --- | --- |
| 주장한 동작만 한다 | suggestion을 낸다 |
| 동작은 하지만 **트레이드오프나 미커버 케이스**가 있다 | suggestion을 내되 **그 트레이드오프를 답글에 적는다** |
| 동작을 확신할 수 없다 | **suggestion을 내지 않고** 방향만 산문으로 설명한다 |

**"안전합니다", "이것만 버리면 됩니다" 같은 문장은 확인한 뒤에만 쓴다.**
확인하지 않고 쓴 안전 주장은, 규모를 정정해 얻은 신뢰를 그 자리에서 되돌려준다.
확신이 없으면 판단을 작성자에게 넘기는 것이 정답이다 — 이 워크플로우의 목적은
작성자가 결정하게 만드는 것이지 봇이 대신 고치는 게 아니다.

#### 5-3. suggestion 블록 검증 — 이 커맨드의 최대 실패 지점

GitHub의 `suggestion` 블록은 **코멘트가 앵커된 라인을 그대로 교체한다.**
`cli.ts`는 리뷰 코멘트를 `line` 하나만 지정해 달기 때문에(`start_line` 없음)
**앵커는 항상 정확히 한 줄**이다. 교체 결과가 여러 줄이 되는 건 가능하지만,
**교체 대상은 그 한 줄뿐**이다.

즉 suggestion 블록의 내용은 **`(추가할 줄들) + 앵커 라인의 현재 텍스트`** 여야 한다.
앵커 라인 텍스트를 빼먹으면 그 줄이 삭제되고, 다르게 쓰면 코드가 조용히 바뀐다.

**suggestion을 만들기 전에 매 스레드마다 아래 세 명령을 실행한다.**
"조심한다"로 대체하지 않는다.

```bash
git status --porcelain -- <path>
git show HEAD:<path> | sed -n '<line>p'
git show HEAD:<path> | sed -n '<line>p' | cat -tv
```

세 명령의 역할이 다르다. **바꿔 쓰면 안 된다.**

- `git show HEAD:` — GitHub이 보는 것은 **커밋된 내용**이다. 워킹트리 파일이 아니다.
- **두 번째 명령(`sed`까지)의 출력이 suggestion에 옮겨 적을 원문이다.** 여기서만 복사한다.
- **세 번째 명령(`cat -tv`)의 출력은 들여쓰기 문자를 세는 용도뿐이다.**
  BSD `cat`의 `-t`는 `-v`를 함께 켜기 때문에 **한글이 전부 `\M-...` 이스케이프로 깨진다.**
  이 레포는 주석·문자열에 한글이 많아 대부분의 줄이 깨져 나온다.

  ```
  $ git show HEAD:pages/content-ui/src/ui/highlight/restoreHighlights.ts | sed -n '7p' | cat -tv
  /** �M-^J��M-^L 그려�M-^@�M-^JM-^T 본문�M-^]M-^D ...
  ```

  **이 출력에서 라인 텍스트를 복사하면 코드가 조용히 망가진다.** 탭(`^I`) 개수만 센다.
  (`cat -A`는 GNU 전용이라 macOS에서 `illegal option`으로 죽는다.)

**아래 중 하나라도 걸리면 suggestion 없이 일반 답글만 단다** (스펙 §6.2의 폴백).
폴백은 실패가 아니라 정상 경로다. 억지로 suggestion을 붙이는 쪽이 실패다.

| 조건 | 이유 |
| --- | --- |
| `line`이 `null` | GitHub이 outdated로 판정 — 붙을 자리가 없다 |
| `headRefOid` ≠ 로컬 `HEAD` (1단계) | 로컬 파일이 GitHub 기준과 다르다 |
| `git status --porcelain`에 해당 파일이 나옴 | 커밋 안 된 수정이 있어 확인 결과를 믿을 수 없다 |
| `git show HEAD:<path>`가 `fatal: path ... does not exist`로 실패 | 파일이 삭제·이동됐다 (3단계 참고) |
| `sed -n '<line>p'` 출력이 **비어 있음** | 파일이 짧아져 그 라인이 없다 |
| 앵커 라인이 질문이 가리키던 코드가 아님 | 코드가 바뀌었다 — 옛 코드에 붙는다 |
| 5-2의 동작 확인을 통과하지 못함 (시니어) | 제안이 무엇을 하는지 확신할 수 없다 |

폴백한 스레드는 8단계 보고에 **이유와 함께** 적는다. 조용히 넘어가면 사용자는
"왜 어떤 스레드만 주석 제안이 없지?"를 스스로 추적해야 한다.

**suggestion의 앵커 라인 줄은 두 번째 명령의 출력과 문자 단위로 같아야 한다.**
들여쓰기만 맞추는 걸로는 부족하다 — 변수명 한 글자, 세미콜론 유무, 따옴표 종류, 줄 끝
공백까지 그대로다. 확인은 두 단계로 한다.

1. **본문**: 두 번째 명령의 출력을 그대로 복사해 붙인다. 눈으로 옮겨 적지 않는다.
2. **들여쓰기**: 세 번째 명령의 `^I` 개수와, JSON에 쓴 `\t` 개수를 대조한다.
   이 레포는 탭 들여쓰기다. 공백으로 바꾸면 suggestion이 통째로 공백 변경 커밋이 된다.

### 6. 후속 작업 항목 추출

#### 6-0. 먼저 PR 본문의 기존 항목을 읽는다

```bash
gh pr view --json body --jq .body
```

`<!-- ai-followup:start -->` 와 `<!-- ai-followup:end -->` 사이 구간을 읽는다.
비어 있거나 마커가 없으면 이번이 처음이다.

**이 단계를 건너뛰면 같은 지적이 두 줄로 남는다.** `followup`의 중복 제거는
공백·대소문자만 정규화한 **완전 일치 비교**다(의미가 비슷한 걸 지워버리면 사용자가 넣은
항목이 조용히 사라지므로 일부러 그렇게 만들었다). 그래서 `post`가 중간에 실패해 재실행하는
경우처럼 같은 스레드를 다시 다루게 되면, 모델이 문장을 **조금 다르게 쓰기만 해도**
중복 제거를 그대로 통과한다.

- 이미 그 논점이 적혀 있으면 → **기존 문장을 글자 그대로 재사용**하거나 항목을 뺀다.
- **바꿔 쓰지 않는다.** "더 잘 다듬은" 문장이 곧 중복 한 줄이다.
- 표현을 정말 고쳐야 하면 항목을 추가하지 말고, 8단계 보고에서 사용자에게 알린다.
  이 커맨드는 기존 항목을 수정·삭제하지 않는다 (`followup`은 append만 한다).

#### 6-1. 항목 선별

**시니어 스레드 중 작성자가 문제를 인정한 것만** 뽑는다 (스펙 §6.3).

| 작성자 답변 | 처리 |
| --- | --- |
| "아 그건 놓쳤네요", "고쳐야겠네요" — 인정 | 항목 추가 |
| "의도한 겁니다" + 근거가 타당 | **추가하지 않는다** |
| "의도한 겁니다" + 근거가 코드와 어긋남 | 답글에서 반박하되, 작성자가 인정한 게 아니므로 **추가하지 않는다** |

인턴 스레드는 후속 작업 대상이 아니다. 인턴의 산출물은 주석이다.

각 항목은 **한 줄**이고, 스레드를 다시 찾아갈 수 있게 **파일명과 스레드 포인터를
포함한다.** 포인터는 그 스레드의 `rootId`를 쓴다 (`pending` 출력에 있다).

```
content-ui/restoreHighlights.ts 복원 렌더가 자기 옵저버를 다시 깨우는 문제 처리 — 스레드 #112
```

경로 전체를 쓸 필요는 없지만, 같은 파일명이 여러 패키지에 있으면 구분되게 쓴다.
`rootId`는 리뷰 코멘트 ID라서
`https://github.com/guesung/web-memo/pull/<PR번호>#discussion_r<rootId>` 로 바로 열린다.

### 7. 입력 파일 작성과 게시

`$GITDIR/ai-review-reply.json` 에 쓴다 (`.git/` 안이라 커밋되지 않는다).
> **입력 파일 경로 주의.** `.git` 은 **worktree에서 디렉토리가 아니라 파일**이다 (`gitdir: ...` 한 줄을 담은 텍스트 파일). 그대로 `.git/xxx.json` 에 쓰려 하면
> `NotADirectoryError` / `ENOTDIR` 로 즉시 죽는다. 아래처럼 실제 gitdir을 구해서 쓴다.
>
> ```bash
> GITDIR=$(git rev-parse --git-dir)
> ```
>
> 일반 클론에서는 `.git`, worktree에서는 실제 gitdir 경로가 나오므로 양쪽 모두 동작한다.
> 아래의 모든 `.git/` 표기는 `$GITDIR/` 로 읽는다.

```json
{
	"replies": [
		{
			"persona": "intern",
			"rootId": 123456,
			"body": "**이도현** · 인턴 개발자\n\n..."
		}
	]
}
```

- `persona` — 정확히 `"intern"` 또는 `"senior"`. **스레드의 `persona`를 그대로 옮긴다.**
  다른 값이면 `cli.ts`가 **첫 네트워크 호출 전에** 배치 전체를 거부하고 아무것도 게시하지
  않는다. **(검증됨)**
- `rootId` — `pending` 출력의 `rootId` 그대로. **숫자다. 문자열로 쓰지 않는다.**
  1 이상의 정수가 아니면(문자열·0·음수·소수 등) `cli.ts`가 같은 사전 검증에서
  배치 전체를 거부한다. **(검증됨)**
- **`cli.ts`가 검사하는 것은 `persona`와 `rootId`(와 questions의 `kind`·`line`)뿐이다.**
  `body`는 검사하지 않는다. `rootId` 검증은 **형식(1 이상의 정수인지)만** 본다 —
  숫자이기만 하면 통과하고, **그 rootId를 가진 스레드가 실제로 존재하는지는 검사하지
  않는다.** 존재하지 않는 rootId면 게시가 시작된 뒤 GitHub이 거부하며, **그 시점엔
  앞선 답글이 이미 나가 있다.** `pending` 출력에서 옮겨 적은 값이 맞는지 확인한다.
- `questions`·`scan` 키는 이 커맨드에서 쓰지 않는다 (`/ai-review` 전용).
- **마커(`<!-- ai-review:... -->`)를 `body`에 쓰지 않는다.** CLI가 `intern:reply` /
  `senior:reply`로 붙인다. 작성한 JSON에 `ai-review:` 문자열이 있으면 지우고 다시 쓴다.
  (2단계의 `question` 본문을 복사해 오면 이게 딸려 온다.)

```bash
node scripts/ai-reviewer/cli.ts post --pr <번호> --input "$GITDIR/ai-review-reply.json"
```

후속 작업 항목이 **하나라도 있으면** `$GITDIR/ai-review-followup.json`:

```json
{
	"items": [
		"content-ui/restoreHighlights.ts 복원 렌더가 자기 옵저버를 다시 깨우는 문제 처리 — 스레드 #112"
	]
}
```

```bash
node scripts/ai-reviewer/cli.ts followup --pr <번호> --input "$GITDIR/ai-review-followup.json"
```

**항목이 하나도 없으면 이 명령을 실행하지 않는다.**

`followup`은 PR 본문의 마커 구간에 **append**하며, 사람이 그 섹션에 적어둔 내용을
지우지 않는다. 중복 제거는 하지만 **공백·대소문자만 정규화한 완전 일치 비교**다. **(검증됨)**
같은 논점을 다르게 쓴 문장은 걸러지지 않으므로, 재실행 안전성은 CLI가 아니라
**6-0단계를 실제로 수행했는지**에 달려 있다.

### 8. 결과 보고

- 재답변한 스레드 수 — 페르소나별로, `파일:라인`과 함께
- **suggestion을 붙인 스레드**와 **폴백한 스레드(이유 포함)**
- PR 본문에 추가된 후속 작업 항목 (없으면 "없음"과 그 이유 — 작성자 답변이 다 타당했다 등)
- PR URL과, 인턴 suggestion이 있으면 "GitHub에서 커밋 버튼으로 반영하세요" 안내

## 주의 — 1턴 제한

**각 스레드에 봇은 딱 한 번만 답한다.** 이건 이 커맨드가 지키는 규칙이 아니라
`pending`이 구조적으로 보장하는 것이다 (스펙 §4.4): 작성자의 첫 답글 이후 같은
페르소나의 답글이 하나라도 있으면 그 스레드는 목록에서 사라진다.

- 같은 스레드를 두 번 처리하려 하지 않는다. **우회 방법을 찾지 않는다.**
- 봇이 답한 뒤 작성자가 또 답글을 달아도 봇은 침묵한다. 정상 동작이다.
- **이 커맨드를 다시 실행해도 이미 답한 스레드는 조회되지 않는다.** 재실행은 안전하며,
  보통 "재답변할 스레드가 없습니다"로 끝난다.

## 실패 대응

게시 실패 시 **조용히 넘어가지 않는다.** `cli.ts`는 어디까지 성공했고 어느 항목에서
멈췄는지를 stderr에 남긴다(`replies[2]` 같은 위치 표기). 그 내용을 그대로 보고한다.

- **입력 검증 에러**(`post 입력이 유효하지 않아 게시를 중단합니다`)는 아무것도 게시되지
  않은 상태다. JSON의 `persona`만 고쳐 그대로 재실행하면 된다.
- **게시 도중 실패**했다면 **앞선 답글은 이미 GitHub에 나가 있고 롤백되지 않는다.**
  - 입력 파일을 그대로 다시 실행하지 않는다. 중복 게시된다.
  - 대신 **`pending`을 다시 실행한다.** 이미 답한 스레드는 목록에서 빠져 있으므로,
    남은 스레드만 가지고 입력 파일을 다시 만들면 된다. 커맨드를 처음부터 다시 실행해도
    같은 결과가 된다 — 이미 나간 답글이 다시 나가지 않는다.
- **후속 작업 항목이 유실되지 않게 한다.** `post`가 성공한 스레드는 `pending`에서
  사라지므로, `followup`을 실행하기 전에 재실행하면 **그 스레드의 후속 작업 항목을 다시
  만들 수 없다.** 그래서 `post`가 중간에 실패했더라도
  **`$GITDIR/ai-review-followup.json`은 지우지 말고 `followup`을 먼저 실행한다.**
  같은 파일을 그대로 다시 실행하는 것은 안전하다(문장이 글자까지 같으므로 중복 제거가
  걸린다). 위험한 것은 **재실행하면서 항목을 새로 쓰는 경우**다 — 6-0단계에서 PR 본문의
  기존 항목을 먼저 읽고 문장을 그대로 재사용한다.
- **토큰/설정 에러**는 `~/.config/web-memo-bots/`의 키와 `config.json` 문제다.
  임의로 고치지 말고 사용자에게 원문 에러를 보여준다.
