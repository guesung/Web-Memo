# /ai-review — 두 페르소나가 PR에 질문한다

현재 브랜치의 PR에 두 AI 페르소나 명의로 인라인 질문 코멘트를 게시한다.
목적은 지적이 아니라 **작성자가 자기 코드를 설명하게 만드는 것**이다.
설계 근거는 [설계 문서](../../docs/superpowers/specs/2026-08-17-ai-review-personas-design.md) 참고.

## 인자

`$ARGUMENTS` — 페르소나별 질문 개수. 비어 있으면 **3**.
양의 정수가 아니면 실행하지 말고 사용자에게 알린다.

---

## 절차

### 1. PR 확인 및 사전 조건 검사

```bash
gh pr view --json number,url,headRefOid,author --jq '{number, url, headSha: .headRefOid, author: .author.login}'
git rev-parse HEAD
```

- PR이 없으면 중단하고 "먼저 `/pr`로 PR을 생성하세요"라고 안내한다.
- **`headRefOid`와 로컬 `HEAD`가 다르면 중단한다.** 코멘트는 GitHub이 아는 head 커밋
  기준으로 달리는데, 로컬에만 있는 커밋이 라인 번호를 바꿔놓았으면 전부 422가 난다.
  "먼저 `git push` 하세요"라고 안내한다.

### 2. 이미 질문이 달려 있는지 확인

```bash
node scripts/ai-reviewer/cli.ts pending --pr <번호>
```

출력은 `{ "prAuthor": ..., "threads": [...] }` 형태다.
`threads`가 비어 있지 않으면 **작성자 답변을 기다리는 스레드가 이미 있다**는 뜻이다.
이 경우 `/ai-review-reply`가 먼저일 가능성이 높다. 사용자에게 알리고,
그래도 새 질문을 추가할지 확인받는다.

### 3. 변경 내역 수집

```bash
git diff origin/master...HEAD --stat
git diff origin/master...HEAD
```

**베이스는 `master`다. `develop` 아님.**

### 4. 컨텍스트 수집 — 이 커맨드가 로컬에서 도는 이유

diff만 보고 질문하면 뻔한 질문이 나오고, 뻔한 질문에는 답을 안 한다.
답을 안 하면 이 워크플로우는 죽는다. 아래를 **반드시** 함께 읽는다.

- 변경된 파일들의 **전체 내용** (diff 조각이 아니라 파일 전체)
- 새로 추가/수정된 함수·훅·상수의 **주요 호출부** (Grep으로 찾는다)
- 함께 변경된 **테스트 파일** — 이미 다루고 있는 케이스를 다시 묻지 않기 위해
- `AGENTS.md` — 프로젝트 컨벤션 (지적 요약의 근거로 쓴다)
- 변경 파일이 속한 패키지의 인접 파일 (기존 패턴 파악용)
- PR 본문과 커밋 메시지 — 이미 설명된 내용을 다시 묻지 않기 위해

### 5. 페르소나 프롬프트 로딩

Read로 읽고 각 규칙을 **정확히** 따른다. 요약해서 기억하지 말고 원문을 읽는다.

- `scripts/ai-reviewer/personas/intern.md`
- `scripts/ai-reviewer/personas/senior.md`

### 6. 질문 생성

**두 페르소나의 질문을 한 번의 사고 흐름에서 함께 만든다.**
따로 생성하면 같은 코드에 중복 질문이 나온다.

- 인턴 질문 N개, 시니어 질문 N개 (N = 인자, 기본 3)
- 각 질문은 **서로 다른 위치**를 가리킨다
- **정말 물어볼 게 없으면 개수를 채우지 않는다.** 형식적 질문 하나가
  나머지 다섯 개의 신뢰까지 같이 깎는다. 개수를 못 채웠으면 그 사실을 사용자에게 보고한다.

시니어의 지적 요약(`scan`)도 함께 만든다. 지적할 게 없으면 `scan`을 `null`로 둔다.

#### 라인 번호 확정

`line`은 **diff에서 실제로 추가·변경된 새 파일 기준 라인 번호**여야 한다.
코멘트는 `side: "RIGHT"`로 달리므로 **삭제된 줄에는 달 수 없다.**
정확한 범위는 아래로 확인한다.

```bash
git diff origin/master...HEAD --unified=0 -- <파일>
```

`@@ -a,b +c,d @@` 의 `+c,d` 가 새 파일 기준 변경 구간이다.
지정한 라인이 이 구간 안에 들어가는지 게시 전에 직접 대조한다.

### 7. 입력 파일 작성

`.git/ai-review-input.json` 에 쓴다 (`.git/` 안이라 커밋되지 않는다).

```json
{
	"questions": [
		{
			"persona": "intern",
			"path": "packages/shared/src/hooks/useMemoQuery.ts",
			"line": 34,
			"kind": "q1",
			"body": "**이도현** · 인턴 개발자\n\n(질문 본문)"
		}
	],
	"scan": {
		"persona": "senior",
		"body": "**박성우** · 시니어 개발자\n\n질문과 별개로 눈에 띈 것들입니다. 답변 안 하셔도 됩니다.\n\n- `파일:라인` — 내용 (근거)"
	}
}
```

스키마 제약 — `cli.ts`가 **첫 네트워크 호출 전에** 전부 검사하고,
하나라도 어긋나면 배치 전체를 게시하지 않는다.

- `persona` — 정확히 `"intern"` 또는 `"senior"`. 다른 값은 통과하지 못한다.
- `kind` — `[a-z0-9_-]+` 만 허용. 페르소나별로 `q1`, `q2`, … 순번을 매기고
  같은 페르소나 안에서 중복시키지 않는다. `Q1`, `q_1!` 같은 값은 거부된다.
- `path` — 레포 루트 기준 경로.
- `scan` — 지적할 게 없으면 키를 생략하거나 `null`. **빈 scan 코멘트를 만들지 않는다.**
- `replies` 키는 이 커맨드에서 쓰지 않는다 (`/ai-review-reply` 전용).

**마커(`<!-- ai-review:... -->`)를 `body`에 직접 쓰지 않는다.** CLI가 붙인다.
직접 쓰면 마커가 두 번 들어가 스레드 판별이 깨진다.
작성한 JSON에 `ai-review:` 문자열이 들어 있으면 지우고 다시 쓴다.

### 8. 게시

```bash
node scripts/ai-reviewer/cli.ts post --pr <번호> --input .git/ai-review-input.json
```

### 9. 결과 보고

게시된 질문을 페르소나별로 `파일:라인` 과 함께 나열하고 PR URL을 출력한다.
사용자에게 "GitHub에서 답변한 뒤 `/ai-review-reply`를 실행하세요"라고 안내한다.

## 실패 대응

게시 실패 시 **조용히 넘어가지 않는다.** `cli.ts`는 어디까지 성공했고 어느 항목에서
멈췄는지를 stderr에 남긴다 (`questions[1]` 같은 위치 표기). 그 내용을 그대로 보고한다.

- **이미 게시된 코멘트는 롤백되지 않는다.** 재시도할 때는 입력 파일에서
  **이미 게시된 항목을 반드시 지운다.** 그대로 다시 실행하면 중복 게시된다.
- **422**는 대부분 `line`이 diff 범위 밖인 경우다. 7단계의 `--unified=0` 대조를
  다시 하고 라인을 고쳐 재시도한다.
- **입력 검증 에러**(`post 입력이 유효하지 않아 게시를 중단합니다`)는 아무것도
  게시되지 않은 상태다. JSON만 고쳐 그대로 재실행하면 된다.
- **토큰/설정 에러**는 `~/.config/web-memo-bots/` 의 키와 `config.json` 문제다.
  임의로 고치지 말고 사용자에게 원문 에러를 보여준다.
