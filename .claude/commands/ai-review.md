# /ai-review — 두 페르소나가 PR에 질문한다

현재 브랜치의 PR에 두 AI 페르소나 명의로 인라인 질문 코멘트를 게시한다.
목적은 지적이 아니라 **작성자가 자기 코드를 설명하게 만드는 것**이다.
설계 근거는 [설계 문서](../../docs/superpowers/specs/2026-08-17-ai-review-personas-design.md) 참고.

## 인자

`$ARGUMENTS` — 페르소나별 질문 개수. 비어 있으면 **3**.
양의 정수가 아니면 실행하지 말고 사용자에게 알린다.

---

## 절차

### 1. PR 확인 및 사전 조건 검사

```bash
gh pr view --json number,url,headRefOid,author --jq '{number, url, headSha: .headRefOid, author: .author.login}'
git rev-parse HEAD
```

- PR이 없으면 중단하고 "먼저 `/pr`로 PR을 생성하세요"라고 안내한다.
- **`headRefOid`와 로컬 `HEAD`가 다르면 중단한다.** 코멘트는 GitHub이 아는 head 커밋
  기준으로 달리는데, 로컬에만 있는 커밋이 라인 번호를 바꿔놓았으면 전부 422가 난다.
  "먼저 `git push` 하세요"라고 안내한다.

### 2. 이미 질문이 달려 있는지 확인

```bash
node scripts/ai-reviewer/cli.ts pending --pr <번호>
```

출력은 `{ "prAuthor": ..., "threads": [...] }` 형태다.
`threads`가 비어 있지 않으면 **작성자 답변을 기다리는 스레드가 이미 있다**는 뜻이다.
이 경우 `/ai-review-reply`가 먼저일 가능성이 높다. 사용자에게 알리고,
그래도 새 질문을 추가할지 확인받는다.

### 3. 변경 파일 목록 수집과 대상 선정

**여기서 전체 diff를 통째로 읽지 않는다.** 먼저 목록만 본다.

```bash
git fetch origin master
git diff origin/master...HEAD --stat
```

**`git fetch`를 건너뛰지 않는다.** 로컬 `origin/master` 참조가 오래됐으면 diff가
PR의 실제 diff보다 넓어지고, PR에 없는 라인에 코멘트를 달아 **전부 422가 난다.**
1단계의 head 검사는 base가 낡은 경우를 잡지 못한다.

**베이스는 `master`다. `develop` 아님.**

`--stat` 결과로 **읽을 파일을 먼저 정한다.** 9,000줄짜리 PR에서 diff를 통째로 읽으면
그 자리에서 컨텍스트가 무너지고, 그 뒤의 선별 규칙은 돌아볼 기회조차 없다.
아래를 그대로 따른다.

1. 아래 **제외 대상**을 목록에서 뺀다.
   - 락파일 (`pnpm-lock.yaml` 등), 스냅샷 (`__snapshots__/`)
   - 생성물 (`packages/shared/src/types/supabase.ts` 같은 자동 생성 타입, `dist/`, `build/`)
   - 번역 번들 (`_locales/**/messages.json`, `messages/*.json`)
   - `pnpm-workspace.yaml`·`package.json` 의 버전 범프만 있는 변경
2. 남은 파일을 `--stat` 의 **변경 라인 수 내림차순**으로 정렬한다.
3. **상위 10개**를 대상 파일로 삼는다. 나머지는 이번 실행에서 다루지 않는다.
4. **대상이 아닌 파일은 질문 대상에서 제외한다.** 예외 없다.
5. 제외·미선정 파일이 있으면 9단계 보고에 **파일 수와 목록을 명시한다.**
   "N개 파일 중 M개만 읽었고 질문은 그 M개에서만 나왔다"고 사용자에게 밝힌다.

### 4. 컨텍스트 수집 — 이 커맨드가 로컬에서 도는 이유

3단계에서 정한 **대상 파일에 한정해서** diff를 읽는다.

```bash
git diff origin/master...HEAD -- <대상 파일 1> <대상 파일 2> ...
```

diff만 보고 질문하면 뻔한 질문이 나오고, 뻔한 질문에는 답을 안 한다.
답을 안 하면 이 워크플로우는 죽는다. 아래를 **반드시** 함께 읽는다.

- 대상 파일들의 **전체 내용** (diff 조각이 아니라 파일 전체)
- 새로 추가/수정된 함수·훅·상수의 **주요 호출부** (Grep으로 찾는다)
- 함께 변경된 **테스트 파일** — 이미 다루고 있는 케이스를 다시 묻지 않기 위해
- `AGENTS.md` — 프로젝트 컨벤션 (지적 요약의 근거로 쓴다)
- 대상 파일이 속한 패키지의 인접 파일 (기존 패턴 파악용)
- PR 본문과 커밋 메시지 — 이미 설명된 내용을 다시 묻지 않기 위해

대상 파일이 10개인데도 양이 감당이 안 되면, **더 줄이고 줄였다고 보고한다.**
일부만 읽고 다 읽은 셈 치는 것이 가장 나쁜 결과다.
읽지 않은 파일에 대한 질문은 반드시 틀린다.

### 5. 페르소나 프롬프트 로딩

Read로 읽고 각 규칙을 **정확히** 따른다. 요약해서 기억하지 말고 원문을 읽는다.

- `scripts/ai-reviewer/personas/intern.md`
- `scripts/ai-reviewer/personas/senior.md`

### 6. 질문 생성

**두 페르소나의 질문을 한 번의 사고 흐름에서 함께 만든다.**
따로 생성하면 같은 코드에 중복 질문이 나온다.

- 인턴 질문 N개, 시니어 질문 N개 (N = 인자, 기본 3)
- 각 질문은 **서로 다른 위치**를 가리킨다
- **정말 물어볼 게 없으면 개수를 채우지 않는다.** 형식적 질문 하나가
  나머지 다섯 개의 신뢰까지 같이 깎는다. 개수를 못 채웠으면 그 사실을 사용자에게 보고한다.

시니어의 지적 요약(`scan`)도 함께 만든다. 지적할 게 없으면 `scan`을 `null`로 둔다.

#### 두 페르소나가 같은 결정을 겨냥할 때

"서로 다른 위치"만으로는 부족하다. 한 결정이 여러 줄에 걸쳐 있으면 두 페르소나가
그 결정을 66번 줄과 67번 줄로 나눠 물 수 있고, 작성자에게는 같은 질문 두 번이다.

**같은 결정을 겨냥하면 한 명만 묻는다.** 판정은 질문의 **답이 어떤 종류인지**로 한다.

| 답의 종류 | 묻는 사람 |
| --- | --- |
| 그렇게 만든 **의도 설명** | 이도현(인턴) |
| 처리되지 않은 **케이스의 결과** | 박성우(시니어) |
| 둘 다로 읽힘 | **이도현(인턴)** |

마지막 줄의 근거: 시니어에게는 지적 요약이라는 다른 출구가 있지만 인턴에게는 없고,
의도 설명이 주석 산출물로 이어지기 때문이다.

**양보한 쪽은 인접 라인으로 옮겨 같은 결정을 다시 묻지 않는다.**
다른 결정으로 옮기거나, 없으면 개수를 줄인다.

한 페르소나 안에서 논점이 겹칠 때의 규칙(**날카로운 쪽을 남긴다**)은
각 페르소나 프롬프트에 있다. 위치가 앞이라는 이유로 남기지 않는다.

#### 라인 번호 확정

`line`은 **diff에서 실제로 추가·변경된 새 파일 기준 라인 번호**여야 한다.
코멘트는 `side: "RIGHT"`로 달리므로 **삭제된 줄에는 달 수 없다.**
정확한 범위는 아래로 확인한다.

```bash
git diff origin/master...HEAD --unified=0 -- <파일>
```

`@@ -a,b +c,d @@` 의 `+c,d` 가 새 파일 기준 변경 구간이다.
지정한 라인이 이 구간 안에 들어가는지 게시 전에 직접 대조한다.

### 7. 입력 파일 작성

`$GITDIR/ai-review-input.json` 에 쓴다 (`.git/` 안이라 커밋되지 않는다).
> **입력 파일 경로 주의.** `.git` 은 **worktree에서 디렉토리가 아니라 파일**이다 (`gitdir: ...` 한 줄을 담은 텍스트 파일). 그대로 `.git/xxx.json` 에 쓰려 하면
> `NotADirectoryError` / `ENOTDIR` 로 즉시 죽는다. 아래처럼 실제 gitdir을 구해서 쓴다.
>
> ```bash
> GITDIR=$(git rev-parse --git-dir)
> ```
>
> 일반 클론에서는 `.git`, worktree에서는 실제 gitdir 경로가 나오므로 양쪽 모두 동작한다.
> 아래의 모든 `.git/` 표기는 `$GITDIR/` 로 읽는다.

```json
{
	"questions": [
		{
			"persona": "intern",
			"path": "packages/shared/src/hooks/useMemoQuery.ts",
			"line": 34,
			"kind": "q1",
			"body": "**이도현** · 인턴 개발자\n\n(질문 본문)"
		}
	],
	"scan": {
		"persona": "senior",
		"body": "**박성우** · 시니어 개발자\n\n질문과 별개로 눈에 띈 것들입니다. 답변 안 하셔도 됩니다.\n\n- `파일:라인` — 내용 (근거)"
	}
}
```

**`cli.ts`가 게시 전에 검사하는 것은 `persona`·`kind`·`line` 세 개다.**
이 셋은 첫 네트워크 호출 전에 배치 전체를 검사하고, 어긋나면 아무것도 게시하지 않는다.

- `persona` — 정확히 `"intern"` 또는 `"senior"`. 다른 값은 통과하지 못한다. **(검증됨)**
- `kind` — `[a-z0-9_-]+` 만 허용. 페르소나별로 `q1`, `q2`, … 순번을 매기고
  같은 페르소나 안에서 중복시키지 않는다. `Q1`, `q_1!` 같은 값은 거부된다. **(검증됨)**
- `line` — 1 이상의 정수여야 한다. 문자열(`"34"`)이나 0 이하, 소수 같은 값은
  거부된다. **(검증됨)** 다만 이 검증은 **형식만** 본다 — 정수이기만 하면 통과하고,
  diff 범위 밖의 라인인지는 검사하지 않는다.

**`path`·`body`는 검사하지 않는다.** 잘못돼 있어도 게시가 시작되고,
해당 항목에서 GitHub이 422를 던지며 멈춘다. **그 시점엔 앞선 코멘트가 이미 나가 있다.**
`line`이 형식은 맞아도 diff 범위 밖이면 마찬가지로 422가 나므로, 앞 절의
`--unified=0` 라인 대조를 생략하면 안 된다. CLI는 그 부분까지는 잡아주지 않는다.

- `path` — 레포 루트 기준 경로. 오타가 나도 게시 시점에야 실패한다.
- `scan` — 지적할 게 없으면 키를 생략하거나 `null`. **빈 scan 코멘트를 만들지 않는다.**
- `replies` 키는 이 커맨드에서 쓰지 않는다 (`/ai-review-reply` 전용).

**마커(`<!-- ai-review:... -->`)를 `body`에 직접 쓰지 않는다.** CLI가 붙인다.
스레드 판별이 깨지지는 않는다 — `parseMarker`의 패턴이 본문 끝에 고정돼 있어
CLI가 마지막에 붙인 마커가 이긴다. 다만 렌더된 코멘트 중간에 쓸데없는 주석이
남는다. 작성한 JSON에 `ai-review:` 문자열이 들어 있으면 지우고 다시 쓴다.

### 8. 게시

**질문이 0개이고 `scan`도 없으면 `cli.ts post`를 실행하지 않는다.**
빈 입력으로 실행하면 아무 일도 없이 성공으로 끝나서, 사용자는 "게시됐다는데
코멘트가 없다"는 상태를 마주하게 된다. 대신 아래를 사용자에게 그대로 알린다.

- 질문할 만한 지점을 찾지 못했다는 사실
- 그 이유 (변경이 너무 작다 / 의도가 코드와 커밋 메시지에 이미 드러나 있다 /
  변경이 생성물·번역 번들 위주다 등)
- 그래서 `post`를 실행하지 않았다는 것

억지로 질문을 만들어 개수를 채우지 않는다.

```bash
node scripts/ai-reviewer/cli.ts post --pr <번호> --input "$GITDIR/ai-review-input.json"
```

### 9. 결과 보고

게시된 질문을 페르소나별로 `파일:라인` 과 함께 나열하고 PR URL을 출력한다.
사용자에게 "GitHub에서 답변한 뒤 `/ai-review-reply`를 실행하세요"라고 안내한다.

아래는 해당될 때 **반드시** 함께 보고한다. 조용히 넘어가면 사용자가
커버리지를 실제보다 넓게 오해한다.

- 요청 개수를 못 채웠으면 페르소나별 실제 개수와 그 이유
- 4단계에서 읽지 않은 변경 파일이 있으면 **"전체 N개 중 M개만 읽었고 질문은
  그 M개에서만 나왔다"** 와 읽지 않은 파일 목록
- 두 페르소나가 같은 결정을 겨냥해 한쪽이 양보했으면 그 사실

## 실패 대응

게시 실패 시 **조용히 넘어가지 않는다.** `cli.ts`는 어디까지 성공했고 어느 항목에서
멈췄는지를 stderr에 남긴다 (`questions[1]` 같은 위치 표기). 그 내용을 그대로 보고한다.

- **이미 게시된 코멘트는 롤백되지 않는다.** 재시도할 때는 입력 파일에서
  **이미 게시된 항목을 반드시 지운다.** 그대로 다시 실행하면 중복 게시된다.
- **422**는 대부분 `line`이 diff 범위 밖인 경우다. 7단계의 `--unified=0` 대조를
  다시 하고 라인을 고쳐 재시도한다.
- **입력 검증 에러**(`post 입력이 유효하지 않아 게시를 중단합니다`)는 아무것도
  게시되지 않은 상태다. JSON만 고쳐 그대로 재실행하면 된다.
- **토큰/설정 에러**는 `~/.config/web-memo-bots/` 의 키와 `config.json` 문제다.
  임의로 고치지 말고 사용자에게 원문 에러를 보여준다.
