# /gs:implement-loop — 개인 프로젝트 구현 오케스트레이터

한 번 호출하면 아래를 **끝까지** 돈다. **마지막 출력까지 사람에게 묻는 자리는 하나도 없다.** 유일한 예외는 그 뒤 ④ 문제 해결 기록 승인이다.

사람이 개입하는 자리는 이 루프에 들어오기 전 [`/gs:design` ⑥ 승인](../design/SKILL.md) 또는 [`/gs:discuss` 확정](../discuss/SKILL.md) 하나뿐이다. 그 승인이 곧 "여기서부터 PR까지 위임한다"는 계약이고, 이 루프는 그 계약을 지킨다 — 판단이 갈리면 보수적으로 정하고 전부 기록해 마지막에 편다. 규약은 [autonomy.md](../../autonomy.md)가 SSOT다.

```
/gs:idea ─→ 기획 확정 ─→ /gs:design ─→ 설계서 + 확정 도장 (사람 승인)
/gs:discuss ─→ 사람과 같이 기획·설계 ─→ 설계서 + 확정 도장 (사람 합의)
                                                      │
[사람] design ⑥ 승인 · discuss 확정 ◄──────────────────┘
   │
   ▼
① 구현            /gs:implement --from-loop — 브랜치·스캐폴딩·아키텍처 문서·TDL·FE/BE 위임
                  ────────────── "막힌 지점"은 보수적으로 정하고 기록
② 셀프 QA         /gs:self-qa --run — FAIL 고치고 QA 재실행 (2연속 FAIL이면 정지)
   │
   ├────────────── 쌓인 `논의 필요`를 코드에 반영 (묻지 않는다)
   ▼
③ 테섭 배포와 PR  md = 테섭 배포(develop 있을 때만) → /gs:pr — [DB-<ID>] 접두사
   │
   ▼
[사람] 최종 검토 — AI가 정한 것 + 수동 QA
   │
   ▼
④ 문제 해결 기록  /gs:problem-log — 초안을 보여주고 사람 승인을 받은 것만 기록 (루프가 묻는 유일한 자리)
```

**회사판의 ②~⑤(검사기·리뷰어·리팩토링·반려자)가 없다.** 그 구간의 연료인 리뷰 원장은 회사 코드리뷰 지적으로 자라는데, 개인 프로젝트에는 리뷰어가 없다. 대신 **동작 검증(QA)은 그대로 남는다** — 코드 퀄리티와 "기능이 제대로 도는가"는 다른 축이고, 개인 프로젝트라고 깨진 채 PR을 올리고 싶지는 않다.

**구현 규칙은 이 파일에 없다.** ①은 [/gs:implement](../implement/SKILL.md) 호출이고, 브랜치·스캐폴딩·아키텍처 문서·TDL·에이전트 라우팅·커밋 단위는 전부 그 스킬이 SSOT다. 두 곳에 적으면 같은 설계서가 호출 경로에 따라 다르게 구현된다.

**③의 develop 머지가 테섭 배포다.** 개인 프로젝트에 별도 테스트 서버는 없지만, develop push에 자동 배포(Vercel 등)가 물려 있으면 그 순간이 테섭 배포다. 루프는 머지 뒤 [autonomy.md의 §권한·시크릿](../../autonomy.md#권한시크릿이-필요할-때--묻지-말고-직접-한다)대로 **`vercel` MCP(막히면 `aside-browser`)로 배포 상태와 URL을 직접 확인**해 PR 본문과 최종 보고에 싣는다. develop·dev가 없으면 머지도 배포 확인도 건너뛴다.

## 노션 접근

개인 업무 로그 페이지를 읽고 쓴다. **식별자·속성·본문 골격은 [notion-databases.md](../../notion-databases.md#개인-업무-로그)를 따른다.** `notion-home` MCP로만 접근한다.

**본문은 `# AI 작성` 아래만 고친다.** `# 인간 작성` 아래는 읽기만 하고, 섹션도 그 H1 아래에서 찾는다 — [AI 작성 경계](../../notion-databases.md#ai-작성-경계).

## §0. 시작 전 확인

1. **인자 파싱.**
   - `notion.com/…` → 개인 업무 로그 페이지 URL.
   - 그 외 → 로컬 설계서 파일 경로(개발·검증용). 도장을 요구하지 않는다.
   - 없으면 멈추고 인자를 요구한다.

   페이지 URL을 확보했으면 **[orca-worktree.md](../../orca-worktree.md)의 절차대로 현재 워크스페이스 메모에 기록한다.** 실패해도 멈추지 않는다. 설계서 파일 경로였다면 **[카드 없음 확인](../../orca-worktree.md#카드-없음-확인)을 수행한다** — 메모에 작업카드가 없으면 새 카드를 만들지 묻는다.
2. **범위 확인 — cashwalk 안이면 시작하지 않는다.** 대상 레포 경로가 `레포지토리/cashwalk/` 아래면 한 줄 남기고 멈춘다(정지 조건 F): `회사 작업은 /nudge:implement-loop 로 돌리세요. 이 플러그인은 개인 프로젝트 전용이라 원장 검사·리뷰어가 없습니다.` 회사 코드를 품질 판정 없이 PR까지 보내는 사고를 막는 가드레일이다.
3. **작업 페이지 읽기.** `API-retrieve-page-markdown`으로 `## 기획서`·`## 디자인`·`## 설계서`·`## TDL`·`## 논의 필요`·`## 루프 로그`를 확보한다. 속성 `ID`(`DB-123`)도 `API-retrieve-a-page`로 읽는다 — ③ PR 제목 접두사에 쓴다.
4. **설계서 확정 여부.** 아래 중 **하나라도** 걸리면 시작하지 않는다(정지 조건 B).

   | 확인 | 걸리면 |
   |---|---|
   | `## 설계서` 첫 줄에 확정 도장(`> 설계 확정 · <시각> · 사람 승인` 또는 `· 사람 합의 (/gs:discuss)`)이 있는가 | **`/gs:design <페이지 URL>`(또는 `/gs:discuss`)을 먼저 실행하라**고 안내하고 멈춘다 |
   | 설계서에 `TBD`/`미정`/`확인 필요`가 남아 있는가 | 해당 줄을 짚고 멈춘다 |

   **`## 논의 필요`가 차 있어도 멈추지 않는다.** `[AI 자동 결정]` 기록과 미해소 항목은 확정 때 설계 설명에 드러나 사람이 그걸 포함해 승인했다. 남은 미해소는 `/gs:implement` §0-5가 보수적으로 정하고 기록한다.

5. **QA 명세 뽑기.** **`/gs:self-qa <페이지 URL> --checklist-only`**로 뽑는다. 설계서가 확정됐으면 거기서 도출되는 것이라 판단 여지가 없다.

   **TDL·스캐폴딩·아키텍처 문서는 여기서 하지 않는다.** `/gs:implement`의 §0이 한다. 구현에 필요한 준비를 구현 스킬이 쥐고 있어야 단독 호출에서도 같은 준비가 일어난다.
6. **상태 파일 초기화.** 대상 레포의 `.omc/state/gs-loop.json`:
   ```json
   { "card": "<URL 또는 경로>", "branch": "<작업 브랜치>", "qa": null, "merge": null, "deploy": null, "pr": null }
   ```
   같은 페이지로 이미 상태 파일이 있으면 **이어서** 돈다(재개). 새로 시작하려면 사용자가 상태 파일을 지운다. TDL 진행 상황은 `/gs:implement`가 자기 상태 파일(`.omc/state/gs-implement.json`)에 들고 있으므로 여기 옮겨 적지 않는다 — 같은 값을 두 파일에 두면 재개 때 어느 쪽이 맞는지 알 수 없다.

## ① 구현 — `/gs:implement` 호출

```
/gs:implement <페이지 URL | 설계서 경로> --from-loop
```

그 스킬이 브랜치·스캐폴딩·아키텍처 문서·TDL·FE/BE 에이전트 라우팅·커밋을 전부 한다. **여기서 다시 정하지 않는다.** `--from-loop`를 붙이면 cashwalk 확인(§0-2가 이미 했다)을 건너뛰고, 머지·PR도 하지 않는다 — 그건 QA를 통과한 뒤 ③의 몫이다.

- 반환된 상태 파일(`.omc/state/gs-implement.json`)의 `branch`·`tdl`·`open_questions`를 읽어 이어간다. `blocked`가 비어 있지 않으면 그 스킬이 정지한 것이므로 같은 정지 조건으로 여기서도 멈춘다.
- 구현 중 막힌 지점의 처리(보수적 선택 + `[AI 자동 결정]` 기록)는 그 스킬 안에 있다. 루프는 그 결과를 받아 마지막 보고에 합친다.

### 작업 범위가 늘어났을 때

사용자가 루프 도중이나 끝난 뒤에 기능 추가·수정을 더 요청하면, 코드만 고치고 끝내지 않는다. 기록을 실제 범위에 맞추는 절차는 `/gs:implement`의 같은 이름 섹션이 갖고 있다. 루프가 더 하는 것은 하나다 — **추가분을 구현한 뒤 ② QA를 다시 돌린다.** 추가된 동작은 QA 명세에도 없으므로, `/gs:self-qa --checklist-only`로 항목을 먼저 늘린다.

## ② 셀프 QA

`--skip-qa`가 없으면 **`/gs:self-qa <페이지 URL> --run`**을 실행한다. 자동 항목은 브라우저 판정, 수동 항목은 재현 방법 기록.

- 결과 JSON(`pass`·`fail`·`manual`·`fail_items`)을 상태 파일 `qa`에 기록한다.
- `fail_items`는 해당 태그의 에이전트에게 보내 고치고 **QA만 다시 돌린다.** QA가 **2회 연속 FAIL이면** 멈추고 사람에게 넘긴다(무한 재시도 방지).
- `manual` 항목은 손대지 않는다. 사람 몫이다. "자동화 못 하니 검증 안 함"이 되지 않게 경계가 DB에 남는 것이 요점이다.

## ③ 머지와 PR

**올리기 직전에 쌓인 `논의 필요`를 반영한다.** 문서에만 적고 끝내지 않는다. 다만 **묻지 않는다** — 사람의 검토는 `/gs:design` ⑥(또는 `/gs:discuss` 확정)에서 이미 끝났다.

- 루프 중 이미 `[AI 자동 결정]`으로 정해진 항목은 그대로 둔다.
- **결정이 코드를 바꾸는 것**만 반영한다(보수적 선택 + 기록). 단순 기록용은 문서에만 남긴다.
- 코드를 고쳤으면 ②를 다시 돌린다. 고친 코드를 검증 없이 올리지 않는다.

### (a) md — 테섭 배포 (develop 머지 · 조건부)

`git branch --list develop dev`로 확인한다. **있으면** [`/common:md`](../../../common/skills/md/SKILL.md)를 실행하고(현재 브랜치를 develop에 `--no-ff` 머지 → push → 원래 브랜치 복귀), 결과를 상태 파일 `merge`에 적는다. **없으면 건너뛰고** `merge: "skipped: develop 없음"`을 적는다 — 개인 레포는 main 단일 브랜치인 경우가 많고, 없는 브랜치를 루프가 만들어내면 그 레포의 브랜치 전략을 스킬이 정하는 셈이 된다.

**머지했으면 배포 결과를 직접 확인한다.** 사람에게 "배포됐나요?"라고 묻지 않는다.

1. `vercel` MCP의 `list_deployments`(대상 레포 프로젝트)로 방금 push한 커밋의 배포를 찾는다. `get_deployment`로 상태를 읽고, `READY`면 배포 URL을, `ERROR`면 `get_deployment_build_logs`로 실패 사유 첫 줄을 잡는다.
2. MCP가 안 붙거나 프로젝트를 못 찾으면 `aside-browser` 스킬로 배포 대시보드를 직접 연다.
3. 둘 다 막히면 그 항목만 건너뛴다. 상태 파일 `deploy`에 `unknown: <시도한 것>`을 적고 루프는 계속 돈다 — 배포 확인 실패로 PR을 못 올리는 쪽이 더 나쁘다.

결과를 상태 파일 `deploy`에 적는다: `{ "url": "...", "state": "READY|ERROR|unknown", "checked_by": "vercel-mcp|aside-browser" }`. 빌드가 `ERROR`면 **PR은 그대로 올리되** 본문 `검증`과 최종 보고에 실패 사유를 적는다. 배포 실패는 코드를 다시 만질 근거이지 PR을 감출 근거가 아니다.

`--skip-pr`이 주어져도 머지는 한다. 둘은 다른 결정이다. 스크립트가 예상 밖 메시지로 끝나면 **그대로 전달하고 우회하지 않는다** — origin에 push하는 되돌리기 어려운 작업이다.

**QA 뒤에 둔 이유**: 깨진 코드가 통합 브랜치에 들어가면 그 뒤의 모든 작업이 그 위에 쌓인다.

### (b) PR

`--skip-pr`이 없으면 **`/gs:pr`**로 PR을 만든다(draft 아님). base는 main(기본 브랜치). 아래 제목 규칙을 `/gs:pr`의 인자로 넘긴다.

### PR 제목

```
[DB-<ID>] <타입>: <요약>        예) [DB-207] feat: 메모 검색 추가
```

- `ID`는 개인 페이지 속성(unique_id)이라 값 자체가 `DB-123` 형태다. **`DB-`를 두 번 붙이지 않는다.**
- 로컬 설계서 파일이면 접두사 없음. 억지로 만들지 않는다. 단 base가 master면 카드가 필수라 `/gs:pr`이 카드를 묻는다.

### PR 본문 `검증` 섹션

- 빌드·타입체크 결과
- QA PASS/FAIL 수, **수동 QA 항목은 개수가 아니라 제목을 전부 나열한다**
- **테섭 배포**: `<배포 URL> · READY` (또는 `ERROR — <사유>` / `건너뜀 — develop 없음` / `확인 실패 — <시도한 것>`)
- **AI가 정한 것 n건** — 되돌리는 비용 `높음` 항목은 제목을 전부 나열한다. 리뷰어(=본인)가 먼저 봐야 할 목록이다
- `원장 검사·리뷰어: 해당 없음 (개인 프로젝트 — gs 파이프라인)` 한 줄. **없는 검증을 한 것처럼 적지 않는다.**

**시크릿 값을 PR 본문에 적지 않는다.** 환경변수는 키 이름까지다.

## 마무리 — 개인 작업 페이지 갱신

`notion-home` MCP(`API-patch-page`, `API-patch-block-children`)로:

- `## TDL` 전부 체크. 속성 `TODO`는 비움
- `## 해결한 문제`는 여기서 채우지 않는다 — 마지막 출력 뒤 ④에서 승인받은 기록만 채운다
- `## 루프 로그`에 구현 요약(FE/BE 항목 수·커밋 수)과 QA 결과 한 줄
- `## 논의 필요`에 루프 중 쌓인 항목 — `[AI 자동 결정]`으로 정한 것 전부, 되돌리는 비용 순
- 속성 `PR`에 PR URL, `메모 / 일정`에 사람 몫(`수동 QA n건 · AI가 정한 것 m건 검토`). **`상태`는 건드리지 않는다** — 사람이 바꾼다
- 속성 `블로그 소재`는 **`/gs:blog-material --work-card <페이지 URL>`을 호출해 채운다.** 승인은 묻지 않는다

로컬 설계서면 같은 내용을 파일 하단 `## 루프 로그` 섹션으로 붙인다.

### 마지막 출력

한 문단 요약 뒤에 **수동 QA 목록을 붙인다.** 총평은 쓰지 않는다.

```
PR: <URL>                                ← 건너뛰었으면 "없음 · <이유>"
테섭 배포: <배포 URL> · READY            ← "ERROR — <사유>" / "건너뜀 (develop 없음)" / "확인 실패 — <시도한 것>"
머지: develop ← <브랜치>                 ← 건너뛰었으면 "건너뜀 (develop 없음)"
구현: FE n건 · BE n건 · 논의 필요 m건
QA: 자동 PASS n · FAIL n

AI가 정한 것 (n건 · 되돌리는 비용 순):   ← 없으면 "AI가 정한 것: 없음"
1. [높음] <무엇> — 채택: <값> · 근거: <…>
2. [중간] …                              ← 높음은 전부 편다. 나머지는 5건까지

자동 작성 문서 — 검토 권장:              ← 없으면 이 줄 생략
- docs/architecture.md

블로그 소재 (작업카드에 기록함):
1. <제목 후보> — <왜 쓸 만한가 한 줄>
2. …                                     ← 없으면 "없음" 한 줄

수동 QA (사람이 직접 봐야 하는 것):
1. <항목 제목> — <재현 방법 한 줄>
2. …
```

`/gs:pr`이 base 충돌을 해결했으면 해결한 파일을 수동 QA 맨 앞에 `충돌 해결: <파일> — <무엇을 합쳤나>`로 올린다. 그 코드는 셀프 QA를 다시 거치지 않고 타입체크·빌드만 통과해 올라갔다.

**수동 QA를 개수로만 보고하지 않는다.** 항목이 6건을 넘으면 앞의 5건만 펴고 나머지는 "그 외 n건 — QA 항목 DB 참조"로 접는다. 수동 항목이 없으면 `수동 QA: 없음` 한 줄.

**`AI가 정한 것`도 마찬가지다.** 루프가 아무것도 안 물은 대가로 사람은 이 목록 하나로 사후 검토를 한다. `높음`은 몇 건이든 전부 편다.

## ④ 문제 해결 기록 — 사람 승인

마지막 출력을 낸 **뒤에** `/gs:problem-log --work-card <페이지 URL>`을 호출한다. 이번 루프에서 원인을 찾느라 시간이 걸렸거나, 가설이 틀렸다가 뚫었거나, 우회만 하고 넘어간 문제가 없으면 호출하지 않고 `## 해결한 문제`에 "없음" 한 줄을 쓴다.

- **승인은 항상 받는다.** problem-log는 초안 전문을 보여주고 한 건씩 묻는다 — 규칙은 그 스킬이 갖는다. 일지는 틀린 원인이 조용히 쌓이면 안 되는 기록이라 자율 모드에서도 예외다.
- PR·배포·보고는 이미 끝났으므로 여기서 기다려도 파이프라인은 멈추지 않는다.
- 승인받아 만든 행만 `## 해결한 문제`에 페이지 mention으로 잇는다. 사람이 답하지 않았거나 거절한 건은 쓰지 않고 `## 해결한 문제`에 `기록 보류 n건` 한 줄만 남긴다.

## 정지 조건

멈출 때는 **어디서 왜 멈췄는지**와 상태 파일 경로를 남긴다. 재개는 같은 인자로 다시 호출하면 된다.

| | 조건 | 남기는 것 |
|---|---|---|
| B | 설계서 미확정 (§0-4) — 확정 도장 없음 · `TBD` 잔존 | 무엇이 걸렸는지. **`/gs:design <페이지 URL>`(또는 `/gs:discuss`) 먼저** |
| D | 타입체크·빌드 FAIL 2회 연속, 또는 QA FAIL 2회 연속 | 에러 로그 · FAIL 항목 |
| E | 노션 페이지 접근 실패 (개인 DB는 `notion-home`) | URL, 에러 |
| F | 대상 레포가 cashwalk 안 (§0-2) — 회사 작업 | 레포 경로와 `/nudge:implement-loop` 안내 한 줄 |

## 하지 않는 것

- 설계서를 바꾸지 않는다. 설계가 틀렸다고 판단되면 `논의 필요`에 적고 설계서대로 구현한다.
- **마지막 출력까지는 사람에게 아무것도 묻지 않는다.** `AskUserQuestion`을 부르지 않고, 하위 스킬(`/gs:implement`·`/gs:self-qa`)도 묻지 않는다. 예외는 마지막 출력 뒤의 ④ `/gs:problem-log` 승인 하나다 — PR까지 다 나간 뒤라 루프를 멈추지 않는다. 검토는 `/gs:design` ⑥(또는 `/gs:discuss` 확정)에서 끝났고, 사후 검토는 마지막 보고의 `AI가 정한 것`으로 한다.
- 권한·시크릿이 필요하다고 사람에게 되묻지 않는다. `vercel`·`aside-browser`·`notion-home` MCP로 직접 뚫고, 막히면 그 항목만 건너뛰고 보고한다.
- 배포가 실패했다고 PR을 감추지 않는다. 올리고 사유를 적는다.
- 구현을 직접 하지 않는다. 에이전트 라우팅·커밋 단위·아키텍처 문서 규칙은 `/gs:implement`가 SSOT다. 여기에 다시 적으면 두 경로가 갈라진다.
- develop 브랜치를 만들지 않는다. 없으면 머지를 건너뛴다.
- main에 직접 push하지 않는다. PR까지다. 머지(=배포 트리거)는 사람이 한다.

## 왜 이렇게 나눴나

- **①을 `/gs:implement` 호출로 뺀 이유** — 구현은 루프를 거치지 않고도 자주 필요하다("이것만 고쳐줘"). 규칙이 루프 안에만 있으면 그런 요청은 브랜치·TDL·논의 필요 기록 없이 처리되고, 나중에 무엇을 왜 고쳤는지가 남지 않는다. 원본을 밖에 두면 두 경로가 같은 규칙으로 돈다.
- **머지를 QA와 PR 사이에 둔 이유** — 통합 브랜치에는 검증을 통과한 것만 들어가야 한다. QA 앞에 두면 깨진 코드 위에 다음 작업이 쌓이고, PR 뒤에 두면 리뷰 전에 이미 합쳐져 PR이 사후 보고가 된다.
- **품질 판정 구간을 아예 안 만든 이유** — 회사판의 원장·리뷰어·반려자는 "사람 리뷰 지적의 재발 방지"가 목적이다. 개인 프로젝트에는 그 지적의 출처가 없고, 코드 퀄리티보다 완성까지의 속도가 축이다. AI 리뷰로 원장을 채우는 변형도 가능했지만, 그건 "사람이 실제로 지적한 것"이라는 원장의 정체성을 깨므로 하지 않았다.
- **배포 단계가 없는 이유** — 개인 프로젝트의 배포는 main 머지에 물린 자동 배포가 대부분이다. PR 머지가 곧 배포 결정이고, 그 결정은 사람의 최종 검토 자리에 이미 있다. ③의 `md`는 배포가 아니라 통합이다.
- **마지막 출력까지 묻는 자리를 0으로 만든 이유** — 예전에는 세 곳(막힌 지점 · PR 직전 · 일지 승인)에서 물었다. 일지 승인만은 남겼지만 PR·보고까지 다 낸 뒤인 ④로 옮겨 루프를 멈추지 않게 했다. 각각은 타당했지만, 셋을 합치면 루프 한 번에 사람이 서너 번 불려 나오고 그때마다 루프가 멈춰 선다. 개인 프로젝트에서 그 대기 시간이 잘못된 자동 결정을 되돌리는 비용보다 컸다. 그래서 판단을 없앤 게 아니라 **시점을 옮겼다** — 사전 검토는 `/gs:design` ⑥ 또는 `/gs:discuss` 확정 한 곳, 사후 검토는 마지막 보고의 `AI가 정한 것` 한 곳.
- **배포 확인을 MCP로 직접 하게 한 이유** — "배포됐는지 확인해 주세요"는 질문 중에서도 가장 아까운 종류다. 사람이 대시보드를 열어 읽고 답하는 일을 `vercel` MCP가 그대로 할 수 있고, 안 되면 `aside-browser`가 사람의 로그인 세션으로 같은 화면을 본다. 권한이 필요하다는 사실이 사람을 부르는 이유가 되지 않게 했다.
- **`AI가 정한 것`을 PR 본문에까지 넣은 이유** — 최종 보고는 터미널 스크롤에 묻히지만 PR은 남는다. 나중에 "왜 이렇게 짰지"를 되짚을 때 그 목록이 커밋 옆에 있어야 한다.
