# /gs:implement — 브랜치 → 구현 → 논의 필요 확인

구현이 본체다. 브랜치를 잡고, 설계서에서 TDL을 뽑고, **FE/BE 에이전트에 위임해** 커밋을 쌓는다.

**이 스킬은 사람에게 묻지 않는다.** 단, 노션 URL 없이 시작했는데 orca 메모에 작업카드가 없으면 카드를 새로 만들지 한 번 묻는다(§0-1). 그 밖에 판단이 갈리는 자리는 가장 보수적인 쪽을 고르고 `논의 필요`에 `[AI 자동 결정]`으로 남긴다 — 규약은 [autonomy.md](../../autonomy.md)가 SSOT다. 사람의 검토 자리는 `/gs:design` ⑥(또는 `/gs:discuss` 확정) 하나이고, 여기서 다시 부르면 그 승인이 무의미해진다.

**구현 규칙의 원본이 이 파일이다.** [/gs:implement-loop](../implement-loop/SKILL.md)는 ①을 이 스킬 호출로 대신하고, 그 뒤에 셀프 QA·머지·PR·일지 기록을 붙인다. 두 곳에 적으면 에이전트 라우팅과 커밋 단위가 따로 자라 같은 설계서가 호출 경로에 따라 다르게 구현된다.

단독으로 부르면 **셀프 QA·블로그 소재는 하지 않는다.** problem-log 점검은 마지막 출력 뒤에 한다(④). 노션 `상태`는 단독이든 루프든 바꾸지 않는다. 다만 구현을 끝낸 뒤 **develop 머지(`md`)와 `/gs:pr`은 한다** — 만들어 놓고 올리지 않으면 작업이 로컬에 고이고, 다음 작업이 그 위에 쌓여 무엇이 어디까지 올라갔는지 사람이 추적하게 된다.

```
/gs:design · /gs:discuss ─→ 설계서 + 확정 도장   (단독 호출이면 도장을 요구하지 않는다)
   │
   ▼
§0 브랜치 · 스캐폴딩 · 아키텍처 문서 · TDL
① 구현      TDL의 [BE] → Agent: gs:backend-dev
            TDL의 [FE] → Agent: gs:frontend-dev
            [공통]     → 메인 컨텍스트
            ───────────── 에이전트가 "막힌 지점"을 반환하면 보수적으로 정하고 기록
   │
   ├───────────── 쌓인 `논의 필요`를 코드에 반영 (묻지 않는다)
   ▼
② md       develop(없으면 dev)에 머지 — 브랜치가 없으면 건너뛴다
③ PR       /gs:pr
   ▼
종료 — 단독 호출이면 여기까지. --from-loop면 ①과 논의 필요 반영까지만 하고 loop로 돌아간다
```

| | 단독 호출 | implement-loop가 호출 (`--from-loop`) |
|---|---|---|
| 입력 | 노션 페이지 · 설계서.md · 자유 지시 | 확정 도장 찍힌 노션 페이지 (loop §0이 확인) |
| §0-2 cashwalk 확인 | 여기서 한다 | loop §0이 이미 했으므로 건너뛴다 |
| §0-5 애매한 지점 | 보수적으로 정하고 기록 | 도장이 찍혔으면 걸리는 게 없어야 정상. 걸리면 똑같이 정하고 기록 |
| 종료 | 노션 갱신 + 마지막 출력 | 상태 파일만 갱신하고 loop로 돌아간다 |
| ② md · ③ PR | 여기서 한다 | **하지 않는다.** loop가 QA 뒤에 한다 |
| QA · 블로그 소재 | 하지 않는다 | loop ②~마무리가 한다 |
| ④ problem-log 점검 | 마지막 출력 뒤에 한다 | 하지 않는다. loop ④가 한다 |

## 노션 접근

개인 업무 로그 페이지를 읽고 쓴다. **식별자·속성·본문 골격은 [notion-databases.md](../../notion-databases.md#개인-업무-로그)를 따른다.** `notion-home` MCP로만 접근한다.

**본문은 `# AI 작성` 아래만 고친다.** `# 인간 작성` 아래는 읽기만 하고, 섹션도 그 H1 아래에서 찾는다 — [AI 작성 경계](../../notion-databases.md#ai-작성-경계).

## §0. 시작 전 확인

1. **인자 파싱.** `--from-loop`를 떼어낸다. 남은 인자로 모드를 정한다.

   | 모드 | 판별 | 스펙 출처 |
   |---|---|---|
   | 노션 | `notion.com/…` URL | 페이지 `# AI 작성`의 `## 설계서`·`## 디자인`·`## TDL` + `# 인간 작성` |
   | 파일 | 남은 인자 **전체가** 존재하는 `.md` 파일 경로 하나 | 파일 전체 |
   | 지시 | 그 외 전부 | 지시문 |

   파일 모드를 좁게 잡는 이유: `src/app/page.tsx 에 버튼 추가해줘`처럼 경로로 시작하는 지시가 파일 모드로 잡히면 소스 파일이 설계서가 되고, 종료 때 그 파일에 `## 루프 로그`가 붙는다.

   - 인자 없음 → 무엇을 구현할지 요구하고 멈춘다. 이건 질문이 아니라 입력 누락이다.
   - 노션 URL을 확보했으면 **[orca-worktree.md](../../orca-worktree.md)의 절차대로 현재 워크스페이스 메모에 기록한다.** 실패해도 멈추지 않는다.
   - 파일·지시 모드이고 `--from-loop`가 아니면 **[orca-worktree.md의 카드 없음 확인](../../orca-worktree.md#카드-없음-확인)을 수행한다.** 메모에 작업카드가 없으면 새 카드를 만들지 사람에게 묻는다 — 이 스킬이 사람에게 묻는 유일한 자리다. 카드를 만들었으면 노션 모드로 넘어가 이후 §0-4를 진행한다.

2. **범위 확인 — cashwalk 안이면 시작하지 않는다.** 대상 레포는 현재 작업 디렉터리의 git 루트다. 정할 수 없으면 노션 페이지 속성 `프로젝트`로 [레포 경로 ↔ 프로젝트](../../notion-databases.md#레포-경로--프로젝트)를 역인용하고, 그래도 안 되면 정지 조건 G로 멈춘다(묻지 않는다 — 어느 레포인지 모르는 채로 코드를 쓰는 것보다 멈추는 쪽이 싸다). 경로가 `레포지토리/cashwalk/` 아래면 한 줄 남기고 멈춘다(정지 조건 G): `회사 작업은 /nudge:implement 로 돌리세요. 이 플러그인은 개인 프로젝트 전용이라 원장 검사·리뷰어가 없습니다.` 회사 코드를 품질 판정 없이 PR 경로로 보내는 사고를 막는 가드레일이다. `--from-loop`면 loop §0-2가 이미 했으므로 건너뛴다.

3. **워킹트리 확인 — 묻지 않고 stash한다.** `git status --porcelain`에 미커밋 변경이 있으면 `git stash push -u -m "gs-implement 자동 stash <시각>"`으로 치우고, 상태 파일 `stash`에 그 메시지를 적는다. 마지막 출력에 `자동 stash: <메시지> — git stash list 로 확인` 한 줄을 남긴다.

   구현 에이전트는 자기가 만든 파일만 스테이징하지만, 사람의 미커밋 변경이 섞이면 어느 커밋이 이번 작업인지 나중에 가려낼 수 없다. stash는 되돌릴 수 있으므로 묻지 않고 한다 — **자동으로 pop하지는 않는다.** 언제 되살릴지는 사람이 정한다.

4. **스펙 읽기.**
   - 노션: `API-retrieve-page-markdown`으로 `## 설계서`·`## 디자인`·`## TDL`·`## 논의 필요`를 확보한다. 속성 `ID`(`DB-123`)는 `API-retrieve-a-page`로 따로 읽는다(마지막 출력과 뒤이은 PR에 쓴다).
   - 모든 모드: 스펙에 **변경 지점(file:line)**이 없으면 레포를 탐색해 직접 짚는다. 도장을 요구하지 않으므로 `## 설계서`가 씨앗(한 줄 목표·범위 밖)뿐일 수 있다. **레포를 읽어 알 수 있는 것은 묻지 않는다.**

5. **애매한 지점 해소 — 묻지 않고 정한다.** 아래가 걸리면 [autonomy.md의 자동 결정](../../autonomy.md#자동-결정--묻지-않는-대신-남긴다) 순서대로 처리한다: 조사 → 안 나오면 가장 보수적인 선택 → `논의 필요`에 `[AI 자동 결정]` 기록.
   - `## 논의 필요`에 코드를 바꾸는 미결 항목이 남았다 (노션)
   - 스펙에 `TBD`/`미정`/`확인 필요`가 남았다 (노션·파일)
   - 동작이 둘 이상으로 갈린다 — 어느 화면인지, 빈 상태를 어떻게 보일지, 기존 동작을 바꾸는지 더하는지 (지시)

   **여기서 "보수적"은 기존 동작을 덜 바꾸는 쪽이다.** 기능을 더하는 것과 기존 동작을 바꾸는 것 사이에서 갈리면 더하는 쪽을 고른다 — 되돌리는 비용이 작다.

   도장을 요구하지 않는 이유: 막아야 하는 것은 "도장 없음"이 아니라 "판단이 안 서는 지점이 남음"이고, 그건 여기서 정하고 기록하는 것으로 대신한다. 확정 도장은 `/gs:design` ⑥(또는 `/gs:discuss` 확정)이 사람의 검토를 받은 표시이지, 구현 자체의 전제는 아니다.

6. **브랜치.** 작업용 feature 브랜치 위면 그대로 쓴다. 기본 브랜치(main) 위면 `feature/<작업명>`을 만들어 옮긴다. 브랜치가 정해지면 `base_sha = git rev-parse HEAD`를 기록한다 — 이번 호출이 쌓은 커밋의 경계이고, 마지막 출력과 뒤이은 QA·PR이 이 sha를 기준으로 본다.

7. **신규 프로젝트면 스캐폴딩 먼저.** 설계서의 스캐폴딩 계획대로 레포·초기 구조를 만들고 **첫 커밋을 따로 남긴다**(`chore: 프로젝트 스캐폴딩`). 노션 `## 기획서` 아래에 `### 프로젝트 정체`가 붙어 있으면(신규라 `/gs:idea`가 파일로 못 쓴 경우) 그 내용을 **그대로** `<레포>/docs/project-identity.md`로 옮긴다 — `/gs:idea`가 자동 작성했더라도 설계 확정 때 사람이 설계 설명과 함께 봤으므로 다시 묻지 않는다. 손대지 않고 옮긴다.

8. **아키텍처 문서 확인.** `<레포>/docs/architecture.md`를 읽는다. 있고 내용이 차 있으면 9로 간다. **없거나 `TBD`뿐이면 여기서 채운다** — 이게 없으면 FE·BE 에이전트가 각자 다른 스택 취향으로 코드를 쌓고, 그 어긋남은 PR 직전에야 드러난다.

   1. **먼저 레포에서 읽는다.** `package.json`·프레임워크 설정 파일·기존 폴더 구조로 [아키텍처 골격](../../project-docs.md#골격--아키텍처)을 최대한 채운다.
   2. 읽어서 알 수 없는 항목은 **묻지 않고 채운다.** [인터뷰 질문](../../project-docs.md#인터뷰-질문--아키텍처)의 답을 `docs/project-identity.md` → 설계서 → 프레임워크의 관례적 기본값 순서로 찾는다. 그래도 안 나오면 `추정: <내용>`으로 표시한다.
   3. 승인 없이 `<레포>/docs/architecture.md`에 쓴다. **해당 없는 섹션은 지운다**(백엔드 없는 프로젝트 등) — 빈 섹션은 에이전트에게 "미정"으로 읽힌다.
   4. `추정:` 항목을 `논의 필요`에 `[AI 자동 결정]`으로 남기고, 파일 경로를 마지막 출력의 `자동 작성 문서 — 검토 권장`에 올린다. **이 문서는 다음 회차부터 FE·BE 에이전트의 규범이 되므로 반드시 노출한다.**

   문서를 쓴 커밋은 구현 커밋과 섞지 않고 `docs: 아키텍처 문서 추가`로 따로 남긴다. 이 단계는 문서가 없는 첫 회에만 일어난다.

9. **TDL.** 작업 단위 = 커밋 단위. 5를 통과했으면 판단 여지가 없으므로 사람 확인 없이 만든다.
   - **각 항목에 `[FE]`/`[BE]`/`[공통]` 태그를 단다** — 설계서 변경 지점의 태그를 그대로 옮긴다. 이 태그가 ①의 에이전트 라우팅 키다.
   - 노션: `## TDL`이 비어 있으면 설계서에서 뽑아 페이지에 채운다. 파일·지시: 상태 파일 `tdl`에 넣는다.
   - QA 체크리스트는 뽑지 않는다(implement-loop §0의 몫).

10. **상태 파일.** 대상 레포 `.omc/state/gs-implement.json`:
    ```json
    {
      "input": "<URL · 경로 · 지시문>", "mode": "notion|file|prompt",
      "branch": "<작업 브랜치>", "base_sha": "<sha>", "stash": null,
      "tdl": [ { "title": "…", "tag": "FE|BE|공통", "done": false, "commit": null } ],
      "merge": null, "pr": null,
      "open_questions": [], "blocked": []
    }
    ```

    **재개 키는 `branch`다.** 현재 브랜치와 같은 `branch`의 상태 파일이 있으면 저장된 `base_sha`로 이어서 돈다(`tdl`의 `done:false`부터). 입력이 달라 보여도 **묻지 않고 이어간다** — 지시문은 매번 다르게 쳐지기 마련이라 입력으로 대조하지 않는다. 이어간 사실을 마지막 출력에 한 줄 남긴다. 다른 브랜치의 상태 파일이면 덮어쓴다.

## ① 구현 — FE/BE 에이전트 위임

**순서 규칙 — BE가 FE보다 먼저다.** FE는 API 계약 위에 쌓이므로, `[BE]` 항목을 먼저 `gs:backend-dev`에 보내고, 반환된 `API 계약`을 `[FE]` 항목의 프롬프트에 넣어 `gs:frontend-dev`에 보낸다. 서로 의존이 없는 항목 묶음이면 두 에이전트를 **병렬로** 띄운다. `[공통]`(설정·타입 공유 등)은 메인 컨텍스트가 직접 한다.

에이전트 프롬프트에는 **설계서·디자인 명세·맡길 TDL 항목·레포 경로·브랜치만** 넣는다. 대화 이력은 넣지 않는다 — 구현 중의 시행착오가 따라 들어가면 에이전트가 이미 버린 방향을 다시 시도한다. 아키텍처 문서도 옮겨 담지 않는다. 에이전트가 레포에서 자기 섹션만 직접 읽는다(FE는 `## 공통`+`## 프론트엔드`, BE는 `## 공통`+`## 백엔드`).

- 항목마다 커밋한다. `/gs:commit`의 규칙(명시적 `git add <files>`, 레포 커밋 스타일, co-author·생성 표식 금지)을 따른다. 커밋 뒤 `tdl[].done`·`commit`을 갱신한다.
- 전역 프론트엔드 컨벤션(`${CLAUDE_PLUGIN_ROOT}/references/frontend-typescript-convention.md`)을 구현하면서 지킨다.
- 항목마다 타입체크를 돌린다. 깨진 채로 다음 항목에 쌓지 않는다. 에이전트 보고의 `검증`이 FAIL이면 그 에이전트에게 고치게 하고, **2회 연속 FAIL이면 정지 조건 D**다.
- 에이전트가 `막힌 지점`을 반환하면 **묻지 않고 정한다.** 설계서·디자인 명세·아키텍처 문서·레포를 다시 뒤져 답을 찾고, 없으면 가장 보수적인 선택(기존 동작을 덜 바꾸는 쪽 · 범위를 덜 넓히는 쪽)을 한다. 정한 것을 프롬프트에 넣어 해당 에이전트를 다시 띄우고, `논의 필요`에 `[AI 자동 결정]`으로 "무엇이 막혔고 무엇으로 정했는지 · 되돌리는 비용"을 적는다.
  - **되돌리는 비용이 `높음`인 것**(데이터 모델 · 인증 방식 · 모듈 경계 · 외부 서비스)은 정하되, 마지막 출력의 `AI가 정한 것`에서 접지 않고 전부 편다. 사람이 PR을 보기 전에 그 목록부터 읽게 된다.
  - 권한·시크릿 때문에 막힌 것이면 [autonomy.md의 §권한·시크릿](../../autonomy.md#권한시크릿이-필요할-때--묻지-말고-직접-한다)대로 MCP로 직접 뚫는다. 사람에게 되묻지 않는다.
- 에이전트 보고의 `코드와 어긋난 지점`이 채워져 있으면 **코드를 고치지 말고** `논의 필요`로 옮긴다. 문서가 낡은 것인지 코드가 잘못 간 것인지는 사람이 판단할 일이다.
- 노션 모드면 항목마다 `## TDL` 체크박스와 속성 `TODO`(`남은 n건: …`)를 갱신한다(`API-patch-page`).
- **스펙이 틀렸다고 판단돼도 스펙을 고치지 않는다.** `논의 필요`에 적고 스펙대로 구현한다.

`논의 필요`를 쓰는 곳은 모드에 따라 다르다 — 노션 모드는 페이지 `## 논의 필요` 섹션, 파일·지시 모드는 상태 파일 `open_questions`.

### 작업 범위가 늘어났을 때

도중이나 끝난 뒤에 **기능 추가·버그 수정을 더 요청받으면**, 코드만 고치고 끝내지 않는다. 기록을 실제 작업 범위에 맞춘다. 설계서 누적은 "스펙을 고치지 않는다"의 유일한 예외다(지우지 않고 덧붙이기만).

1. 노션: `## 설계서`(기획 층위면 `## 기획서`)에 추가 요구를 **누적**해 덧붙인다. 무엇이 언제 늘었는지가 나중에 회고 재료다. 파일·지시: 상태 파일 `tdl`에 추가만 한다.
2. `## TDL`에 태그 달린 항목을 추가한다. 이미 체크된 항목은 건드리지 않는다.
3. 추가분을 ①과 같은 라우팅으로 구현한다.
4. 노션: **`이름`(title)을 늘어난 범위에 맞게 고친다.** 추가분이 원래 작업의 연장이면 그대로 두고, 성격이 다른 것이 하나 붙었으면 `원래 제목 + 추가분`, 셋 이상으로 불어났으면 묶는 상위 개념으로 다시 짓는다.
5. `논의 필요`에 "무엇이 언제 추가 요청됐는지"를 한 줄 남긴다.

## 논의 필요 반영 — 종료 앞

`논의 필요`에 쌓인 것을 **문서에만 적고 넘어가지 않는다.** 코드가 굳기 전인 여기서 반영한다. 다만 **묻지 않는다** — 사람의 검토 자리는 `/gs:design` ⑥(또는 `/gs:discuss` 확정)이었고, 여기서 다시 부르면 그 승인이 무의미해진다.

- 구현 중 이미 `[AI 자동 결정]`으로 정해진 항목은 그대로 둔다.
- 남은 것 중 **결정이 코드를 바꾸는 것**만 반영한다. 보수적 선택 + `[AI 자동 결정]` 기록. 단순 기록용 항목은 문서에만 남긴다.
- 고쳤으면 그 항목도 커밋하고 타입체크를 다시 돌린다.
- 반영할 것이 하나도 없으면 아무것도 하지 않는다. 이 자리는 **있으면 처리하는 곳**이지 매번 거치는 관문이 아니다.

## 종료 — 기록 갱신

노션 모드면 `notion-home`으로:
- `## TDL` 전부 체크, 속성 `TODO` 비움. **`상태`는 건드리지 않는다**(`진행 중` 유지)
- `## 루프 로그`에 구현 요약(FE n건 · BE n건 · 공통 n건 · 커밋 n개). 단독 호출이면 `QA·PR 미실행 (/gs:implement)` 한 줄을 더한다
- `## 논의 필요`에 구현 중 쌓인 `[AI 자동 결정]` 전부와 §논의 필요 반영에서 정한 것

파일 모드면 같은 내용을 설계서 파일 하단 `## 루프 로그`로 붙인다. 지시 모드는 상태 파일과 아래 출력으로 끝낸다.

**`--from-loop`면 여기서 implement-loop로 돌아간다.** 아래 ②·③과 마지막 출력은 하지 않는다 — loop가 상태 파일을 읽어 QA부터 잇고, 머지·PR은 QA를 통과한 뒤에 해야 한다.

## ② md — 테섭 배포 (develop 머지 · 조건부)

**개인 프로젝트에서 develop 머지가 곧 테섭 배포다** — develop push에 자동 배포(Vercel 등)가 물려 있다. `git branch --list develop dev`로 확인한다.

- **있으면** [`/common:md`](../../../common/skills/md/SKILL.md)를 실행한다(현재 브랜치를 develop에 `--no-ff` 머지 → push → 원래 브랜치 복귀). 결과를 상태 파일 `merge`에 적는다.
- **없으면 건너뛴다.** `merge: "skipped: develop 없음"`을 적고 마지막 출력에 한 줄 남긴다 — 개인 레포는 main 단일 브랜치인 경우가 많고, 없는 브랜치를 만들어내는 건 이 스킬이 정할 일이 아니다.
- 스크립트가 `이미 develop 브랜치입니다` 같은 메시지로 끝나면 **그대로 전달하고 우회하지 않는다.** origin에 push하는 되돌리기 어려운 작업이라, 예상과 다른 상태에서 밀어붙이지 않는다.

## ③ PR

`/gs:pr`을 실행한다. base는 main(기본 브랜치), draft 아님 — 규칙은 그 스킬이 SSOT다.

노션 모드면 제목 접두사로 속성 `ID`를 넘긴다.

```
[DB-<ID>] <타입>: <요약>        예) [DB-207] feat: 메모 검색 추가
```

`ID`는 값 자체가 `DB-123` 형태다. **`DB-`를 두 번 붙이지 않는다.** 파일·지시 모드는 접두사 없음 — 붙일 카드가 없는데 억지로 만들지 않는다.

PR URL을 상태 파일 `pr`에 적고, 노션 모드면 속성 `PR`에도 적는다.

이미 이 브랜치로 열린 PR이 있으면 새로 만들지 않는다. `/gs:pr`이 push까지 하므로 커밋이 그 PR에 붙는다.

## 마지막 출력 (단독 호출)

총평 없이 아래 형식만.

```
브랜치: <작업 브랜치> · 커밋 n개
구현: FE n건 · BE n건 · 공통 n건
테섭 배포: develop ← <브랜치>     ← 건너뛰었으면 "건너뜀 (develop 없음)"
PR: <URL>
자동 stash: <메시지>              ← 없었으면 이 줄 생략

커밋:
- <hash> <메시지>

AI가 정한 것 (n건):               ← 없으면 "AI가 정한 것: 없음"
1. [높음] <무엇> — 채택: <값> · 근거: <…>
2. [중간] …                        ← 높음은 전부. 나머지는 5건까지

자동 작성 문서 — 검토 권장:       ← 없으면 이 줄 생략
- docs/architecture.md

논의 필요 (남은 것):          ← 없으면 "논의 필요: 없음"
1. <항목> — <왜 남았는지>

다음 단계:
- 동작 확인: /gs:self-qa <페이지 URL | 설계서> --checklist-only 후 --run
```

## ④ 문제 해결 기록 점검 (단독 호출)

마지막 출력을 낸 **뒤에** [`/gs:problem-log`의 작업 스킬 끝 점검](../problem-log/SKILL.md#작업-스킬-끝의-점검)을 **반드시** 한다. 에이전트가 반환한 막힌 지점, 2회 이상 재시도한 빌드·타입체크, `/gs:pr` 충돌 해결까지 이번 호출에서 일어난 일을 전부 훑는다. 후보가 있으면 `/gs:problem-log --work-card <페이지 URL>`로 승인을 묻고, 없으면 `문제 해결 기록: 없음` 한 줄. PR까지 이미 나갔으므로 여기서 기다려도 작업은 멈추지 않는다.

`--from-loop`면 하지 않는다 — loop ④가 루프 전체를 모아 한 번에 한다.

## 정지 조건

멈출 때는 어디서 왜 멈췄는지와 상태 파일 경로를 남긴다. 같은 브랜치에서 다시 호출하면 이어서 돈다. 번호는 implement-loop와 맞췄다(B·F는 도장·범위 조건이라 loop에도 있다). **implement-loop가 부른 경우 loop도 같은 문자로 멈춘다.**

| | 조건 | 남기는 것 |
|---|---|---|
| D | ①에서, 또는 ③ `/gs:pr`의 충돌 해결에서 타입체크·빌드 2회 연속 실패 | 에러 로그, 어느 TDL 항목(또는 충돌 파일)에서인지 |
| E | 노션 페이지 접근 실패 (개인 DB는 `notion-home`) | URL, 에러 |
| G | 대상 레포가 cashwalk 안 (§0-2) — 회사 작업 | 레포 경로와 `/nudge:implement` 안내 한 줄 |

## 하지 않는 것

- 스펙(설계서)을 바꾸지 않는다. 틀렸다고 판단되면 `논의 필요`에 적고 스펙대로 구현한다. 범위가 늘어난 경우의 누적만 예외다.
- 셀프 QA·블로그 소재를 하지 않는다. implement-loop ②~마무리의 몫이다. problem-log 점검은 단독 호출이면 ④에서 한다.
- 노션 `상태`는 어떤 경우에도 바꾸지 않는다. implement-loop도 마찬가지다 — 사람과 notion-orca 러너가 관리한다.
- `--from-loop`면 ②·③(머지·PR)을 하지 않는다. QA를 통과하지 않은 코드를 develop에 올리지 않기 위해서다.
- develop 브랜치를 만들지 않는다. 없으면 머지를 건너뛴다.
- `gh pr create`를 직접 부르지 않는다. PR은 `/gs:pr`을 통해서만 만든다.
- FE 에이전트에 BE 항목을, BE 에이전트에 FE 항목을 보내지 않는다. 경계가 애매한 항목은 `[공통]`으로 메인이 한다.
- 아키텍처 문서를 **에이전트에게 쓰게 하지 않는다.** 구현 에이전트가 자기 취향대로 쓴 문서는 다음 회차에 그 취향을 규범으로 되돌려준다. 메인 컨텍스트가 레포를 읽어 쓰고, 추정한 항목을 반드시 노출한다.
- 기본 브랜치(main)에 직접 push하지 않는다.
- **`AskUserQuestion`을 부르지 않는다.** 이 스킬에는 사람에게 묻는 자리가 없다. 갈리는 것은 보수적으로 정하고 `[AI 자동 결정]`으로 남긴다.
- 자동 stash를 자동으로 pop하지 않는다. 되살리는 시점은 사람이 정한다.
- 정한 것을 마지막 출력에서 빠뜨리지 않는다. 안 물어본 대신 사후에 검토할 수 있어야 한다.

## 왜 이렇게 나눴나

- **구현 규칙의 원본을 여기 두는 이유** — implement-loop의 ①이 곧 이 스킬이다. 두 곳에 적으면 에이전트 라우팅·커밋 단위·막힌 지점 처리가 따로 자라, 같은 설계서가 호출 경로에 따라 다르게 구현된다. loop는 이 스킬을 부르기만 한다.
- **단독 호출에서도 머지·PR까지 미는 이유** — 구현만 하고 멈추면 작업이 로컬 브랜치에 고이고, 다음 작업이 그 위에 쌓인다. 그러면 PR 하나가 여러 작업을 담게 되고 리뷰도 되돌리기도 어려워진다. 끝을 스킬이 책임지면 "올리는 걸 깜빡함"이라는 실패 모드가 사라진다.
- **`--from-loop`일 때 머지·PR을 빼는 이유** — loop는 뒤에 셀프 QA가 있다. 여기서 먼저 올리면 QA FAIL을 고친 커밋이 PR 뒤에 따라붙거나, 깨진 코드가 develop에 들어간다. 검증 뒤에 올리는 순서는 loop가 지킨다.
- **develop이 없으면 건너뛰는 이유** — 개인 레포는 main 단일 브랜치인 경우가 많다. 없는 브랜치를 스킬이 만들어내면 그 레포의 브랜치 전략을 스킬이 정하는 셈이 된다.
- **자유 지시까지 받는 이유** — 개인 프로젝트의 상당수 작업은 설계서를 만들 만큼 크지 않다. 그런 요청을 스킬 밖에서 처리하면 브랜치·TDL·커밋 단위·논의 필요 기록이 전부 빠지고, 나중에 무엇을 왜 고쳤는지가 남지 않는다. 도장을 요구하지 않는 대신 §0-5에서 애매한 지점을 막는다.
- **확정 도장을 요구하지 않는 이유** — 도장은 "QA·PR까지 사람 개입 없이 밀어도 되는가"의 조건이지 구현의 전제가 아니다. 구현이 막아야 하는 것은 판단이 안 서는 지점이고, 그건 §0-5가 정하고 기록하는 것으로 대신한다.
- **막힌 지점에서 안 묻게 바꾼 이유** — 예전에는 "잘못 찍으면 구현이 통째로 버려지니 미루는 비용이 더 크다"는 이유로 즉시 물었다. 맞는 말이지만, 실제로는 사람이 자리를 비운 사이 루프가 멈춰 서 있는 시간이 재작업 비용보다 컸다. 그래서 **보수적 선택 + 전부 기록**으로 바꾸고, 되돌리는 비용이 큰 결정은 마지막 출력 맨 위에 펴서 PR을 보기 전에 읽히게 했다. 버려지는 구현은 줄지 않지만, 멈춰 있는 시간이 사라진다.
- **시작 Draft PR을 만들지 않는 이유** — 회사판은 진행 상황을 PR로 공유하지만, 개인 프로젝트에는 그 PR을 볼 사람이 없다. `/gs:pr`도 draft를 만들지 않는 정책이라 진행 중 PR이라는 상태 자체가 없다.
- **BE→FE 순서를 강제하는 이유** — 혼자 만들면 한 컨텍스트가 프론트와 백엔드를 오가며 짜기 쉽고, 그러면 API 계약이 "구현하다 보니 이렇게 된" 형태로 굳는다. BE가 계약을 먼저 고정하면 그 계약이 설계서에 남고 재작업이 줄어든다.
