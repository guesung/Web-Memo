# /gs:study — 내가 세팅한 것을 내 자료로 다시 배운다

일반론 강의가 아니라 **내가 실제로 한 작업을 이해하는 것**이 목표다. 설명은 카드·위키·코드에 적힌 사실로 채우고, 개념은 그 사실을 읽는 데 필요할 때만 항목 안에서 한두 줄로 푼다.

**쓰기 없음.** 노션과 레포는 읽기만 한다. 결과는 대화창에만 낸다.

## 입력

학습 키워드 하나(`/gs:study GA`). 없으면 묻는다.

탐색 대상은 **개인 업무 로그**(작업 카드)와 **개발 위키 DB** 두 곳 고정이다. ID는 [notion-databases.md](../../notion-databases.md)에서 읽는다 — 스킬 본문에 두지 않는다.

## ① 후보 찾기

**시작 전에 [notion-databases.md](../../notion-databases.md)를 읽는다.** 개인 워크스페이스라 `notion-home` MCP로만 연다(`claude.ai Notion`으로 열면 404).

**키워드 변형**을 먼저 정한다. 약어·영문·한글 표기가 갈릴 만한 것은 함께 찾는다(예: `GA` → `GA` · `Google Analytics` · `구글 애널리틱스` · `gtag`). 변형은 3~4개까지.

변형마다 아래를 조회하고 결과를 합쳐 중복을 제거한다.

1. **개인 업무 로그** — `API-query-data-source`, `이름` contains 변형
2. **개발 위키 DB** — `API-query-data-source`, `Name` contains 변형 `or` `요약` contains 변형
3. **본문 검색 보완** — 속성 필터는 제목·요약만 본다. `API-post-search`로 변형을 한 번 더 검색해, 부모가 위 두 DB인 페이지만 추가한다.
4. **연결 문서** — 1에서 찾은 카드의 `이름`으로 개발 위키 DB의 `메모` contains 를 조회해, 그 카드에 딸린 위키 문서도 후보에 넣는다(카드 멘션은 plain text가 카드 제목이라 이걸로 잡힌다).

속성명이 틀려 `validation_error`가 나면 `API-retrieve-a-data-source`로 실제 속성명을 대조하고 다시 조회한다. 한쪽 DB 조회가 실패해도 다른 쪽 결과로 진행하고, 실패를 후보 목록 아래에 밝힌다.

## ② 확인받기

후보를 번호 목록으로 보여주고 **답을 기다린다.** 고르기 전에 본문을 읽거나 설명을 시작하지 않는다.

```
'<키워드>' 관련 개발 기록 <n>건

작업 카드
1. [<이름>](<URL>) — <작업 시작 날짜> · <프로젝트>

개발 위키
2. [<Name>](<URL>) — <유형> · <작성일>   ← 연결 문서면 끝에 "(1번 카드)"
3. …

어떤 걸로 볼까요? 번호로 골라 주세요. 전부면 "전부".
```

- 각 묶음 안은 날짜 최신순. 묶음에 결과가 없으면 `없음` 한 줄.
- 후보가 20건을 넘으면 상위 20건만 보이고 "키워드를 좁혀 달라"는 한 줄을 붙인다.
- 후보가 하나도 없으면 시도한 변형을 보여주고 다른 키워드를 묻는다.

## ③ 자료 읽기

고른 것만 읽는다.

1. **작업 카드** — `API-retrieve-a-page`로 속성(`이름`·`프로젝트`·`PR`·`TODO`), `API-retrieve-page-markdown`으로 본문 전체. `# 인간 작성`·`# AI 작성` 양쪽 다 읽는다.
2. **위키 문서** — `API-retrieve-page-markdown`으로 본문, `유형` 속성도 함께 본다.
3. **레포 코드** — 고른 카드의 `프로젝트`를 [레포 경로 ↔ 프로젝트](../../notion-databases.md#레포-경로--프로젝트) 표로 역매핑해 레포가 정해지면, 키워드와 자료에 나온 식별자(환경변수명, 패키지명, 함수명 등)로 grep해 실제 세팅 코드를 찾는다. 카드에 PR이 연결돼 있으면 그 PR의 diff를 우선 근거로 본다(`gh pr view --json files` 등). 위키 문서만 골랐으면 `프로젝트` 속성으로 같은 매핑을 시도한다. 레포가 안 정해지면 건너뛰고 설명에서 "코드 근거 없음"이라고 밝힌다.

여러 개를 골랐으면 따로 설명하지 않고 **하나로 합쳐** ④를 쓴다.

## ④ 설명 — 대화창, 이 순서 고정

```
# <키워드>

## 가장 신경쓴 것
## 고민
## 트러블 슈팅
## 더 확장/수정한다면
```

모든 항목에서 문장마다 근거를 단다: 코드는 `파일:라인`, 노션은 페이지 링크. **자료에 없는 내용을 일반론으로 채워 "내가 한 것"처럼 쓰지 않는다** — 빈 곳은 `자료에 없음`으로 표시한다. 낯선 개념이 나오면 그 자리에서 한두 줄로 풀고 넘어간다.

**가장 신경쓴 것** — 이 작업에서 가장 공들인 지점 1~3개와 왜 거기에 공을 들였는지. 카드의 판단 근거와 실제 세팅 코드로 뒷받침한다. 무엇을 어떻게 붙였는지(세팅 흐름)도 이 항목 안에서 필요한 만큼 보여준다.

**고민** — 선택지가 둘 이상이었던 결정마다 `선택지 → 고른 것 → 이유`. 출처는 카드의 `## 논의`·`## 논의 필요`·`## 설계서`와 위키 `유형`이 `설계 판단`·`트레이드 오프 고민`·`고민`인 문서다. 결정 과정이 자료에 없으면 `자료에 없음` 한 줄.

**트러블 슈팅** — 위키 문서 하나당 한 묶음: `막힌 지점 → 원인 → 해결 → 교훈 한 줄`, 문서 링크 포함. 고른 문서 중 해당하는 게 없으면 `고른 기록에 트러블 슈팅 없음` 한 줄.

**더 확장/수정한다면** — 두 갈래로 나눠 표시한다.
- `자료 근거` — 카드의 `TODO`·남은 항목, 위키에서 `미확인 — 우회함`으로 넘어간 문제, 범위 밖으로 미룬 것
- `제안` — 위 사실과 현재 코드를 보고 내가 덧붙이는 개선 방향. 자료가 아니라 추론임을 드러낸다

마지막 줄: `더 파볼 부분이 있으면 물어보세요.` 이후 대화는 ③에서 모은 자료를 근거로 이어가고, 필요하면 ②의 다른 후보나 레포를 더 읽는다.

## 정지 조건

| 조건 | 대응 |
|---|---|
| 키워드가 없음 | 묻는다 |
| 두 DB 모두 접근 실패 | 에러와 함께 멈춘다. MCP를 `notion-home`으로 썼는지 먼저 확인 |
| 후보 없음 | 시도한 변형을 보여주고 다른 키워드를 묻는다 |

## 하지 않는 것

- 사용자가 고르기 전에 설명을 시작하지 않는다. 후보를 짐작으로 골라 진행하지 않는다.
- 노션 속성·본문, 레포 파일을 고치지 않는다.
- 근거 없는 내용을 내 작업으로 포장하지 않는다. `제안`은 `자료 근거`와 섞지 않는다.
- 요청 없이 퀴즈를 내거나 배운점 DB에 저장하지 않는다(복습은 `/learn:quiz` 몫).
