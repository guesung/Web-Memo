# 조합 페이지(programmatic SEO) 공개 기준

"지역 × 시술"처럼 두 축을 곱해 검색용 페이지를 늘리는 방식을 웹 메모에 쓸 때의 기준입니다.
새 조합 페이지를 기획하거나 만들기 전에 이 문서를 먼저 읽습니다.
방향의 근거는 [`docs/project-identity.md`](project-identity.md)입니다. 이 문서와 어긋나면 정체 문서를 따릅니다.

## 왜 기준이 필요한가

- 직군·용도 조합 페이지 `use-cases/*` 7개는 번역 키와 아이콘만 바꾼 템플릿(`LandingPageTemplate`)입니다. 7개월 동안 검색 유입이 합계 약 11명이었습니다(GA4, 2026-03-01~09-23, DB-1044).
- 조합마다 고유한 데이터가 없는 페이지를 많이 찍으면, Google 정책의 scaled content abuse·doorway 페이지에 해당합니다. 그러면 유입이 늘지 않을 뿐 아니라 사이트 전체 평가가 떨어질 수 있습니다.
- 2026-09-02에 도메인을 `webmemo.xyz`로 옮겼고, 옛 도메인에는 301 리다이렉트가 없습니다. 2026-10-10 기준으로 새 도메인의 공개 URL 25개 중 색인된 것은 2개뿐입니다. 색인이 쌓이기 전에 페이지를 늘리면 성과를 잴 수 없습니다.

## 고유 데이터 판정 기준

조합 페이지 하나는 **다른 조합 페이지에 없는 사실을 최소 하나** 가져야 공개합니다. 인정하는 것은 두 가지뿐입니다.

1. **출처와 확인 날짜가 있는 사실**
   - 공식 페이지에서 확인한 지원 여부·요금·제약입니다.
   - 출처 링크와 마지막 확인 날짜를 페이지에 함께 적습니다.
   - 선례는 `/ko/compare/chrome-memo-extensions`의 비교표입니다(`comparison.ts`, `COMPARE_LAST_CHECKED_DATE`).
2. **직접 실측한 결과**
   - 그 사이트에서 메모·요약·하이라이트가 실제로 되는지 직접 돌려본 결과입니다.
   - 스크린샷과 실측 날짜를 함께 남깁니다.
   - 웹 메모만 만들 수 있는 데이터입니다.

**문구 차별화는 고유 데이터로 인정하지 않습니다.** 같은 템플릿에서 단어·예시·문장 순서만 바꾼 페이지는 위 정책에 그대로 걸립니다. AI로 생성한 본문도 인정하지 않습니다.

## 축 후보와 정체 문서 제약

| 축 | 예 | 고유 데이터 | 정체 문서 제약 |
|---|---|---|---|
| ① 지원 사이트 × 작업 | 유튜브·velog·브런치·네이버 블로그 × 메모·요약·하이라이트 | 사이트별 실측 결과 | 요약은 일부 사이트에서만 됩니다. 실측 없이 요약 지원을 약속하지 않습니다 |
| ② 상황별 비교 | "유튜브 강의 정리용 확장 비교" | `comparison.ts`의 출처 있는 사실 | 포지셔닝의 "맞서는 상대는 다른 메모 확장이 아니다"와 "대비는 설명 텍스트에서만 말한다"를 지킵니다. 그래서 "X 대안" 제품별 페이지가 아니라 상황별 비교로 만들고, 웹 메모가 답이 아닌 상황에서는 다른 제품을 정직하게 추천합니다. "라이너 대안" 같은 검색어가 리포트에 실제로 잡히면 그때 다시 검토합니다 |
| ③ 직군 × 상황 | 기존 `use-cases/*` 확장 | 지금은 없음 | 고유 데이터를 붙이지 못하면 늘리지 않습니다. 기존 7개는 일단 그대로 두고, 파일럿 결과를 본 뒤 보강할지 통합할지 정합니다 |
| ④ 사용자 공개 메모(UGC) | 사용자가 공개를 고른 메모 | 사용자가 쓴 글 | 지금은 범위 밖입니다. 다시 검토하려면 세 가지가 먼저 갖춰져야 합니다. 메모 공유(읽기 전용 링크)가 있어야 하고, 사용자 본인 메모만 다뤄야 하고, AI 요약 공개는 빼야 합니다. 요약 공개는 "하지 않을 것: AI 자동 생성 콘텐츠 확대"에 걸리고, 남의 글을 요약한 것이라 저작권 문제도 있습니다. 한번 색인된 사용자 콘텐츠는 회수하기 어렵습니다 |

## 축 선택 절차

1. **GSC 수요 리포트를 한 번 실행합니다.**
   - GitHub Actions에서 `Report GSC Demand`(`report-gsc-demand.yml`)를 수동으로 실행합니다.
   - 실행 결과 아티팩트에서 `gsc-demand.md`를 엽니다.
2. **사이트맵 상태부터 확인합니다.** 제출 URL 수에 비해 색인 URL 수가 적거나 사이트맵 제출 기록이 없으면, 새 페이지보다 색인을 먼저 해결합니다. 해결 방법은 GSC 콘솔에서 사이트맵을 제출하고 주요 URL에 색인을 요청하는 것입니다.
3. **기회 검색어를 축 후보에 대어 봅니다.** 기회 검색어는 노출은 있지만 클릭이 적은 검색어입니다. 검색어가 어느 축(①·②·③)의 조합과 맞는지 묶어 보고, 실제 수요가 보이는 축 **하나**를 고릅니다.
4. **공개 페이지 성과에서 기준선을 적어 둡니다.** 기존 `use-cases`·`features`·`compare`·`introduce`의 노출·클릭이 파일럿 성공 판정의 기준선입니다.

리포트를 보지 않고 축을 고르지 않습니다. `use-cases`가 수요 확인 없이 만들어진 것이 이 문서의 출발점입니다.

## 파일럿 착수 조건과 규모

착수 조건은 아래 두 가지가 모두 갖춰지는 것입니다.

- 위 GSC 수요 리포트를 **1회 이상** 실행해 축을 골랐을 것
- DB-1044 비교 페이지(`/ko/compare/chrome-memo-extensions`, 2026-09-24 공개)의 **8주 판정**(2026-11-19 전후)이 나왔을 것

파일럿 규모와 범위는 다음과 같습니다.

- 고른 축 하나로 **3~5장**만 만듭니다. 사실 갱신 부담은 페이지 수에 비례하고, 작업은 퇴근 후·주말에만 합니다. 축이 틀렸을 때 지울 페이지도 적어야 합니다.
- **한국어만** 만듭니다. 영어판은 번역이 아니라 별도 글이고, 사실 데이터를 두 벌로 관리해야 합니다.
- 기존 `use-cases` 7개는 **유지합니다.** 다시 쓰거나 noindex로 돌리거나 통합하는 것은 파일럿 결과를 본 뒤에 정합니다.
- 다른 축은 동시에 시작하지 않습니다.

파일럿 성공 기준은 세 가지입니다.

1. 공개 4주 안에 GSC에서 "색인 생성됨"으로 확인됩니다.
2. 공개 8주 뒤, 파일럿 페이지의 합산 클릭이 같은 길이 기간의 `use-cases` 7개 합산 클릭보다 많습니다.
3. 파일럿 페이지마다 다른 조합 페이지에 없는 사실 항목을 하나 이상 가리킬 수 있습니다.
