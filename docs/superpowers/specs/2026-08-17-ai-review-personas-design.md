# 설계 문서 — 인턴/시니어 페르소나 AI 코드리뷰 워크플로우

**날짜**: 2026-08-17
**유형**: feature (개발 워크플로우 도구)
**상태**: 설계 승인 완료 (구현 전)
**대상 베이스 브랜치**: master
**작업 브랜치**: `guesung/코드-리뷰-워크플로우-만들기`

---

## 1. 배경 & 목표

### 1.1 만들려는 것

PR에 두 개의 서로 다른 페르소나를 가진 AI가 **각자의 GitHub 정체성으로** 코멘트를 달아 질문하고,
PR 작성자가 답변하면, 그 답변을 읽고 각자 재답변하는 워크플로우.

```
1. PR 생성
2. 이도현(인턴)   → "이 코드는 어떤 코드인가요?" 계열 질문 (인라인 코멘트)
   박성우(시니어) → "더 개선할 점이 없나요?" 계열 질문 (인라인 코멘트)
3. 작성자가 GitHub 웹에서 각 스레드에 답변
4. 이도현 → 이해한 내용 정리 + JSDoc suggested change
   박성우 → 수용/반박 + 구체적 개선안 + 후속 작업 체크리스트
5. 종료 (1턴 제한)
```

### 1.2 왜 만드는가

**설명하게 만드는 장치**다. 정적 분석 도구가 아니다.

- **인턴 질문에 답하면서** 내 코드의 의도를 스스로 언어화하게 된다. 그 결과물이 JSDoc으로 남는다.
- **시니어 질문에 답하면서** 내가 놓친 케이스를 스스로 떠올리게 된다. 그 결과물이 후속 작업으로 남는다.

"AI가 지적하고 내가 고친다"가 아니라 **"AI가 묻고 내가 설명한다"**가 핵심이다.
이 방향성을 잃으면 이 도구를 만들 이유가 없다.

### 1.3 성공 기준

- PR당 질문 6개를 **실제로 답변하게 되는** 양과 질이어야 한다. 답변하지 않으면 워크플로우 전체가 죽는다.
- 인턴 질문에 답한 내용이 코드 주석으로 남아야 한다.
- 시니어 질문에 답한 내용 중 내가 수용한 것이 후속 작업으로 남아야 한다.

## 2. 실행 방식 — 로컬 실행 (GitHub Actions 아님)

### 2.1 결정

**Claude Code 슬래시 커맨드로 로컬에서 수동 실행한다.** GitHub Actions를 쓰지 않는다.

### 2.2 근거

| 항목 | GitHub Actions 방식 | **로컬 실행 방식 (채택)** |
|------|---------------------|--------------------------|
| 비용 | Anthropic API 키 필요, 월 약 $10 (PR 12건 기준) | Claude Code 구독 활용, 추가 비용 0 |
| 무한루프 위험 | **있음** — App 토큰 코멘트가 워크플로우를 재트리거 | **없음** — 자동 트리거 자체가 없음 |
| 컨텍스트 | diff만 (토큰=비용이라 상한 필요) | **레포 전체** 읽기 가능 |
| Secrets | public 레포에 API 키 + App private key 보관 | 로컬에만 보관 |
| 트리거 | 자동 | 수동 (커맨드 2회) |

**무한루프 함정**: GitHub의 기본 `GITHUB_TOKEN`은 재귀 트리거 방지가 내장돼 있지만,
**GitHub App 설치 토큰으로 만든 코멘트는 워크플로우를 다시 트리거한다.**
Actions 방식을 택했다면 봇 판별 가드가 선택이 아니라 필수였다. 로컬 실행은 이 문제를 통째로 제거한다.

**컨텍스트가 비용보다 중요한 이유**: 이 워크플로우의 성패는 "질문이 얼마나 좋은가"다.
diff만 보고 던지는 질문은 뻔하다. 변경 파일의 전체 내용, 호출부, 기존 컨벤션을 다 읽고
묻는 질문이라야 답변할 마음이 생긴다.

### 2.3 전제 조건 (중요)

**수동 트리거 유지가 이 설계의 전제다.**
나중에 cron이나 `/loop`로 감싸 무인 자동화로 돌리면 Claude Code 구독의 일반적 사용 범위를 벗어난다.
무인 자동화가 필요해지는 시점에는 §2.2의 Actions + API 키 방식으로 되돌아가야 한다.

### 2.4 잃는 것 (수용함)

- 팀원이 트리거할 수 없다 (내 로컬에서만 실행)
- 내 터미널이 없으면 안 돌아간다

현재 이 레포 사용 형태(사실상 1인 개발)에서는 문제가 되지 않는다.

## 3. 봇 정체성

### 3.1 GitHub App 2개

| | 이름 | App slug | 캐릭터 |
|---|------|----------|--------|
| 인턴 | **이도현** | `lee-dohyun` | 6개월차. 모르는 걸 모른다고 묻는다 |
| 시니어 | **박성우** | `park-seongwoo` | 10년차. 되묻고, 그 다음 답을 준다 |

### 3.2 이름 표시의 제약 (알려진 한계)

GitHub PR 타임라인에서 **작성자 자리에 렌더링되는 것은 App의 slug**다 (`lee-dohyun[bot]`).
한글 이름은 작성자 자리에 표시되지 않으며, 한글만으로 App 이름을 지으면 slug가 정상 생성되지 않는다.

**대응**: 아바타 이미지 + 코멘트 본문 첫 줄 서명으로 한글 이름을 살린다.

```markdown
**이도현** · 인턴 개발자

이 부분 좀 여쭤봐도 될까요? ...
```

### 3.3 App 권한

| 권한 | 수준 | 용도 |
|------|------|------|
| Pull requests | Read and write | 리뷰 코멘트 게시, PR 본문 수정 |
| Contents | Read | commit SHA 조회 |
| Metadata | Read | 필수 기본 권한 |

### 3.4 자격 증명 보관

App private key 2개는 **`~/.config/web-memo-bots/` 에 보관**한다.
레포에는 경로만 참조한다. **이 레포는 public이므로 키가 커밋되면 즉시 유출된다.**

```
~/.config/web-memo-bots/
  lee-dohyun.pem
  park-seongwoo.pem
  config.json      # { appId, installationId } × 2
```

`.gitignore`에 `*.pem` 을 추가해 실수를 한 겹 더 막는다.

## 4. 스레드 상태 판별 — 외부 상태 저장소 없음

### 4.1 문제

"어떤 스레드가 재답변이 필요한가"를 알아야 한다. 로컬 실행이므로 상태를 들고 있을 프로세스가 없다.

### 4.2 해법

**GitHub 데이터만으로 완전히 판별한다.** 상태 파일도, DB도 필요 없다.

`GET /repos/guesung/web-memo/pulls/{n}/comments` 가 반환하는 각 리뷰 코멘트의
`in_reply_to_id` 로 스레드를 복원한 뒤, 아래 3조건을 **모두** 만족하는 스레드를 처리 대상으로 삼는다.

1. root 코멘트가 우리 봇이 단 것 (본문 마커로 식별 — §4.3)
2. 스레드 안에 **PR 작성자**의 답글이 있다
3. 작성자의 **첫** 답글 이후에 해당 봇의 답글이 **없다**
   (판정 기준은 첫 답글, 재답변에 넘기는 `authorReply` 값은 마지막 답글 — 둘은 다르다)

### 4.3 마커

봇이 다는 모든 코멘트 본문 끝에 HTML 주석 마커를 남긴다 (렌더링되지 않음).

```html
<!-- ai-review:intern:q3 -->
<!-- ai-review:senior:q1 -->
<!-- ai-review:senior:scan -->
<!-- ai-review:intern:reply -->
```

봇 식별을 `user.login` 이 아니라 마커로 하는 이유: **App 이름을 나중에 바꿔도 기존 스레드가 깨지지 않는다.**

### 4.4 1턴 제한이 공짜로 구현된다

조건 3이 곧 1턴 제한이다. 봇이 한 번 답하는 순간 조건 3이 깨져 다시 처리되지 않는다.
**턴 카운터, 상태 파일, 별도 플래그가 전혀 필요 없다.**

부수 효과 — 의도한 동작:
- 내가 답변을 여러 번 나눠 써도 봇은 한 번만 답한다
- 봇 답변 뒤에 내가 또 답글을 달아도 봇은 침묵한다

## 5. `/ai-review` — 질문 생성

### 5.1 동작

1. 현재 브랜치의 PR 번호 확인 (`gh pr view --json number`)
2. `git diff origin/master...HEAD` 로 변경 내역 수집
3. **컨텍스트 수집** — 변경 파일의 전체 내용, 주요 호출부, `AGENTS.md` 컨벤션
4. **한 번의 사고 흐름에서 두 페르소나 질문을 동시에 생성** (서로 중복 방지)
5. 각 봇의 installation token 으로 인라인 리뷰 코멘트 게시
6. 박성우의 지적 요약 코멘트 1건 추가 게시 (§5.3)

### 5.2 질문 개수

**기본값 각 3개, 총 6개.** 커맨드 인자로 조절 가능 (`/ai-review 5`).

근거: PR당 20개가 달리면 답변을 안 하게 되고, 답변하지 않으면 워크플로우가 죽는다(§1.3).
3개면 "다 답해볼까" 싶은 양이다.

### 5.3 박성우의 지적 요약 코멘트 (질문과 별개)

CodeRabbit을 사용하지 않기로 했으므로, 오타·명백한 버그·컨벤션 위반을 잡을 주체가 없다.
박성우가 **소크라테스식 질문 스레드와 분리된** 요약 코멘트 1건으로 이를 메운다.

```markdown
**박성우** · 시니어 개발자

질문과 별개로 눈에 띈 것들입니다. 답변 안 하셔도 됩니다.

- `MemoCard.tsx:34` — `isOpen` → `isDeleteModalOpen` (컨벤션 2: 구체적 네이밍)
- `useMemoQuery.ts:12` — `export`인데 JSDoc 누락 (컨벤션 1)
- `api/memo.ts:88` — `then` 사용, `async/await`로 (컨벤션 6)

<!-- ai-review:senior:scan -->
```

이 코멘트는 §4.2의 조건 1을 만족하지 않도록 **일반 PR 코멘트**(리뷰 코멘트 아님)로 단다.
따라서 재답변 대상에서 자동으로 제외된다.

`AGENTS.md`에 컨벤션이 명문화돼 있어 기계적으로 잘 잡힌다.

## 6. `/ai-review-reply` — 재답변 + 산출물 반영

### 6.1 동작

1. PR의 리뷰 코멘트 전부 조회
2. §4.2 조건으로 미답변 스레드 추출
3. **전체를 한 번에 읽고 배치 처리** — 스레드별 개별 실행이 아님
4. 각 스레드에 해당 봇 명의로 답글 게시
5. 산출물 반영 (§6.2, §6.3)

배치 처리가 Actions 방식보다 나은 지점이다. Actions는 답글 하나마다 워크플로우가 따로 돈다.

### 6.2 인턴 스레드 → 코드 주석

내 설명을 JSDoc으로 정리해 **GitHub suggested change 블록**으로 제안한다. 클릭 한 번으로 커밋된다.

````markdown
**이도현** · 인턴 개발자

아 캐시 무효화 때문이었군요. 이해했습니다!
나중에 저 같은 사람이 또 헷갈릴 것 같아서 설명해주신 걸 주석으로 정리해봤는데 맞을까요?

```suggestion
/**
 * 메모 목록 쿼리
 * @description 태그 필터 변경 시에도 캐시를 유지하기 위해 queryKey에서 tag를 제외한다.
 */
export const useMemoListQuery = ...
```

<!-- ai-review:intern:reply -->
````

이 레포 컨벤션 1번(모든 `export` 대상에 JSDoc)과 정확히 맞물린다.

**제약**: suggested change 는 코멘트가 **정확한 라인**에 달려 있어야 동작한다.
질문 게시 이후 커밋이 추가돼 라인이 어긋난 경우 suggestion 블록 없이 일반 답글로 폴백한다.

### 6.3 시니어 스레드 → 구체적 개선안 + 후속 작업

**질문 단계는 소크라테스식을 유지하되(§7.2), 재답변 단계에서는 구체적 답을 준다.**
순서가 바뀐 게 아니라 뒷단이 추가된 구조다 — 질문으로 내 생각을 먼저 끌어낸 뒤 그 위에 답을 얹는다.

````markdown
**박성우** · 시니어 개발자

아 의도적으로 그렇게 두신 거군요.
그럼 태그가 20개 넘어가는 케이스만 짚고 넘어가면 될 것 같은데, 이렇게 하면 어떨까요?

```suggestion
const queryKey = ['memos', workspaceId, tags.length > TAG_KEY_THRESHOLD ? 'all' : tags];
```

<!-- ai-review:senior:reply -->
````

**후속 작업 반영** — 내가 수용한 항목만 PR 본문에 누적한다.

```markdown
<!-- ai-followup:start -->
## 🔭 후속 작업 (시니어 리뷰)

- [ ] `useMemoListQuery` 캐시 무효화 범위 축소 — #412 스레드
<!-- ai-followup:end -->
```

- 마커 사이 구간만 교체하므로 `PULL_REQUEST_TEMPLATE.md` 내용은 보존된다.
- 내가 "의도한 겁니다"라고 답한 항목은 추가하지 않는다.
- 섹션이 없으면 PR 본문 맨 끝에 새로 만든다.

## 7. 페르소나 프롬프트

이 워크플로우의 성패가 여기에 달려 있다.

### 7.1 이도현(인턴) — 금지 사항

| 금지 | 이유 |
|------|------|
| 코드 지적 | 6개월차가 시니어 코드를 지적하면 인턴이 아니다 |
| 개선 제안 | 위와 동일 |
| 아는 척 | "아마 ~때문이겠지만" 류의 추측성 서두 금지 |

**오직 "왜 이렇게 하셨는지"만 묻는다.**
인턴이 지적하기 시작하면 "내가 설명하며 스스로 정리한다"는 이 워크플로우의 절반이 사라진다.

> 참고: 이 제약은 CodeRabbit 회피 목적이 아니라 **페르소나 일관성** 때문이다.
> CodeRabbit을 쓰지 않기로 한 뒤에도 이 제약은 유지된다.

### 7.2 박성우(시니어) — 질문 단계 규칙

**질문 단계에서는 답을 주지 않는다.** "이렇게 고치세요"가 아니라 "X 상황에서는 어떻게 되나요?"로 묻는다.

근거: 원 요구사항이 "시니어가 '더 개선할 점이 없나요?' 나에게 질문한다"이다.
질문 단계에서 답을 주면 내가 생각할 기회가 사라지고, 애초 요청한 플로우가 성립하지 않는다.

재답변 단계에서는 구체적 답을 준다(§6.3). 지적 요약 코멘트도 별도로 단다(§5.3).

### 7.3 공통 규칙

- 코멘트는 **항상 한글**
- 첫 줄은 `**이름** · 직급` 서명
- 인라인 코멘트는 반드시 `path` + `line` 지정
- 본문 끝에 마커(§4.3)

## 8. 파일 구성

```
.claude/commands/
  ai-review.md              # 질문 생성 커맨드
  ai-review-reply.md        # 재답변 + 산출물 반영 커맨드

scripts/ai-reviewer/
  appToken.ts               # App private key → installation token 발급
  personas/
    intern.md               # 이도현 페르소나 프롬프트
    senior.md               # 박성우 페르소나 프롬프트
```

**`.github/workflows/` 추가 없음. Secrets 추가 없음. API 키 없음.**

### 8.1 `appToken.ts`

`gh` CLI에는 App installation token 발급 기능이 없어 스크립트가 필요하다.

- App private key로 JWT(RS256) 서명 → `POST /app/installations/{id}/access_tokens`
- 발급 토큰 수명 1시간 — 커맨드 실행 시점에 매번 새로 발급 (캐싱하지 않음)
- **추가 의존성 없음** — Node 내장 `node:crypto`(RS256 서명)와 전역 `fetch`만 사용한다

### 8.2 실행 환경

- **`.nvmrc` = v24. Node 24는 TypeScript를 네이티브로 실행한다** (타입 스트리핑).
  `node scripts/ai-reviewer/cli.ts` 로 바로 실행되며 `tsx`나 빌드 단계가 필요 없다.
  - 제약: 타입 스트리핑은 *지울 수 있는 문법*만 지원한다. `enum`, `namespace`,
    생성자 파라미터 프로퍼티는 쓸 수 없고, 타입 전용 import는 `import type`으로 명시해야 한다.
- 테스트는 루트 vitest를 쓴다. `vitest.config.ts`의 `include`가 `**/*.test.ts`이므로
  `scripts/ai-reviewer/*.test.ts`가 자동으로 수집된다.
- **biome는 `scripts/`를 검사하지 않는다** (`biome.json`의 `files.includes`가
  `**/src/**`, `**/app/**`, `e2e/tests/**`로 한정). `pnpm lint`가 이 코드를 잡아주지
  않으므로 포맷(탭 인덴트)은 수동으로 맞춘다.
